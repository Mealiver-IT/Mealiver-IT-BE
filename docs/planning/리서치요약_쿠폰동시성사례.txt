# 밀리버릿 프로젝트 — 핵심 요약 (프로젝트 지식용)

> 대규모 트래픽 선착순 쿠폰 발급 시스템. 팀명 "태진아", 프로젝트명 "밀리버릿(MealiVit)".
> 배민 스타일 배달앱의 점심 오픈런 쿠폰(재고 10,000장, 재고 초과 발급 절대 0건)을 소재로 한 동시성·정합성 프로젝트. 같은 주제로 4팀 경쟁, 시상 있음.
> 기술스택: Java/Spring Boot, MySQL, Redis(로컬 Docker Compose). 평가축은 처리량이 아니라 **동시성 정확성**과 **정합성 자기검증**.

---

## 1. 핵심 요구사항 (원본 과제 요약)

- 재고 10,000장에 20,000명 동시 요청 → 초과발급 0건, 1인 최대 1매
- 발급/사용/취소/만료 상태 전체 관리, 동일 요청 중복·동시 발생해도 1회만 반영(idempotency)
- 300만 건 발급이력 전체 대상 정합성 자기검증(결정론적 재실행 가능해야 함)
- 100만 유저·300만 이력 더미데이터, PII 마스킹 필수, 알림은 Mock 처리
- 회원가입/로그인 미구현(가상 회원)

## 2. 확정된 아키텍처 결정

| Phase | 전략 | 핵심 이유 |
|---|---|---|
| **Phase 1 (MVP)** | DB 비관적 락(`SELECT...FOR UPDATE`) | 추가 인프라 없이 정확성부터 증명. 배민 파일럿 프로젝트(2023) 사례와 동일 논리(synchronized는 여러 서버에서 무의미해서 기각) |
| **Phase 3 (하드닝)** | Redis **이중 카운터(DualCounter)** | Lua보다 단순하고 가벼움(올리브영 실측: Lua 21%저하 vs 이중카운터 8%저하). 중복체크는 DB unique 제약이 최종방어선 |
| 검토 후 기각 | Redisson 분산락 | Kleppmann("How to do distributed locking", 2016)의 비판 근거 — fencing token 부재로 정합성 보장 부적합. 컬리도 Redisson은 "효율성" 목적으로만 사용 |
| 검토 후 기각 | V3(재고+중복 통합 Lua, 알리바바 패턴) | 장애 시 영향범위가 재고+중복 둘 다 커짐, 구현복잡도 상승. "검토했으나 기각" 발표카드로만 활용 |

### 버전 라벨링 규칙
- **메이저(V1→V2→V3)**: 원자성이 "보장하는 범위" 자체가 바뀔 때 (예: 재고판정 권한이 DB→Redis로 이동)
- **마이너(V2.0→V2.1)**: 보장범위는 같고 구현방법만 바뀔 때 (예: Lua→INCR 방식 교체)
- 최종: V1.0(DB락) → V2.0(Redis Lua 게이트) → **V2.1(이중카운터, 최종채택)** → V2.2(SADD 프리체크, Phase4 선택) / V3.0(풀Lua통합, 기각)

### DB 필수 제약 (Defense in Depth)
```sql
ALTER TABLE coupon_issue ADD CONSTRAINT uk_campaign_user UNIQUE (campaign_id, user_id);      -- 1인1매 최종방어선
ALTER TABLE coupon_issue ADD CONSTRAINT uk_idempotency_key UNIQUE (idempotency_key);          -- 중복요청 방지
ALTER TABLE coupon_issue ADD CONSTRAINT uk_coupon_code UNIQUE (coupon_code);
ALTER TABLE coupon_issue ADD COLUMN version BIGINT NOT NULL DEFAULT 0;                        -- 상태전이 낙관적락
```
Redis는 반드시 **마스터 단일노드**로만 구성(복제 안 씀) — 배민 빼빼로데이 반례가 근거.

## 3. 우리만의 독자적 발견 — countReq 조기소진 이슈 ⭐(발표 핵심 포인트)

**문제**: 이중카운터 구조에서 `countReq`(1차 필터, 검증 전 증가) → `count`(2차 확정)로 나뉘는데, 1인1매 위반이나 idempotency key 충돌로 "죽는 요청"도 `countReq`는 이미 소모함. 이게 쌓이면 재고가 실제로 남았는데도 신규 유저가 "품절"로 조기 거절될 수 있음.

**검증 결과**: 이건 **초과발급 문제가 아니라 UX/공정성 문제**. `count`(2차 관문)는 독립적으로 자체 롤백하므로 총 발급량이 `totalStock`을 절대 못 넘음(수학적으로 증명됨).

**원인 정정**: 1인1매 위반뿐 아니라 **DB unique 제약에 사후적으로 걸리는 모든 케이스**(동일 idempotency key 동시요청 포함)가 원인.

**대응안 비교**:
- A안(countReq 버퍼링 1.2배): 근본해결 아님, 확률게임
- B안(countReq도 롤백): 이중카운터의 존재이유(저비용 1차필터) 희석됨
- **C안(감수) — 채택**: 채점기준(FR-03 "초과발급 0건")이 이 케이스를 안 봄 + 메인 부하테스트 시나리오(20,000명 **서로 다른 유저**)에서는 애초에 발현 안 됨
- D안(SADD 프리체크, Phase4 선택): 중복유저를 countReq 이전에 걸러 완전 해결 — 단, 완전 동시 요청(더블클릭)엔 여전히 구멍 있음(최종방어선은 DB unique)

**서브 시나리오 주의사항**: "5,000명이 4회씩 재요청" 테스트 시, 재고를 5,000명이 딱 맞게 받는 양으로 설계하면 라이브 데모에서 "재고 남았는데 왜 다 못받지?" 현상이 화면에 찍힐 수 있음 → 재고를 여유있게 설계하거나 발표 스크립트에 미리 대응 준비.

## 4. 국내외 업계 사례 리서치 핵심 (발표 근거)

### 국내
| 기업 | 핵심 내용 |
|---|---|
| 배민 파일럿(2023) | synchronized 실패→비관적락 채택. "여러 서버에선 로컬락 무의미" |
| 배민 빼빼로데이(2016) | ⚠️반례: Redis **복제 노드**에서 카운터 읽어 선착순 1,111명 초과발급 실제 발생. "카운터는 마스터만 참조해야" |
| 배민 선물하기(2021) | Redis Set+SCARD로 재고관리, RDB 이력 이원화(fast path+ground truth) |
| 배민 47만RPM 이벤트 | Redis Sorted Set 대기열로 트래픽 자체를 조절 |
| 올리브영(2025) | Lua 21%저하로 기각→이중카운터(8%저하) 채택. **우리가 채택한 패턴의 원출처** |
| 여기어때(2022) | Redis INCR+Kafka, TPS3600+에서 초과발급 0건 |
| 토스(2024) | RedLock+Increment+Kafka. 로컬캐시 집계는 "hard capping 아님"이라고 스스로 인정 |
| 컬리(2023) | Redisson 분산락, 트랜잭션 커밋 후 락해제 원칙 |

### 해외
| 기업 | 핵심 내용 |
|---|---|
| 알리바바/Tmall | 초당 583,000건. CDN→Redis필터→Lua원자적차감→비동기주문 4계층. 2012년 초과발급 사건(비공식, 배민 반례와 대응) |
| AWS/DynamoDB | 초당1.51억요청. 낙관적락+조건부쓰기+가상대기실(JWT) |
| SeatGeek(AWS) | "토큰=티켓 1:1 발행" — 초과발급 구조적으로 불가능하게 만드는 아이디어 |
| Walmart | 파티션당 단일소유자 액터(락 없이 경합 제거) — 우리 미검토 대안 |
| **Kleppmann(2016)** | Redlock은 정합성 목적 부적합, fencing token 필요 — 우리 Redisson 기각 근거 |
| Nike SNKRS | FCFS→무작위추첨 전환(봇 경쟁 회피) — 공정성 대안 참고용 |

**핵심 공통 결론**: 국내외 모두 "① 트래픽 셰딩 → ② 단일권한 원자적 차감 → ③ idempotency로 비동기 후처리" 3단계로 수렴.

## 5. 발표 스토리라인 (9막 구조)

**컨셉**: 결론만 보여주지 않고 "V1으로 시작→문제발견→대안검토→새문제발견→최종결정"의 여정을 그대로 보여줌. 다른 팀과의 차별화 포인트.

```
Act0 문제정의(재고1만 vs 요청2만) → Act1 V1(DB락) 시도, hot row 문제 발견
→ Act2 Redis Lua 도입(V2.0) → Act3 Lua의 두 그림자(올리브영 성능↓, 배민 정합성↓ 반례)
→ Act4 분산락 검토·기각(Kleppmann) → Act5 이중카운터 발견(V2.1 채택)
→ Act6 countReq 이슈 발견·검증·C안 채택(★우리 독자 발견, 발표 최대 비중)
→ Act7 최종 아키텍처 확정 → Act8 검증(부하테스트+정합성쿼리+결정론적해시) → Act9 클로징
```
시간배분: 도입15% / 여정55% / 검증+결론20% / 클로징10%

## 7. 정합성 검증 설계 요지 (system_design.md 기반)

- 검증 쿼리 4종: (a)재고초과여부 (b)유저당중복발급 (c)카운터-이력 불일치 (d)상태전이 위반
- **결정론성 필수**: `NOW()` 등 시점의존 조건 배제, 결과셋 정렬 후 SHA-256 해시로 재실행 동일성 기계적 확인
- 오염 데이터(의도적 위반 샘플) 삽입 → 검증배치가 정확히 탐지하는지까지 증명 (차별화 전략 1번)
- SQL 집계쿼리(개발중 수시실행용) + Spring Batch Job(정식 리포트용) 이원화
