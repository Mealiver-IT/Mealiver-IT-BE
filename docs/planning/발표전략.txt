# 발표 전략

> 이 문서를 처음 읽는 사람(또는 AI)을 위한 배경
>
> - 프로젝트: 대규모 트래픽 선착순 쿠폰 발급 시스템 (팀명 태진아 / 프로젝트명 밀리버릿)
> - 소재: 배달앱 오전 11시 오픈 선착순 할인 쿠폰
> - 상황: 같은 주제로 4팀이 순서대로 발표. 시상 있음. LG 부트캠프 심사
> - 배점 인식: 기술성 + 수행능력 60%, 프론트 10%
> - 관련 문서: 03_버전사다리(결과표) / 07_실행계획 / 리서치요약(9막 구조 원안) / 01_설계보완검토안

이 문서는 리서치요약 5절의 9막 구조를 대체하는 것이 아니라, 순서를 재배치한 것이다.
내용은 대부분 그대로 살아있고 배치만 바뀐다.


================================================================
1. 전제 — 무엇이 차별점이고 무엇이 아닌가
================================================================

차별점이 아닌 것 (4팀 전부 보여줌):
  - 문제 정의 (재고 10,000 vs 요청 20,000, 테스트 유저 20,000명 중복없음 / ramp-up 60초 — 멘토가 전 팀 공통조건으로 확정)
  - 20,000 요청 → 10,000 발급 → 초과 0건
  - Redis를 썼다는 사실
  - 부하테스트를 돌렸다는 사실

이것들은 과제 통과 조건이지 차별점이 아니다.
"20,000 요청에 초과 0건"이 발표의 클라이맥스라면, 4팀의 클라이맥스가 전부 같아진다.

차별점인 것 (우리만 가진 것):
  - V1(고장난 버전)부터 V4까지의 실측 대조표
  - 장애를 일부러 주입하고도 0건을 유지하는 시연
  - 검증 배치가 실제 위반을 탐지하는 증명 (V1이 만든 진짜 오염 데이터 사용)
  - countReq 조기소진 이슈 자체 발견
  - 국내외 17개 기업 사례 기반 의사결정
  - 명시적 비목표 문서화

발표 구성은 이 차별점들에 시간을 몰아주는 방향으로 짠다.


================================================================
2. 핵심 결정 — 문제 정의로 시작하지 않는다
================================================================

리서치요약 5절의 원안은 Act0(문제정의)로 시작해 도입에 15%를 쓴다.
이 배치를 바꿀 것을 권한다. 이유는 세 가지다.

  (1) 이 문제는 심사위원이 출제한 문제다.
      그들은 재고 10,000에 요청 20,000이 온다는 것을 이미 안다.

  (2) 4팀이 순서대로 같은 문제 정의를 반복한다.
      3번째 팀쯤 되면 심사위원은 이미 그 설명을 세 번 들은 상태다.

  (3) 우리의 가장 강한 카드(장애 주입)를 뒤로 미룰 이유가 없다.
      발표 후반은 집중도가 떨어지는 구간이다.

[대안: 콜드 오픈]

  0:00  "부하 테스트를 돌리면서, 중간에 Redis를 죽이겠습니다."
        → 실행. 화면에 재고 카운트다운.
        → Redis 강제 종료. 대시보드가 잠깐 흔들린다.
        → 복구. 최종 발급 건수 10,000. 초과발급 0건.

  1:30  "이게 어떻게 가능한지 지금부터 설명드리겠습니다."

90초다. 그리고 다른 세 팀은 이것을 하지 않는다.
심사위원이 4팀을 다 보고 나서 기억하는 장면이 이것 하나면 충분하다.

이후의 여정(V1 → V2 → V3 → V4, countReq 발견)은 연대기가 아니라
"방금 본 그 견고함이 어디서 나왔는가"에 대한 설명이 된다.
같은 내용인데 훨씬 잘 붙는다.

3. 구성과 시간 배분
================================================================

  10%  콜드 오픈 — 장애 주입 라이브 데모
  20%  최종 아키텍처 — 왜 견디는가 (슬라이드 1장)
  30%  여정 — V1 병목 → V2 → V3 전환 → countReq 자체 발견
  25%  검증 — 오염 데이터 유형별 탐지 + 결정론성 해시
  10%  명시적 비목표
   5%  클로징

[각 구간에서 반드시 나와야 하는 것]

  콜드 오픈
    - Redis를 실제로 죽인다 (docker stop 또는 redis-cli shutdown)
    - 대시보드에 재고 카운트다운이 보인다
    - 최종 DB COUNT가 정확히 10,000임을 화면으로 확인

  최종 아키텍처
    - Redis 게이트 + DB 조건부 UPDATE 백스톱 + 워밍업 3겹 구조
    - "Redis는 속도, DB는 최종 진실" 한 문장으로 요약
    - 04_아키텍처 4.2절 내용

  여정
    - V1: 제어가 없으면 실제로 이렇게 됩니다 (30초. 길게 설명하지 말 것)
    - V2: 락으로 막으면 정확하지만 이렇게 느립니다 (30초)
    - V3: Redis로 빼면 빨라집니다. 그런데 Redis가 죽으면? (여기가 본론 진입)
    - countReq 조기소진 발견 — 우리 팀 고유 인사이트. 비중 크게
    - V4: 그래서 백스톱을 넣었습니다 → 콜드 오픈으로 되돌아온다 (수미상관)

  검증
    - "위반 0건"만 보여주는 것은 아무것도 증명하지 못한다.
      검증 로직이 비어 있어도 같은 결과가 나오기 때문이다.
    - 그래서 V1을 실제로 돌려 나온 진짜 위반 데이터를 먹여서 탐지시킨다
    - 유형별 탐지: 초과발급 / 중복발급 / 상태역행 / idempotency 충돌 / 등급위반
    - 결정론성: 2회 실행 결과 해시 동일

  명시적 비목표
    - 취소 시 재고 복구 미지원 (allow_reissue_on_cancel = false, 재고 카운터 한정 — 취소된 쿠폰 본인 재사용은 별개로 허용)
    - 엄밀한 FCFS 순서 미보장
    - Kafka 비동기 분리 미채택
    - 각각 "안 한 것"이 아니라 "판단해서 안 한 것"으로 서술

[리서치 슬라이드는 1장으로 압축한다]
  17개 기업 사례는 의사결정의 각주이지 본론이 아니다.
  발표가 문헌 조사처럼 보이면 주인공이 "우리 시스템"이 아니라 "남의 사례"가 된다.
  배민 빼빼로데이 반례와 Kleppmann 정도만 여정 안에서 인용하고, 나머지는 부록으로.

6. 예상 질문과 답변 준비
================================================================

Q1. "왜 Kafka를 쓰지 않았나요?"
  → 10,000건 규모에 Kafka는 과설계라고 판단했습니다.
     또한 eventual consistency가 발생하면 "즉시 정합성 검증"이라는 이 과제의
     핵심 평가 포인트와 설명 부담이 커집니다.
     트래픽 스파이크 흡수가 필요한 규모라면 채택했을 것이고,
     그 경계를 어디로 볼지는 저희가 검토한 내용입니다.

Q2. "Redisson 분산락은 왜 기각했나요?"
  → Kleppmann의 2016년 분석에 따르면 Redlock은 fencing token이 없어
     정합성 목적에는 부적합합니다. 컬리도 Redisson을 효율성 목적으로만 씁니다.
     저희 목표가 정확성이므로 목적이 맞지 않는다고 판단했습니다.

Q3. "countReq 조기소진을 감수했다는데, 재고가 남는 건 문제 아닌가요?"
  → 초과발급 문제가 아니라 UX/공정성 문제입니다.
     2차 관문인 count가 독립적으로 롤백하므로 총 발급량은 total_stock을 넘지 못합니다.
     다만 재고가 남았는데 품절 처리되는 케이스는 발생할 수 있고,
     이것이 실측에서 어떻게 나타났는지가 저희 결과표에 있습니다.
     (V3 A/B 측정 결과에 따라 이 답변은 조정된다. 03_버전사다리 4절 참고)

Q4. "Redis가 죽으면 어떻게 되나요?"
  → 그것을 콜드 오픈에서 보여드렸습니다.
     DB 조건부 UPDATE가 총량을 잡고, 복구 후 워밍업이 DB 실제 발급 수 기준으로
     카운터를 재동기화합니다. V3는 이 상황에서 무너지고 V4는 견딥니다.

Q5. "검증 배치가 정말 작동하나요? 위반 0건이면 로직이 비어 있어도 0건인데요."
  → 정확한 지적입니다. 그래서 저희는 양방향으로 테스트했습니다.
     정상 데이터에서 0건, 그리고 V1을 실제로 돌려 나온 진짜 위반 데이터에서
     정확히 N건을 탐지하는 것까지 확인했습니다.
     (이 질문은 반드시 나온다. 준비된 답이 있으면 크게 가점된다)

Q6. "1인 1매는 어떻게 보장하나요?"
  → DB의 uk_campaign_user 유니크 제약이 최종 방어선입니다.
     애플리케이션 레벨 제어가 버그로 뚫려도 DB가 물리적으로 두 번째 INSERT를 거부합니다.
     다만 이 제약은 1인 1매만 막고 총량 초과는 막지 못하는데,
     그 사실을 V1 실행 결과로 실증했습니다.

Q7. "300만 건 검증이 얼마나 걸리나요?"
  → 실행 시간은 과제 평가 대상이 아니라고 명시되어 있어 최적화 우선순위를 낮췄습니다.
     대신 결정론성에 집중했습니다. 필요한 인덱스는 설계했고 EXPLAIN으로 확인했습니다.
     (실제 측정값을 넣을 것)

Q8. "취소하면 재고가 복구되나요?"
  → 복구하지 않습니다. 명시적 비목표로 문서화했습니다.
     복구를 허용하면 "발급 총량 ≤ 재고" 불변식이 깨져 검증 설계 전체를 다시 해야 하고,
     Redis 카운터 복구와 DB 상태전이 사이에 새로운 경쟁 상태가 생깁니다.
     요구사항에 없는 유연성보다 정합성 검증의 단순함을 택했습니다.

Q9. "성능이 평가 대상이 아닌데 왜 버전 비교를 했나요?"
  → 성능 자체를 자랑하려는 것이 아니라, 각 버전이 서로 다른 이유로 실패한다는 것을
     보여주기 위해서입니다. V1은 정확성, V2는 확장성, V3는 내결함성에서 무너집니다.
     처리량은 그 실패를 드러내는 지표일 뿐입니다.

Q10. "실제 서비스라면 무엇을 더 해야 하나요?"
  → 대기열(Sorted Set) 도입으로 트래픽 자체를 조절하는 것,
     Redis 복제 구성 시 마스터만 참조하도록 강제하는 것,
     취소 재고 복구 정책 등입니다.
     특히 복제 노드 참조 문제는 배민 빼빼로데이 사례에서 실제 초과발급이 발생했던
     지점이라, 저희는 마스터 단일 노드로 제한했습니다.

Q11. "이 부하테스트, 저희가 직접 실행해봐도 되나요?"
  → 네. 멘토 확인 결과 심사위원분들이 직접 실행해보실 수 있다고 안내받았습니다.
     그래서 초기화(재고 리셋·Redis 카운터 삭제·워밍업)부터 실행까지 원커맨드 스크립트로
     구성해뒀고, 저희가 쓴 것과 동일한 재현 가이드를 GitHub/구글드라이브에 함께 올려뒀습니다.
     조건은 다른 팀과 동일하게 테스트 유저 20,000명(중복없음) / ramp-up 60초입니다.

Q12. "이 팀은 백엔드를 잘 이해하고 있다고 느끼게 하는 차별점이 뭔가요?"
  → (멘토 답변: 평가 기준은 세부과업 수행여부 + 전체 밸런스 + 완성도. 정답이 따로 없는 질문이므로
     아래는 우리 답변 초안 — 실측 확정 후 구체 수치로 보강할 것)
     V1→V4 대조 실측, 장애 주입 후 복구, 검증 배치의 실제 위반 탐지 증명, 이 세 가지를
     "말"이 아니라 "라이브 데모"로 보여드리는 것입니다.

7. 클로징 문장 후보
================================================================

발표 마지막 30초에 남길 한 문장. 팀에서 골라 쓸 것.
