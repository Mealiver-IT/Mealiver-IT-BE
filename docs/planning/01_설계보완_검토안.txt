## 1. 결정 안건 A — 멤버십 "배치 자동 산정" 축소 여부 ⭐ 최우선

### 문제

Phase 1 목록에 다음이 전부 들어 있다(3인 기준):

> 도메인 모델 + 발급 API + 비관적 락 + 멤버십 4단계 + eligibility + `MembershipTierBatchJob` + 상태전이 API + 상태머신 + **유저 100만 + orders 약 1,000만** + 300만 발급이력 + 검증 SQL 5종 + 프론트 2화면 기능 + 4화면 mockup

[일정과역할.md](./일정과역할.txt) 3절이 리스크로 인지하고 있으나, 완화책이 "배치 INSERT로 단순 처리"다. 이는 **적재 속도** 대책이지 **서브시스템이 하나 늘어난 문제**의 대책이 아니다.

**핵심**: [일정과역할.md](./일정과역할.txt) 1.5절의 차별화 포인트 6개 중 **5개가 코어(쿠폰 동시성·정합성)에 있고 멤버십에는 1개뿐인데, 멤버십이 Phase 1 공수의 상당 부분을 점유한다.** 일정이 밀리면 차별화가 없는 쪽에 시간을 다 쓴 상태가 된다.

### 선택지

**A안 — 배치 산정만 잘라내기 (권장)**

| 유지 (창의력 + 기술 어필 그대로) | 제거 |
|---|---|
| 4단계 등급제 (이등병~병장) | `orders` 테이블 + 약 1,000만 건 더미 |
| 계급별 차등 할인율 (10/30/50%) | `MembershipTierBatchJob` |
| `min_membership_tier` eligibility | `membership_tier_log` |
| **락 획득 이전 eligibility 체크** ← 기술 어필의 본체 | 검증 쿼리 (e) |
| 발급 시점 계급/할인율 스냅샷 불변 | 월간 배치 스케줄링 |

등급은 더미데이터 생성 시 목표 분포대로 직접 부여한다. [05_시스템설계.md](./05_시스템설계.txt) 2.1절이 이를 "로직 이원화 방지"를 이유로 배치 계산으로 바꿨는데, **좋은 설계 본능이지만 시간이 한정된 경쟁에서 순수성을 위해 서브시스템 하나를 짓는 트레이드오프**다.

부수 효과: 계급이 정적 값이 되면 **위 0절 #3(false positive)과 검증쿼리 (e)의 결정론성 문제가 동시에 소멸한다.** 지금 이 두 이슈는 "계급이 변동값"이라는 전제에서만 발생한다.

**B안 — 유지하되 orders 볼륨만 축소**

등급 분포를 하향 조정: 이등병 40/일병 30/상병 20/병장 10% → **70/20/8/2%**

| 등급 | 유저 수 | 유저당 주문 | 소계 |
|---|---|---|---|
| 이등병 | 70만 | 0~2 (평균 1) | 약 70만 |
| 일병 | 20만 | 3~10 (평균 6) | 약 120만 |
| 상병 | 8만 | 11~30 (평균 20) | 약 160만 |
| 병장 | 2만 | 31~45 (평균 35) | 약 70만 |
| **합계** | | | **약 420만 건** (기존 1,000만 대비 **-58%**) |

배달앱 유저 대부분이 가끔 주문한다는 점에서 오히려 현실적인 분포이며, 기획 근거로도 방어된다.

**C안 — 현행 유지**

Phase 1 일정 리스크를 감수. 선택 시 **Phase 1 완료 기준일을 명시하고, 그 시점에 미달이면 A안으로 자동 폴백**하는 트리거를 미리 합의해 둘 것.

### 판단 근거

심사위원은 `membership_tier` 값이 배치 계산에서 나왔는지 시드에서 나왔는지 **묻지 않는다.** 등급제의 어필 포인트는 "락 획득 이전 eligibility 체크"라는 기술적 연결이지, 산정 방식의 자동화가 아니다.

## 2. 결정 안건 B — V2.1 채택 근거의 자체 실측 재검증

### 문제

심사위원이 물을 수 있는 질문: **"성능이 평가 대상이 아니라면서, 왜 성능을 근거로 알려진 결함을 감수했나요?"**

문서를 그대로 이어붙이면 이렇게 된다.

- [09_기획서.md](./09_기획서.txt) `NFR-02`: 처리량/응답속도 자체는 평가대상 아님 — 정확성 우선 설계
- [04_아키텍처.md](./04_아키텍처.txt) 4.1절 (f) 채택 근거: Lua 21% 저하 vs 이중카운터 8% 저하
- (f)의 대가: countReq 조기소진 → C안(감수)

**스스로 "보지 않는다"고 선언한 축을 근거로 정확성 인접 결함을 받아들인 구조**라 방어가 껄끄럽다.

### 추가 검토 사항

1. **왕복 횟수**: 이중 카운터는 Redis 왕복 2회(`countReq` INCR → `count` INCR), Lua는 1회(EVAL). 왕복 2회가 1회보다 싸다는 것은 직관에 반하므로, 올리브영의 -21%는 **Lua 자체 비용이 아니라 해당 스크립트의 작업량**(SISMEMBER + GET + DECR + SADD 등)에서 나왔을 가능성이 크다. 우리 Lua가 "재고 확인 + 차감" 수준이면 그 수치는 우리 조건에 적용되지 않는다.
2. **D안(SADD 프리체크)과의 관계**: SADD(중복체크)와 INCR(재고)를 **별도 호출**로 하면 그 사이에 경쟁 상태가 존재한다. 원자적으로 묶으려면 결국 Lua다. **D안을 제대로 구현하면 (c)로 수렴한다** — [리서치요약_쿠폰동시성사례.md](./리서치요약_쿠폰동시성사례.txt) 3절 D안 검토 시 함께 고려 필요.

### 제안 — 결론 변경이 아니라 근거 강화

V2.0(Lua)을 "검토 후 대체"로 넘기지 말고, **우리 워크로드에서 직접 벤치마크**한다.

```
동일 조건(재고 10,000 / 요청 20,000 / 동일 하드웨어)에서
  - V2.0: Lua script (재고확인 + 차감, 2줄)
  - V2.1: 이중 카운터 (countReq INCR → count INCR)
측정: 처리 완료 시간, p95 latency, 초과발급 건수, countReq 조기소진 발생 건수
```

**결과별 서술 분기**:

| 실측 결과 | 최종 채택 | 발표 서술 |
|---|---|---|
| 차이 미미 (예: 5% 이내) | **(c) Lua** | "올리브영의 21%는 스크립트 복잡도에서 온 값이고, 우리 조건에서는 재현되지 않았다. 성능 이득이 없으므로 countReq 결함이 없는 쪽을 택한다" |
| 이중카운터가 유의미하게 우세 | **(f) 유지** | "인용 수치를 우리 환경에서 재현했다. 결함은 C안으로 감수하되, 그 대가로 얻는 이득을 실측으로 제시한다" |

어느 쪽이든 **9막 구조의 Act3~6은 그대로 살아있고**, countReq 발견도 버려지지 않는다. 다만 격이 올라간다 — **"업계 사례를 인용한 팀"에서 "업계 사례를 우리 조건에서 재측정한 팀"으로.**

비용은 크지 않다. V2.0 Lua는 어차피 구현 후 대체하기로 되어 있으므로, **삭제하지 않고 측정 한 번 더 돌리는 것**이 전부다.

- [ ] **팀 결정 필요**: 벤치마크 수행 여부 / 수행 시 최종 채택은 결과에 따름

## 3. 결정 안건 C — `allow_reissue_on_cancel` 확정 (권고: `false`)

[리서치요약_쿠폰동시성사례.md](./리서치요약_쿠폰동시성사례.txt) 6절에서 "최우선" 미결로 표시된 항목.

**권고: `false` (취소 시 재고 미복구, 재고는 발급 이벤트 기준 단조감소)**

근거:
- 복구를 허용하면 "발급 총량 ≤ 재고" 불변식이 깨져 검증 쿼리 (a)(c)를 전부 재설계해야 한다.
- Redis 카운터 복구 타이밍과 DB 상태전이 사이에 **새로운 경쟁 상태**가 생긴다 — 정합성 검증의 심장부에 복잡도를 추가하는 선택.
- **과제 요구사항에 없다.**

PPT에는 **명시적 비목표**로 한 줄 넣을 것. "안 한 것"이 아니라 "판단해서 안 한 것"으로 읽힌다.

> 예시 문구: "취소분 재고 복구는 지원하지 않는다. 재고 불변식을 단조감소로 유지해 정합성 검증을 단순하게 만드는 편이, 요구사항에 없는 유연성보다 이 프로젝트의 목표에 부합한다고 판단했다."

- [x] **팀 결정 완료**: 권고안(`false`) 수용

**추가 결정 (2026-08-13, 팀 회의)**: 위 `allow_reissue_on_cancel=false`는 **재고 카운터(remaining_stock) 복구 여부**에만 적용되는 원칙이고, "취소된 쿠폰을 발급받은 본인이 다시 쓸 수 있는가"는 별개 축이다. 이 별개 축에 대해 팀은 **본인 재사용 허용**으로 결정했다(주문취소/환불 시 `USED→ISSUED` 전이로 복귀 — 04_아키텍처.md 3절 / 02_기능명세서_개정본.md FR-CPS-002·004 반영). 재고 카운터는 이 결정과 무관하게 여전히 미복구(단조감소) 원칙을 유지한다 — 새 발급이 아니라 기존 row 상태만 되돌리는 것이라 "발급 총량 ≤ 재고" 불변식((a)(c) 검증)에 영향 없음.
