## 1. 단계별 로드맵 (Phased Roadmap)

각 단계는 독립적으로 데모 가능해야 한다.

### Phase 1 — MVP (핵심 기능 + 최소 동시성 제어)
- [ ] 도메인 모델/스키마 확정, unique constraint 적용 (`Orders`/`MembershipTierLog` 포함, [04_아키텍처.md](./04_아키텍처.txt) 1~2절)
- [ ] 캠페인/쿠폰 CRUD(관리자용, 간단히), 발급 API(동기, **전략 (a) 비관적 락**)
- [ ] 멤버십 등급(4단계) 필드 + 회원 전용 쿠폰 eligibility 체크 ([04_아키텍처.md](./04_아키텍처.txt) 6절, [09_기획서.md](./09_기획서.txt) 6절) — 락 획득 이전 단계라 동시성 전략에 영향 없음
- [ ] `MembershipTierBatchJob` 구현(계급 산정 로직) — 더미데이터 시드에도 그대로 재사용 ([04_아키텍처.md](./04_아키텍처.txt) 6.2절)
- [ ] 상태전이 API(사용/취소/만료) + 상태 머신 검증
- [ ] 100만 User + orders 더미데이터 적재 → `MembershipTierBatchJob` 1회 실행으로 등급 산정, 300만 발급이력(정상 케이스 위주) 적재 ([05_시스템설계.md](./05_시스템설계.txt) 2절)
- [ ] 정합성 검증 SQL 쿼리 5종 작성 및 수동 실행 확인 ([05_시스템설계.md](./05_시스템설계.txt) 1절)
- [ ] 이벤트 페이지(쿠폰 수령) + 결제 페이지(쿠폰 적용) 프론트 기능 구현, 나머지 화면은 정적 mockup ([09_기획서.md](./09_기획서.txt) 5절)
- **데모**: 소규모 동시요청(예: 100 vs 50 재고)으로 정확성 시연, 등급 미달 유저 발급 거부 시연

### Phase 2 — Core (Idempotency + 검증 자동화)
- [ ] Idempotency key 전 구간 적용(발급 + 상태전이)
- [ ] `spring-retry` 낙관적 락 재시도 적용(상태전이)
- [ ] PII 마스킹(로그 컨버터 + 응답 시리얼라이저) 적용
- [ ] Mock 알림 발송 연동
- [ ] 오염 데이터 유형별(초과발급/카운터불일치/상태역행/등급위반) 삽입 → 검증 배치가 건수·위치까지 탐지하는지 테스트. idempotency는 uk_idempotency_key 제약으로 DB INSERT 삽입 방식이 안 통해 별도 통합테스트로 검증. 중복발급도 uk_campaign_user 제약으로 동일한 이유로 목록에서 제외(2026-08-14)
- [ ] 결정론성 자동 검증 스크립트: 동일 데이터 2회 실행 → 결과 해시/diff 자동 비교
- **데모**: 동일 요청 100회 동시 재전송해도 상태 1회만 변경됨을 시연

### Phase 3 — Edge cases / Hardening (대규모 동시성 + Redis 게이트)
- [ ] **V2.0 — 전략 (c) Redis Lua script** 게이트키퍼 도입, DB 비관적 락과 비교 벤치 → 오버헤드/반례 확인 후 **V2.1 — 전략 (f) Redis 이중 카운터**로 교체(최종 채택, [04_아키텍처.md](./04_아키텍처.txt) 4.1절)
- [ ] 10,000 vs 20,000 동시요청(테스트 유저 20,000명 중복없음 / ramp-up 60초 — 멘토 확정 공식 조건) k6 부하테스트 시나리오 완성 및 반복 실행(5회+)
- [ ] Redis-DB 불일치 보상 로직(재고 롤백) 구현 및 장애 주입 테스트(Redis 재시작 등) 라이브 데모
- [ ] Spring Batch 검증 Job으로 승격, `verification_result` 테이블 적재
- [ ] **발급 현황 실시간 카운트다운 화면** — 부하테스트 중 재고가 10,000→0으로 줄어드는 걸 SSE/WebSocket으로 라이브 시각화 ([1.5절](#15-차별화-전략-동일-주제-4팀-대비-확정) 차별화 포인트 4번, 데모 임팩트 대비 비용 낮아 우선순위 승격)
- **데모**: 20,000 동시요청 → 정확히 10,000건 발급, 검증 배치가 0건 위반 리포트, Redis 장애→복구 시연, 재고 카운트다운 실시간 시연

## 1.5 차별화 전략 (동일 주제 4팀 대비, 확정)

같은 주제(동시성·정합성)로 4팀이 경쟁하는 구도라, 프론트/브랜드 룩앤필이 아니라 **"같은 문제를 얼마나 더 깊이 풀었는가"**로 차별화한다 — 배점상 기술성+수행능력이 60%, 프론트는 10%뿐이라는 전제를 그대로 따른다.

1. 오염 데이터 탐지 다양화 — 위반 유형별(초과발급/카운터불일치/상태역행/등급위반) 개별 시연 + idempotency 통합테스트 별도 시연 (Phase 2)
2. 장애 주입 + 복구 라이브 데모 — Redis 강제 종료 후 보상 로직으로 자동 복구되는 과정을 시연 (Phase 3)
3. 결정론성 자동 증명 — 해시/diff 비교 스크립트 (Phase 2/3)
4. **발급 현황 실시간 대시보드** — 재고가 10,000 → 0으로 줄어드는 걸 부하테스트 중 라이브로 시각화(Redis `stock:{id}:remaining`을 SSE/WebSocket으로 push). 로그·터미널 결과보다 심사 현장에서 임팩트가 큼, 비용 대비 효과 높음 → PRD 선택확장 "발급 현황 실시간 조회" 항목을 Phase 3~4 우선순위로 승격 검토
5. **PPT 비교 슬라이드** — "일반적인 접근(정상 케이스 데모로 종료) vs 우리 접근(장애주입/결정론성 증명/등급 eligibility까지)"을 명시적으로 대비시키는 슬라이드 1장 추가. 심사위원이 4팀을 순서대로 볼 때 차별점을 스스로 찾게 두지 않고 먼저 짚어준다.
6. 멤버십 등급제(이등병~병장)는 장식이 아니라 "락 획득 이전 eligibility 체크"라는 실제 기술 포인트로 연결되어 있음을 PPT/데모에서 명시 — 창의력(기획)과 기술성 두 배점에 동시에 어필

## 3. 리스크 및 완화 방안

| 리스크 | 영향 | 완화 |
|---|---|---|
| DB 비관적 락(전략 a)이 hot row 경합으로 부하테스트 시 타임아웃 대량 발생 | 데모 중 다수 요청이 5xx로 실패해 보임(정확성엔 문제 없으나 인상이 나쁨) | 락 대기 타임아웃(`innodb_lock_wait_timeout`) 조정 + 실패 시 "품절/재시도 안내" 도메인 에러로 매끄럽게 처리, VU 수를 단계적으로 올려 데모 |
| Redis-DB 정합성 어긋남(전략 c/d) | 검증 배치에서 위반 탐지되나 원인 추적 어려움 | 재고 확보(Redis) 성공/DB insert 실패 시 반드시 보상(Redis 재고 복구) 트랜잭션 로직 필수화, 실패 로그에 상관관계 ID 남김 |
| 300만 건 검증 쿼리가 인덱스 부재로 느려짐 | 평가대상은 아니나 데모 중 대기시간 과다 | `(campaign_id, user_id)`, `campaign_id`, `coupon_issue_id` 등 필요한 인덱스 사전 설계 및 `EXPLAIN`으로 확인 |
| 낙관적 락 재시도 폭증(thundering herd) | 상태전이 API 응답지연 | 재시도 backoff(지수 백오프) 적용, 최대 재시도 초과 시 명확한 409 응답 |
| PII 마스킹 누락 지점(신규 로그 추가 시 정규식이 못 잡는 포맷) | 개인정보 노출 요구사항 위반 | DTO 레벨 강제(엔티티 직접 응답 금지 컨벤션) + 코드리뷰 체크리스트에 "PII 필드는 마스킹 시리얼라이저 필수" 항목 추가 |
| Docker Compose 로컬 자원 부족(MySQL+Redis+Kafka 동시 구동) | 개발 환경 불안정 | Kafka는 하드닝 이후 선택 확장 단계에서만 기동, 기본은 MySQL+Redis만으로 개발 |
| orders 더미데이터가 300만 발급이력과 별개로 약 1,000만 건 안팎 추가됨([05_시스템설계.md](./05_시스템설계.txt) 2.2절) | Phase 1 일정 지연 가능 | 생성 속도는 평가대상 아니므로 배치 INSERT로 단순 처리, 계급 구간 경계값(2/10/30건)만 정확히 맞추고 나머지는 대충 채워도 무방 |
