# PRD — 대규모 트래픽 선착순 쿠폰 발급 시스템

- **프로젝트명**: 밀리버릿 (MealiVit — Meal + Delivery + it)
- **팀명**: 태진아

## 1. Overview

본 프로젝트는 한정 수량 쿠폰에 대한 대량 동시 요청 상황에서 **초과 발급 0건, 1인 1매**를 보장하는 선착순 쿠폰 발급 시스템을 Java/Spring Boot 기반으로 구축한다. 핵심은 동시성 제어의 정확성과, 발급/사용/취소/만료 전 이력에 대해 언제든 재고-이력 정합성을 스스로 검증할 수 있는 결정론적 배치/쿼리를 갖추는 것이다. 인프라는 로컬 Docker Compose(MySQL, Redis, 선택적 Kafka) 기준으로 설계하며, 100만 유저·300만 발급이력 더미데이터로 실증한다.

**도메인 시나리오**: 배민(배달의민족)류 배달앱. 매일 점심시간(11:30) 정각 배달비 무료/할인쿠폰을 선착순 발급하는 반복 이벤트. [architecture.md](./architecture.md)의 캠페인당 재고 카운터 모델을 그대로 사용.

핵심 평가 포인트: **동시성 제어 정확성(초과발급 0건)**, **정합성 설계와 자기검증 능력**. 처리 속도·도구 선택은 평가 대상이 아니다.

## 2. 전제 조건 (팀 확정 사항)

- 기술 스택: **Java + Spring Boot** (Maven/mvnw.cmd)
- DB: MySQL (가정 — 팀 회의에서 변경 가능)
- 인프라: 로컬 Docker Compose (MySQL, Redis, 선택적 Kafka) (가정 — 변경 가능)
- 동시성 제어 전략: 옵션 비교 후 팀 회의에서 확정 → [architecture.md](./architecture.md) 4절 참고
- 회원가입/로그인 미구현, 가상 회원 데이터로 대체
- 도메인 시나리오: **배민 스타일 배달앱** — 매일 점심시간 정각 오픈런 배달비 무료/할인쿠폰 (확정)
- 쿠폰 캠페인 (확정): 런치 오픈런 쿠폰(`FIXED`, 15,000원, 재고 10,000장, 선착순) / 상시 10% 할인 쿠폰(`RATE`, 재고 사실상 무제한)
- 쿠폰 사용 정책 (확정): 한 주문에 쿠폰 1개만 사용 가능, 조합/스태킹 미지원

## 3. 기능 요구사항 (Functional Requirements)

| ID | 요구사항 | 검증 방법 |
|---|---|---|
| FR-01 | 캠페인은 오픈 시각과 재고 수량(예: 10,000장)을 가진다 | 캠페인 조회 API |
| FR-02 | 사용자는 캠페인당 최대 1장의 쿠폰을 발급받을 수 있다 | DB unique constraint + 검증 쿼리 |
| FR-03 | 재고 초과 발급은 어떤 동시 요청 상황에서도 발생하지 않는다 | 부하테스트 + 검증 쿼리 |
| FR-04 | 쿠폰은 ISSUED → USED / CANCELED / EXPIRED 상태를 가지며 역행 불가 상태전이는 거부된다 | 상태전이 단위테스트 + 검증 배치 |
| FR-05 | 동일한 발급/사용/취소/만료 요청이 중복·동시에 들어와도 결과는 1회만 반영된다 (idempotency) | 동시 중복요청 통합테스트 |
| FR-06 | 회원 개인정보(이름, 전화번호, 이메일 등)는 로그 및 API 응답에서 마스킹되어야 한다 | 로그/응답 스냅샷 테스트 |
| FR-07 | 알림 발송은 외부 연동 없이 Mock으로 대체된다 | Mock 호출 로그 확인 |
| FR-08 | 300만 건 발급이력 전체에 대해 재실행 시 동일 결과를 내는 정합성 검증 쿼리/배치를 제공한다 | 동일 데이터로 2회 실행 후 diff |

## 4. 비기능 요구사항 (Non-Functional Requirements)

| ID | 요구사항 |
|---|---|
| NFR-01 | 재고 10,000 vs 동시요청 20,000 상황에서 초과발급 0건 (핵심 평가지표) |
| NFR-02 | 처리량/응답속도 자체는 평가대상 아님 — 정확성 우선 설계 |
| NFR-03 | 더미데이터 생성/적재 속도는 평가대상 아니나 개발 흐름을 막지 않을 정도로는 효율화 |
| NFR-04 | 검증 배치의 실행시간은 평가대상 아니나 결과는 결정론적이어야 함 |

## 5. 선택 확장 (Optional / Stretch)

| 확장 | 설명 |
|---|---|
| 오픈 시각 예약 | `campaign.open_at` 이전 요청 거부, 오픈 순간 Redis 재고 캐시 워밍업 |
| 발급 현황 실시간 조회 | Redis 캐시 조회 API + WebSocket/SSE 대시보드 |
| 검증 결과 리포트 자동화 | Spring Batch Job 결과를 Markdown/HTML 리포트로 자동 생성 |

모두 "선택"이며, MVP~하드닝 단계 완료 후 시간 여유에 따라 팀이 우선순위를 정한다. 상세는 [task_list.md](./task_list.md) Phase 4 참고.

## 6. 성공 기준 체크리스트 (평가 기준 직결)

- [ ] 재고 10,000 / 동시요청 20,000 상황에서 `coupon_issue` 테이블의 캠페인별 row 수가 정확히 10,000건 (초과발급 0건)
- [ ] 동일 캠페인에서 `(campaign_id, user_id)` 조합 중복이 0건 (1인 1매)
- [ ] 위 두 조건이 반복 실행(최소 5회) 시 매번 재현됨
- [ ] 발급/사용/취소/만료 각각에 대해 동일 요청을 동시에 N회 보내도 상태 변경이 정확히 1회만 반영됨 (idempotency 통합테스트 통과)
- [ ] 허용되지 않은 상태전이(예: CANCELED → USED)가 어떤 경로로도 발생하지 않음
- [ ] 검증 쿼리/배치가 300만 건 전체에 대해 위반 0건을 리포트
- [ ] 동일 데이터 기준 검증을 2회 이상 재실행해도 결과(위반 건수, 결과 해시)가 동일함 (결정론성)
- [ ] 오염 데이터(의도적 위반 샘플)를 삽입하면 검증 배치가 정확히 해당 건을 탐지함 (검증 로직 자체의 신뢰성 증명)
- [ ] 로그 및 API 응답 어디에도 마스킹되지 않은 이름/전화번호/이메일이 노출되지 않음
- [ ] 알림 발송이 외부 연동 없이 Mock으로 정상 동작하고 발급 트랜잭션과 분리되어 있음
