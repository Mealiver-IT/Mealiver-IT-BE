1. 핵심 요약 (한 줄)
================================================================

동시성 정확성(V2, DB 비관적 락)은 core 단계로 구현 완료, **다만 소규모(재고
100/요청50)만 실측됐고 20,000명 규모 공식조건 실측은 아직 없음**(2.2절 정정
참고 — 이전 버전 문서에서 "실측 완료"로 잘못 표기했던 부분). V1(고장버전
실증)·V3(Redis 게이트)·V4(Redis+DB 백스톱+장애복구)는 원래 순서상 다음
단계라 아직 안 찍힌 것뿐, 진행이 밀린 게 아님. 남은 13일 안에 이 사다리를
완성하는 게 다음 우선순위(2절 표 참고). 그 사이 안정화·반복측정 준비 작업은
계속 진행됨(상태전이 버그픽스, k6 idempotency 검증, 반복측정용 리셋
스크립트) — 사다리만 나오면 곧바로 측정에 들어갈 수 있는 상태.

2. 동시성 파트 상세 현황
================================================================

## 2.1 완료된 것 (간단히)

발급 API 5단계(idempotency → OPEN체크 → eligibility → reserve → INSERT) 중
DB 조건부 UPDATE 백스톱만 빼고 동작. 상태전이·PII마스킹·Mock알림·주문연동·
상태전이 버그픽스 2건 완료. k6는 소규모(재고100/요청50, idempotency
100동시요청)까지 실측 완료, 반복측정용 리셋 스크립트도 완성.

## 2.2 V1~V4 버전 사다리 현황 (핵심)

| 버전 | 기술 | 증명하려는 것 | 상태 |
|---|---|---|---|
| V1 | 제어 없음 | 초과발급이 실제로 난다는 것(문제 실증) | 미착수 |
| V2 | DB 비관적 락 (`SELECT ... FOR UPDATE`) | 정확성은 확보되나 hot row 경합으로 느림 | **정확성 확보, 소규모 실측만 완료(아래 정정 참고)** |
| V3a | Redis Lua script | 빠르지만 Redis 장애 시 총량 방어선 소실 | 미착수 |
| V3b | Redis 이중카운터 (최종 채택 후보) | 위와 동일 + countReq 조기소진 이슈 | 미착수 |
| V4 | Redis 게이트 + DB 조건부 UPDATE 백스톱 + 워밍업 | 장애 주입에도 초과발급 0건 유지 | 미착수 (백스톱 쿼리는 죽은 코드로 이미 존재) |

부가 사실: Redis 의존성 자체가 프로젝트에 없음(pom.xml에 starter 없음, `.lua`
파일 없음). `/bench/{strategy}` 라우팅도 없음. 콜드오픈 라이브 데모(발표전략
2절)는 V3/V4가 나와야 가능.

**[정정, 재조사로 발견] 20,000명 규모 실측이 실제로는 없음.** 멘토 확정
공식조건(20,000VU/ramp-up 60초)에 맞춘 `coupon_race.js`가 한 번 작성됐었지만
(git 커밋 `f02607d`), "Phase 1 폴더 정리" 커밋(`e9d867b`, 8/14)에서 삭제됨.
phase1/phase2 README 둘 다 "대규모 동시요청은 `K6/phase3/`에 있다"고 적어
두었지만 그 폴더 자체가 저장소에 없음. 지금까지 실행 완료된 건 소규모
리허설(재고100/요청50, 8/12, 50/50 성공)과 idempotency 100동시요청뿐 —
20,000명 규모는 스크립트조차 없는 상태. 로컬 머신에서 20,000개 동시 커넥션을
하나의 서버로 열면 ephemeral port 고갈 등 TCP 소켓 한계에 부딪혀 신뢰
가능한 결과가 안 나올 수 있음(팀 내 공유된 내용, 커밋 기록엔 원인이 안 남아
있어 확인 필요) — Phase3 폴더를 다시 만들 때 로컬 실행이 아니라 별도
부하생성 환경(k6 cloud, 전용 호스트 등)을 쓰는 방안도 같이 검토해야 함.


================================================================
3. Kafka — 아직 결정 안 함, 멘토에게 먼저 물어볼 것
================================================================

경쟁팀이 마지막 단계에 Kafka를 쓰는 이유는 보통 "Redis 판정 → Kafka 발행 →
Consumer가 비동기로 DB INSERT" 구조로 **DB 쓰기 폭주를 흡수**하기 위함.
우리는 아직 채택/기각을 확정하지 않았고, 멘토링에서 물어볼 첫 번째 질문으로
쓸 예정이다(5절 티어1 참고). 아래는 그 전에 미리 정리해둔 장단점 — 질문을
빈손으로 던지지 않고 우리 판단 근거를 먼저 제시한 뒤 의견을 구하기 위함.

**우리 규모(재고 1만 / 요청 2만)에서 Kafka가 주는 이득과 대가:**
- (이득) Redis 판정과 DB 쓰기를 분리해 DB 쓰기 폭주를 흡수, 처리량은 크게 늘어남
- (대가) Redis 당첨과 DB 반영 사이에 컨슈머 랙 윈도우 발생 → 우리 과제 핵심
  평가축인 "즉시 정합성 검증"과 상충 여지 (300만 건 결정론적 검증 스토리도
  컨슈머 타이밍에 따라 흔들릴 수 있음)
- (대가) at-least-once 전달 → 컨슈머 멱등 처리 별도 설계 필요, 중복/순서 이슈
- (대가) 파티션/컨슈머그룹/DLQ/오프셋 전략까지 남은 기간 안에 감당해야 함
- (참고) MySQL 조건부 UPDATE + unique 제약만으로 이 규모는 수천 TPS까지 방어
  가능하다는 게 우리 쪽 예비 판단 — 이 판단 자체가 맞는지도 질문 대상


================================================================
4. 정합성 심화 — 설계 근거, 빈틈, 그리고 우리가 직접 확인한 것
================================================================

이 절의 목적은 질문 리스트를 채우는 게 아니라, 우리가 "정합성"을 어떤
수준까지 파고들었는지 팀 전체가 같은 그림을 갖는 것이다. 심사위원이 물어봐도
우리가 물어봐도 상관없다 — 어느 쪽이든 아래 내용을 알고 있어야 답이 나온다.
각 항목 끝에 성격을 표시했다: [이해] 우리가 그냥 알아야 하는 것 / [질문 후보]
멘토에게 물어볼 만한 것 / [액션] 우리가 고치거나 만들어야 하는 것.

## 4.1 이중 카운터의 원자성 빈틈 — countReq 드리프트

흐름은 `INCR countReq(1차 저비용 필터) → 검증 → DB INSERT → INCR count(2차
확정)`. 이 사이 어디서든 실패하면(1인1매 위반, idempotency 충돌, 서버 크래시)
`countReq`만 소모되고 `count`는 안 늘어난 채로 남는다.

수학적으로는 이미 검증됨(리서치요약 3절): `count`는 실패 시 자체 롤백하므로
총 발급량이 `total_stock`을 절대 못 넘는다 — 즉 **초과발급 문제가 아니라
"재고는 남았는데 조기 품절 표시되는" UX/공정성 문제**다.

재동기화는 지금 아예 안 하기로 결정된 상태다(C안 "감수" 채택) — 메인
부하테스트(20,000명 서로 다른 유저)에서는 애초에 이 케이스가 발현 안 되고,
채점기준("초과발급 0건")도 이 문제를 안 본다. D안(SADD 프리체크)은 Phase4
선택 확장으로 남겨뒀지만 완전 동시 더블클릭까지 막지는 못한다(최종 방어선은
DB unique 제약).
[질문 후보] "이 드리프트를 얼마나/어떤 트리거로 재동기화해야 적절한가"보다
정확한 질문은 "감수하기로 한 우리 판단(C안) 자체가 실무 기준에서 타당한가".

## 4.2 왜 Lua가 아니라 이중카운터인가 — 왕복 횟수의 역설

올리브영 실측(Lua -21% vs 이중카운터 -8%)을 근거로 이중카운터를 채택했는데,
Lua는 왕복 1회, 이중카운터는 왕복 2회라 직관적으로는 이중카운터가 더 느려야
한다. 우리 가설(03_버전사다리 4절에 이미 문서화): 올리브영의 -21%는 Lua
자체의 원가가 아니라 그 회사 스크립트의 작업량(SISMEMBER+GET+DECR+SADD 등)
에서 나온 수치일 수 있다. 우리 Lua는 "재고확인+차감" 정도로 단순해서 그
수치가 재현 안 될 수도 있다는 뜻 — 그래서 인용 수치를 그대로 믿지 않고
V3a/V3b를 둘 다 구현해 우리 워크로드로 A/B 실측하기로 했다(아직 미착수).
[질문 후보] 이미 "검토 중"이라고 스스로 인정한 지점이라 멘토 의견을 구하기
좋은 재료 — 실무에서는 이런 벤치마크 이식성을 어떤 기준으로 판단하는지.

## 4.3 DB 백스톱의 실제 작동 빈도 — 측정 수단이 없음

Redis 게이트를 통과한 요청만 조건부 UPDATE에 도달하므로, 평소엔 사실상
항상 성공하는 no-op에 가깝다. Redis가 상태를 잃었을 때만 실제로 걸러낸다.
문제는 "게이트는 통과했는데 백스톱에서 걸리는 케이스가 실제로 몇 건인지"를
잴 지표가 지금 설계엔 없다는 것 — `decreaseStockIfAvailable()`이 0 rows를
반환한 횟수를 세는 카운터조차 없다.
[액션] V4를 만들 때 이 카운터를 같이 넣어야 한다. 그래야 장애주입 라이브
데모에서 "2차 방어선이 실제로 작동했다"를 숫자로 보여줄 수 있다 — 지금은
이걸 증명할 데이터가 없다.

## 4.4 멱등성 이중 방어선 — 코드로 확인하다가 실제 버그 후보 발견

두 메커니즘은 경쟁이 아니라 순차 역할분담이다: (1) `request_id`로
`CouponStateLog` 조회 → 이미 처리된 요청이면 즉시 반환(멱등 fast-path),
(2) 다른 요청이 같은 row를 경합하면 `@Version` 낙관적 락이 걸리고
`@Retryable(maxAttempts=3, backoff=...)`로 재시도(`CouponIssueService.java`).

그런데 실제 코드(`GlobalExceptionHandler.java:59-65`)를 확인해보니
`OptimisticLockingFailureException` 핸들러가 딱 하나뿐이고
`CAMPAIGN_STATE_CONFLICT`("다른 요청이 먼저 **캠페인** 상태를 변경했습니다")
로 매핑돼 있다. 이 핸들러는 관리자용 캠페인 상태변경 API를 위해 만든
것인데, `@RestControllerAdvice`라 전역으로 걸린다 — 쿠폰 상태전이
(`markUsed`/`markCanceled`)의 재시도 3회가 다 실패해도 같은 예외 타입이라
이 핸들러를 그대로 타게 된다. 결과: 쿠폰 충돌인데 클라이언트는 "캠페인"
에러 메시지를 받는다.
[액션] 질문이 아니라 실제로 고쳐야 할 버그 후보. 쿠폰 상태전이 전용
에러코드(`COUPON_STATE_CONFLICT` 등)로 분리하거나, 예외 타입 자체를
구분해야 한다.

## 4.5 idempotency_key 보관정책 — 지금 규모에선 실질 문제 아님

`idempotency_key`는 UNIQUE 인덱스로 영구 보관, 300만 건 규모. 300만 건짜리
B-tree 유니크 인덱스는 성능상 실질적 문제가 되는 규모가 아니다(파티셔닝/
아카이빙은 보통 수천만~수억 건대에서 고려 대상) — 그래서 별도 TTL/아카이빙
설계는 안 하기로 한 것(명시적 비목표에 가까움, 발표전략 §3의 다른 비목표
항목들과 같은 성격).
[질문 후보] 우리 설계를 바꾸는 질문은 아니고, 실무에서 훨씬 큰 규모라면
어떻게 관리하는지 지식 습득 차원에서 물어볼 수는 있음 — 우선순위 낮음.

## 4.6 검증 배치의 운영 부하 — 언제 돌릴 것인가

300만 건 풀스캔인 검증 SQL/배치를 상시 서비스라면 언제 돌릴지(off-peak
스케줄링 등)는 아직 논의 안 됐다. `ConsistencyVerificationJob` 자체도
미구현이라(6.1절) 지금 당장의 문제는 아니지만, 배치로 승격시킬 때 같이
결정해야 하는 지점이다.
[질문 후보] 실시간 서비스에서 이런 정합성 검증 배치를 언제/어떻게 돌리는
게 적절한지 — 실무 스케줄링 기준을 물어볼 만함.

## 4.7 USED→ISSUED 복귀와 감사추적 — 이미 설계에 반영돼 있음

우려 지점: 쿠폰을 여러 번 재사용(ISSUED↔USED 여러 사이클)하면 감사추적이
꼬이지 않는가. 확인 결과 이미 검증쿼리 `c3_broken_chain.sql`(체인 끊김
검증)이 정확히 이 문제를 잡도록 설계돼 있다 — 매 전이가 `coupon_state_log`에
기록되므로(로그N.to_status == 로그N+1.from_status) 사이클이 여러 번이어도
체인 연속성 검증으로 커버된다.
[이해] 설계는 이미 있음, 남은 건 4.6과 동일하게 이 검증을 지속적으로 자동
재실행하는 배치뿐 — 새로운 문제가 아니라 기존 미착수 항목(6.1절)과 같은 것.

5. 멘토링 질문 리스트
================================================================

우선순위 2단계로 정리 — 시간 없으면 티어1만, 남으면 티어2 추가.
Redis 장애주입 라이브 데모 여부는 멘토에게 안 묻기로 함 — 상황 따라 팀이
직접 결정.

## 티어 1 — 반드시 물어볼 것, 이 순서로
1. **Kafka를 쓸지 말지 자체를 먼저 묻는다.** 저희가 미리 정리해둔 장단점은
   3절 참고(이득: DB 쓰기 폭주 흡수 / 대가: 컨슈머 랙 윈도우가 "즉시 정합성
   검증"과 상충 여지, 멱등 처리·파티션/DLQ 설계 부담). 아직 채택/기각을
   확정하지 않은 상태라 결론이 아니라 판단 재료로 가져간다.
2. V1(고장버전)~V4(Redis+백스톱) 사다리를 남은 13일 안에 전부 완성하는 것과,
   V2(정확성 확보, 소규모 실측만 완료)에 Redis 게이트(V4)만 추가해서 시간을 아끼는 것
   중 어느 쪽이 평가·데모 임팩트 측면에서 더 나을지 의견을 듣고 싶습니다.
   (V1 자체는 배점 평가 대상이 아니라 "우리가 만든 증거"용인데, 이 증거의
   우선순위를 어느 정도로 둬야 할지 판단이 서지 않습니다.)
   → 이 답에 따라 남은 기간 목표가 정해지므로 Kafka 다음으로 묻는다.

## 티어 2 — 시간 남으면
3. 300만 건 검증의 "결정론성"(동일 데이터 재실행 시 동일 결과) 증명이
   해시/diff 비교 수준이면 충분히 설득력 있다고 보시는지, 더 엄밀한 방법이
   필요한지 궁금합니다.
   → 검증배치 팀 작업량을 좌우하는 실질적 질문.
4. 심사위원이 직접 부하테스트를 재현 실행할 수 있다고 안내받았는데, 저희
   DB가 Tailscale 경유 원격 호스트라 심사 현장 네트워크에서 접근 가능할지가
   불확실합니다.
   → 이건 멘토가 우리 네트워크 구성을 모르니 답을 못 줄 가능성이 큼. 멘토링
   전까지 이호성님이 다른 네트워크(핫스팟 등)에서 접속 테스트를 먼저 해보고,
   그래도 막히면 "심사 현장 네트워크 정책 관련 확인 방법"만 짧게 묻는 걸로
   다운그레이드.

## 티어 3 — 선택, 심화 (4절에서 뽑은 후보, 시간이 아주 많이 남을 때만)
5. Lua(왕복 1회)보다 이중카운터(왕복 2회)가 더 빠르다는 올리브영 수치를
   그대로 믿지 않고 우리 워크로드로 직접 A/B 재측정하기로 했는데, 실무에서는
   이런 벤치마크 이식성을 어떤 기준으로 판단하는지 궁금합니다(4.2절).
6. countReq 조기소진 드리프트를 "감수"하기로 한 판단(4.1절) 자체가 실무
   기준에서 타당한지, 재동기화 없이 두는 게 맞는지 의견을 구하고 싶습니다.

## 6.1 데이터/검증배치 상세 (코드 직접 확인)

**완료된 것**
- 더미데이터 시더 5개 존재 (`api/src/main/java/.../seed/`): `UserSeedRunner`,
  `CampaignSeedRunner`, `OrderSeedRunner`, `CouponIssueSeedRunner`,
  `MembershipTierSeedRunner` — 유저/캠페인/주문/발급이력/등급배치 전 구간 커버
- 검증 SQL 5종(파일 7개) 작성 완료 (`api/src/main/resources/sql/verification/`):
  a_초과발급 / b_카운터불일치 / c1_로그누락 / c2_상태역행 / c3_체인끊김 /
  d_등급위반 / e_등급-주문불일치 — 전부 "0 rows면 정상" 형태로 설계됨
- 오염 데이터 시더 완성 (`api/src/main/resources/sql/fixtures/dirty_data_seed.sql`
  + `dirty_data_cleanup.sql`, 현재 브랜치 `feat/dirty-data-fixtures`):
  검증쿼리 7개 파일 각각을 정확히 타겟팅하는 케이스를 캠페인/유저 단위로 격리
  구성 — 케이스별 정확한 기대 건수까지 파일 주석에 명시(예: 카운터불일치 100
  rows, 등급위반 100 rows). 서로 다른 케이스가 서로의 검증쿼리에 안 걸리게
  설계된 부분이 눈에 띄는 완성도. **로컬+리모트(Tailscale 원격 DB) 양쪽 실측
  검증까지 완료** — 개발 환경에서만 도는 게 아니라 실제 데모에 쓸 DB에서도
  기대 건수대로 잡히는 것 확인됨
- 원래 있던 "중복발급 검증쿼리"는 `uk_campaign_user` DB 제약이 이미 중복
  INSERT 자체를 막기 때문에 오염 표본을 만들 수 없다고 판단해 **의도적으로
  제거** — 사유가 verification/README.md에 명문화돼 있음(설계 판단이 살아있는
  좋은 근거 자료)
- k6 고정 유저 목록(`users_20000.json`) 재생성 스크립트 + 생성 전 DB 실측
  검증 단계 추가 — 유저 목록이 실제 DB 상태와 어긋난 채로 부하테스트를
  돌리는 사고를 미리 차단
- 부하테스트 캠페인 리셋 스크립트(`reset_load_test_campaign.sql`) 완성 —
  발급이력·상태로그 삭제 + 재고 카운터 복원을 한 번에 처리(숫자만 UPDATE하면
  카운터불일치 오염이 생기므로 반드시 이 순서로). 03_버전사다리 6절 "매 실행
