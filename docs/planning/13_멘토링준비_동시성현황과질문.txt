1. 핵심 요약 (한 줄)
================================================================

동시성 정확성(V2, DB 비관적 락)은 core 단계로 구현·실측 완료 — 계획대로
기본기부터 다진 상태. V1(고장버전 실증)·V3(Redis 게이트)·V4(Redis+DB
백스톱+장애복구)는 원래 순서상 다음 단계라 아직 안 찍힌 것뿐, 진행이 밀린
게 아님. 다만 발표 전략의 핵심 자산(콜드오픈 장애주입 데모, V1~V4 대조표)이
이 세 버전을 전제로 하므로, 남은 8일 계획에서 다음 착수 순서로 넣을 것.
k6 부하테스트는 이호성님 전담 — 현재 버전(V2)에서 이미 20,000VU/ramp-up
60초 시나리오로 돌아가고 있고, 이후 버전이 나올 때마다 같은 스크립트로
재측정하면 됨.

2. 동시성 파트 상세 현황
================================================================

## 2.1 구현된 것

- `StockReservationStrategy` 인터페이스 — 설계 문서와 일치 (`reserve`/`rollback`만 존재)
- `PessimisticLockStockReservationStrategy` (03_버전사다리 기준 V2 = DB 비관적 락)
  - `SELECT ... FOR UPDATE`로 campaign row 잠금 → 재고 확인/차감
  - 코드 주석에 "Phase 1 MVP 기본 전략"으로 명시돼 있어 설계 의도와 일치
- 발급 API 흐름(`CouponIssuanceService` → `CouponIssuanceTransactionalOperations`):
  idempotency 조회 → OPEN 상태 체크 → eligibility 체크 → reserve() → INSERT
  → unique 제약 충돌 시 기존 레코드 반환(재시도 아닌 조회로 처리) — 5단계 중
  4단계는 문서와 일치, **DB 조건부 UPDATE 백스톱 단계만 빠짐** (2.2절 참고)
- k6 부하테스트(`coupon_race.js`): ramping-vus로 20,000 VU, ramp-up 60초,
  재고 20,000 기준 — **멘토 확정 조건과 이미 일치하게 짜여 있음**. 전부 201만
  나오는지 검증하는 형태로 이미 동작.
- 상태전이(사용/취소/만료), PII 마스킹, Mock 알림 발송 분리, 주문 생성/취소
  연동은 git 로그 기준 완료.

| 콜드오픈 라이브 데모(발표전략 2절) | 전제 조건(V3/V4)이 없어 현재는 불가능 |

## 2.3 기술 스택별 트레이드오프 (04_아키텍처 4절 요약 + 구현 현황 매핑)

| 전략 | 정합성 | 처리량 | 복잡도 | 인프라 | 실패 모드 | 구현 상태 |
|---|---|---|---|---|---|---|
| (a) DB 비관적 락 | 강함 | 낮음(hot row 경합) | 낮음 | MySQL만 | 락 타임아웃, 커넥션풀 고갈 | **완료·실측 완료** |
| (b) DB 낙관적 락+재시도 | 강함 | 중간 | 중간 | MySQL만 | 재시도 폭증 | 상태전이 API에는 적용(발급엔 미적용) |
| (c) Redis Lua | 강함(단일스레드 원자성) | 높음 | 중간 | Redis 필수 | Redis 장애 시 전체 중단 | 미착수 |
| (f) Redis 이중카운터(최종 채택안) | 강함, 총량 절대 못넘음 | 높음 | 중간 | Redis 필수(단일 마스터) | countReq 조기소진(UX 이슈, 초과발급 아님) | 미착수 |
| (d) Kafka 비동기 분리 | eventual consistency | 매우 높음 | 높음 | Redis+Kafka | 컨슈머 지연/중복 | **선택 확장, 기각 검토 중 — 3절 참고** |
| (e) Redisson 분산락 | 강함 | 낮음~중간 | 중간 | Redis 필수 | fencing token 부재로 정합성 리스크(Kleppmann) | 기각 확정 |

3. Kafka — 알아만 두기용 (경쟁팀 대비, 구현 안 함)
================================================================

경쟁팀이 마지막 단계에 Kafka를 쓰는 이유는 보통 "Redis 판정 → Kafka 발행 →
Consumer가 비동기로 DB INSERT" 구조로 **DB 쓰기 폭주를 흡수**하기 위함.

**우리 규모(재고 1만 / 요청 2만)에서 Kafka가 주는 이득은 거의 없고, 대가는 크다:**
- Redis 당첨과 DB 반영 사이에 컨슈머 랙 윈도우 발생 → 우리 과제 핵심 평가축인
  "즉시 정합성 검증"과 정면 충돌
  (300만 건 결정론적 검증 스토리도 컨슈머 타이밍에 따라 흔들림)
- at-least-once 전달 → 컨슈머 멱등 처리 별도 설계 필요, 중복/순서 이슈
- 파티션/컨슈머그룹/DLQ/오프셋 전략까지 2주 안에 감당하기엔 과함
- MySQL 조건부 UPDATE + unique 제약만으로 이 규모는 수천 TPS까지 방어 가능 —
  Kafka는 보통 DB 쓰기 자체가 병목인 훨씬 큰 규모에서 가치가 생김

**멘토가 "왜 Kafka 안 썼냐" 물으면 답변 초안:**
"Redis 판정과 DB 반영 사이에 컨슈머 랙 윈도우가 생기는데, 이게 저희 과제의
핵심 평가 포인트인 '즉시 정합성 검증'과 상충한다고 판단해 기각했습니다.
이 규모(1만 재고)에서는 MySQL 조건부 UPDATE만으로 충분히 방어되고,
트래픽이 한 자릿수 이상 커지거나 후속 시스템(알림·정산 등)이 늘어나면
그때 재검토할 지점이라고 봅니다."

4. 멘토링 질문 리스트
================================================================

우선순위 3단계로 정리 — 시간 없으면 티어1만, 남으면 순서대로 추가.
(기존 "동시성 우선순위 1번"과 "일정 6번"은 사실상 같은 질문이라 하나로 합침)

## 티어 1 — 반드시 물어볼 것 (남은 8일 배분이 여기 달림)
1. [구 A-1 + D-6 통합] V1(고장버전)~V4(Redis+백스톱) 사다리를 8일 안에 전부
   완성하는 것과, V2(정확성 확보·실측 완료)에 Redis 게이트(V4)만 추가해서
   시간을 아끼는 것 중 어느 쪽이 평가·데모 임팩트 측면에서 더 나을지 의견을
   듣고 싶습니다. (V1 자체는 배점 평가 대상이 아니라 "우리가 만든 증거"용인데,
   이 증거의 우선순위를 어느 정도로 둬야 할지 판단이 서지 않습니다.)
   → 이 답에 따라 이번 주 목표가 정해지므로 제일 먼저 묻는다.
2. [구 A-2] Redis 장애 주입 라이브 데모를 심사 현장에서 실제로 보여드리는 게
   좋을지, 리스크 대비 처음부터 녹화본 위주로 준비하는 게 나을지 조언
   부탁드립니다.
   → 질문 1의 답이 "V4까지 간다"일 때만 의미 있는 후속 질문이라 순서상 다음.

## 티어 2 — 시간 남으면
3. [구 B-4] 300만 건 검증의 "결정론성"(동일 데이터 재실행 시 동일 결과) 증명이
   해시/diff 비교 수준이면 충분히 설득력 있다고 보시는지, 더 엄밀한 방법이
   필요한지 궁금합니다.
   → 검증배치 팀 작업량을 좌우하는 실질적 질문이라 티어2 중에서는 최우선.
4. [구 A-3] 저희가 Kafka를 기각한 이유(3절)에 대해 심사 관점에서 이 판단이
   타당한지 확인받고 싶습니다.
   → 이미 자체 결론이 선 사안이라 답을 몰라도 진행에 지장 없음. 발표 Q&A
   방어 강화용 확인 질문.

## 티어 3 — 멘토링 전에 자체 해결 시도, 그래도 안 풀리면만 질문
5. [구 C-5] 심사위원이 직접 부하테스트를 재현 실행할 수 있다고 안내받았는데,
   저희 DB가 Tailscale 경유 원격 호스트라 심사 현장 네트워크에서 접근
   가능할지가 불확실합니다.
   → 이건 멘토가 우리 네트워크 구성을 모르니 답을 못 줄 가능성이 큼. 월요일까지
   이호성님이 다른 네트워크(핫스팟 등)에서 접속 테스트를 먼저 해보고, 그래도
   막히면 "심사 현장 네트워크 정책 관련 확인 방법"만 짧게 묻는 걸로 다운그레이드.

## 5.1 데이터/검증배치 상세 (코드 직접 확인)

**완료된 것**
- 더미데이터 시더 5개 존재 (`api/src/main/java/.../seed/`): `UserSeedRunner`,
  `CampaignSeedRunner`, `OrderSeedRunner`, `CouponIssueSeedRunner`,
  `MembershipTierSeedRunner` — 유저/캠페인/주문/발급이력/등급배치 전 구간 커버
- 검증 SQL 5종(파일 7개) 작성 완료 (`api/src/main/resources/sql/verification/`):
  a_초과발급 / b_카운터불일치 / c1_로그누락 / c2_상태역행 / c3_체인끊김 /
  d_등급위반 / e_등급-주문불일치 — 전부 "0 rows면 정상" 형태로 설계됨
- 오염 데이터 시더 완성 (`api/src/main/resources/sql/fixtures/dirty_data_seed.sql`
  + `dirty_data_cleanup.sql`, 현재 브랜치 `feat/dirty-data-fixtures`):
  검증쿼리 7개 파일 각각을 정확히 타겟팅하는 케이스를 캠페인/유저 단위로 격리
  구성 — 케이스별 정확한 기대 건수까지 파일 주석에 명시(예: 카운터불일치 100
  rows, 등급위반 100 rows). 서로 다른 케이스가 서로의 검증쿼리에 안 걸리게
  설계된 부분이 눈에 띄는 완성도.
- 원래 있던 "중복발급 검증쿼리"는 `uk_campaign_user` DB 제약이 이미 중복
  INSERT 자체를 막기 때문에 오염 표본을 만들 수 없다고 판단해 **의도적으로
  제거** — 사유가 verification/README.md에 명문화돼 있음(설계 판단이 살아있는
  좋은 근거 자료)

**아직 없는 것**
- `ConsistencyVerificationJob` (Spring Batch) — 아직 미구현. 지금은 7개 SQL
  파일을 MySQL 클라이언트로 손으로 하나씩 실행하는 방식 (README에 명시). 300만
  건 규모에서 이걸 자동 배치로 승격하는 게 다음 단계
- 결정론성 자동 증명(동일 데이터 2회 실행 → 해시/diff 자동 비교) 스크립트 —
  아직 자동화 안 됨, 수동 확인만 가능한 상태
- 검증 결과를 `verification_result` 테이블에 적재하는 것(일정과역할 Phase 3
  항목) — 미착수

**참고**: 둘 다 "Phase 2 선택 확장" 항목으로 원래 계획에서도 다음 단계라
지금 안 된 게 늦은 게 아님. 다만 발표에서 "V1을 실제로 돌려 나온 진짜 위반
데이터를 검증 배치가 탐지"하는 서사(03_버전사다리 8절)를 쓰려면, 결국
수동 실행이 아니라 자동 배치가 있어야 라이브 데모가 매끄럽다.
