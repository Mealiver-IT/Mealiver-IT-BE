## 1. 정합성 자기검증(Self-Verification) 설계

300만 건 전체 대상, **재실행 시 동일 결과가 나오는 결정론적** 검증이 요구사항이므로, 시점(`NOW()`)에 의존하는 조건 대신 상태값 자체만으로 판정 가능한 규칙으로 설계한다.

### 1.1 검증 항목별 SQL

**(a) 캠페인별 발급 수량이 재고를 초과하지 않았는가**

```sql
SELECT c.id AS campaign_id, c.total_stock,
       COUNT(ci.id) AS issued_count
FROM campaign c
LEFT JOIN coupon_issue ci ON ci.campaign_id = c.id
GROUP BY c.id, c.total_stock
HAVING COUNT(ci.id) > c.total_stock
ORDER BY c.id;
-- 결과 0 rows 여야 함
```
> 설계 판단: 재고는 "발급 성공 이벤트" 자체를 카운트한다. **`allow_reissue_on_cancel = false`(취소분 재고 미복구, 재고는 발급 이벤트 기준 단조감소)로 확정** — 재고 복구를 허용하면 "발급 총량 ≤ 재고" 불변식이 깨져 (a)/(c) 두 검증을 모두 재설계해야 하고, Redis 카운터 복구와 DB 상태전이 사이에 새로운 경쟁 상태가 생긴다. 과제 요구사항에 없는 복잡도이므로 **명시적 비목표**로 문서화한다([01_설계보완_검토안.md](./01_설계보완_검토안.txt) 3절).

**(b) 유저당 캠페인별 중복 발급이 없는가**

```sql
SELECT campaign_id, user_id, COUNT(*) AS cnt
FROM coupon_issue
GROUP BY campaign_id, user_id
HAVING COUNT(*) > 1
ORDER BY campaign_id, user_id;
-- 결과 0 rows 여야 함 (uk_campaign_user 로 원천 불가하지만, 제약 우회 경로 유무를 이중 확인)
```

**(c) 이력 테이블과 캠페인 카운터가 일치하는가**

```sql
SELECT * FROM (
    SELECT c.id AS campaign_id,
           c.total_stock - c.remaining_stock AS counter_issued,
           COALESCE(actual.issued_count, 0) AS issued_count
    FROM campaign c
    LEFT JOIN (
        SELECT campaign_id, COUNT(*) AS issued_count
        FROM coupon_issue
        GROUP BY campaign_id
    ) actual ON actual.campaign_id = c.id
) t
WHERE t.counter_issued <> t.issued_count
ORDER BY t.campaign_id;
-- 결과 0 rows 여야 함. Redis 카운터 전략이면 stock:{campaignId}:remaining 값도 별도 스크립트로 비교
```
> ⚠️ **`LEFT JOIN` 필수**: `INNER JOIN`으로 쓰면 발급 이력이 **0건인 캠페인이 조인에서 탈락**해 검증 대상에서 통째로 빠진다. `remaining_stock`만 잘못 차감되고 이력은 0건인 오염 케이스(= Redis-DB 불일치의 대표 증상)를 못 잡으므로, 오염 데이터 탐지 시연이 여기서 실패한다.
>
> **이 쿼리는 `campaign.remaining_stock`이 실제로 갱신되는 컬럼일 때만 의미가 있다.** V2.1(Redis 이중 카운터)에서 재고 판정 권한이 Redis로 이동하면 이 컬럼이 방치되어 검증이 공허해지므로, [04_아키텍처.md](./04_아키텍처.txt) 4.2절의 **DB 조건부 UPDATE 백스톱**이 이 컬럼을 계속 갱신하는 주체가 된다(미결항목 "`remaining_stock` 실사용 여부" 해소).

**(d) 상태전이가 유효한가**

```sql
-- 일반화: 현재 상태로 이어지는 로그가 하나도 없는 레코드 전체 탐지
SELECT ci.id, ci.status
FROM coupon_issue ci
WHERE ci.status <> 'ISSUED'  -- ISSUED는 최초상태이므로 로그 없어도 정상
  AND NOT EXISTS (
      SELECT 1 FROM coupon_state_log l
      WHERE l.coupon_issue_id = ci.id AND l.to_status = ci.status
  );
-- 결과 0 rows 여야 함

-- 허용되지 않은 전이가 로그에 기록된 적 있는지 (상태머신 우회 버그 탐지)
-- 주의: from_status는 nullable이라 (from_status, to_status) NOT IN (튜플 목록)을 그대로 쓰면
-- to_status가 허용값과 우연히 일치할 때 SQL 3값 논리(NULL 비교 → UNKNOWN)로 인해 해당 row가
-- WHERE에서 조용히 빠진다. COALESCE로 NULL을 실제 status와 안 겹치는 sentinel('\0')로
-- 치환해 비교한다. ISSUED는 최초상태라 to_status로 등장하면 안 되므로 허용 목록에
-- '\0|ISSUED' 항목을 추가하지 않는다.
SELECT * FROM coupon_state_log
WHERE CONCAT(COALESCE(from_status, '\0'), '|', to_status) NOT IN (
    'ISSUED|USED', 'ISSUED|CANCELED', 'ISSUED|EXPIRED',
    'USED|CANCELED',   -- 관리자 강제회수 (사용 여부 무관)
    'USED|ISSUED'      -- 주문취소 시 본인 재사용 복귀 (2026-08-13 팀 결정, FR-CPS-002/004)
)
ORDER BY id;
-- 결과 0 rows 여야 함

-- 로그 체인이 끊기지 않는가 (직전 로그의 to_status == 다음 로그의 from_status)
-- 위 두 쿼리는 "각 로그가 개별적으로 유효한가"만 보므로,
-- ISSUED→USED 다음에 ISSUED→CANCELED 가 기록된 케이스(각각은 유효하지만 이어붙이면 모순)를 못 잡는다.
SELECT id, coupon_issue_id, from_status, to_status, prev_to_status
FROM (
    SELECT l.id, l.coupon_issue_id, l.from_status, l.to_status,
           LAG(l.to_status) OVER (PARTITION BY l.coupon_issue_id ORDER BY l.id) AS prev_to_status
    FROM coupon_state_log l
) t
WHERE (prev_to_status IS NULL     AND from_status <> 'ISSUED')  -- 첫 로그는 반드시 ISSUED에서 출발
   OR (prev_to_status IS NOT NULL AND from_status <> prev_to_status)
ORDER BY coupon_issue_id, id;
-- 결과 0 rows 여야 함. id는 AUTO_INCREMENT라 삽입 순서 = 전이 순서로 간주
```

**(e) 회원 전용 쿠폰이 등급 미달 유저에게 발급된 적이 없는가** ([09_기획서.md](./09_기획서.txt) 6.3절, [04_아키텍처.md](./04_아키텍처.txt) 6절)

```sql
SELECT ci.id, ci.user_id,
       ci.issued_membership_tier AS tier_at_issue,
       c.min_membership_tier AS required_tier
FROM coupon_issue ci
JOIN campaign c ON c.id = ci.campaign_id
WHERE c.min_membership_tier IS NOT NULL
  AND FIELD(ci.issued_membership_tier, 'PRIVATE','PFC','CORPORAL','SERGEANT')
    < FIELD(c.min_membership_tier, 'PRIVATE','PFC','CORPORAL','SERGEANT')
ORDER BY ci.id;
-- 결과 0 rows 여야 함. FIELD()로 등급 순서를 정수 인덱스처럼 비교(PRIVATE=1 < ... < SERGEANT=4)
```
> ⚠️ **`users.membership_tier`(현재 계급)와 비교하면 안 된다.** 계급은 `MembershipTierBatchJob`이 매월 재산정하는 **변동값**이므로, 발급 당시 병장이었다가 이후 상병으로 강등된 유저가 **정상 발급인데도 위반으로 잡히는 false positive**가 발생한다. 검증 결과가 배치 실행 시점에 따라 달라지므로 결정론성 규칙((f)의 `NOW()` 금지와 동일한 문제)도 함께 깨진다.
>
> 해결: `coupon_issue`에 **발급 시점 계급 스냅샷 컬럼 `issued_membership_tier`를 추가**한다([04_아키텍처.md](./04_아키텍처.txt) 1절). 이미 `discount_type`/`discount_value`를 같은 이유로 스냅샷하고 있으므로 기존 패턴의 확장이며, 컬럼 1개 추가로 끝난다.

**(f) 계급이 orders 집계와 일치하는가** ([09_기획서.md](./09_기획서.txt) 6.2절, [04_아키텍처.md](./04_아키텍처.txt) 6.2절)

```sql
-- <월시작>/<월종료>는 대상 배치 실행분의 tier_calculated_at이 속한 캘린더 월 경계로 고정(NOW() 사용 금지 — 결정론성 규칙)
SELECT * FROM (
    SELECT u.id AS user_id,
           u.membership_tier AS current_tier,
           COALESCE(computed.order_count, 0) AS order_count,
           CASE
             WHEN COALESCE(computed.order_count, 0) >= 31 THEN 'SERGEANT'
             WHEN COALESCE(computed.order_count, 0) >= 11 THEN 'CORPORAL'
             WHEN COALESCE(computed.order_count, 0) >= 3  THEN 'PFC'
             ELSE 'PRIVATE'
           END AS expected_tier
    FROM users u
    LEFT JOIN (
        SELECT user_id, COUNT(*) AS order_count
        FROM orders
        WHERE status = 'COMPLETED' AND paid_amount >= 10000
          AND completed_at >= :월시작 AND completed_at < :월종료
        GROUP BY user_id
    ) computed ON computed.user_id = u.id
) t
WHERE t.current_tier <> t.expected_tier
ORDER BY t.user_id;
-- 결과 0 rows 여야 함. 반드시 마지막 배치의 집계 윈도우([:월시작, :월종료))로 고정 조회 — "현재 시각까지의 누적"으로 계산하면 배치 이후 새로 쌓인 주문 때문에 오탐 발생
```
> ⚠️ **`LEFT JOIN` + `COALESCE(order_count, 0)` 필수**: `INNER JOIN`이면 해당 월 주문이 **0건인 유저가 조인에서 탈락**해 검증 대상에서 빠진다. 이등병(0~2건) 구간이 전체의 40%인데 그중 0건 유저는 **아예 검사되지 않으며**, `membership_tier = 'SERGEANT'`인데 주문 0건인 오염 데이터를 심어도 탐지되지 않는다. 오염 데이터 탐지 시연이 여기서 실패하므로 반드시 수정한다.

### 1.2 SQL 집계 vs Spring Batch — 둘 다 사용

| 구분 | 용도 | 이유 |
|---|---|---|
| **순수 SQL 집계 쿼리(위 6개)** | 개발 중 수시 실행, 부하테스트 직후 즉시 검증 | 인덱스(`campaign_id`, `(campaign_id,user_id)`, `coupon_issue_id`, `(user_id,status,completed_at)`)만 잘 걸리면 300만 건도 수 초~수십 초 내 완결. 별도 배치 인프라 없이 재현 가능. "재실행 시 동일 결과"를 가장 단순하게 증명(같은 쿼리, 같은 데이터 → 같은 결과는 SQL의 기본 속성) |
| **Spring Batch Job (`ConsistencyVerificationJob`)** | 정식 검증 리포트 생성, CI/데모 시 자동 실행, 결과를 별도 테이블/파일로 영속화 | 6가지 검증을 `Step` 단위(`stockCheckStep`, `duplicateCheckStep`, `counterSyncStep`, `stateTransitionStep`, `membershipEligibilityStep`, `tierConsistencyStep`)로 구성, `Chunk` 기반 `JdbcPagingItemReader`로 300만 건을 10,000건씩 페이징하여 읽고, `ItemProcessor`가 위반 여부 판정, `ItemWriter`가 `verification_result` 테이블에 위반 건만 적재. `BatchJobExecution` 메타테이블에 실행 이력이 자동으로 남아 감사 추적 가능. `tierConsistencyStep`은 계급 재산정을 수행하는 `MembershipTierBatchJob`([04_아키텍처.md](./04_아키텍처.txt) 6.2절)과는 별개 Job — 이쪽은 재산정 결과를 사후 검증만 한다 |

**권장**: SQL 집계 쿼리를 1차 진단 도구로, Spring Batch Job을 "정식 자동화된 검증 리포트"로 이원화. MVP는 SQL만으로 요구사항(결정론적, 300만 건 전체, 재실행 동일결과)을 충족하고, Spring Batch는 선택 확장에서 "자동화 리포트"로 격상.

위 6개 쿼리의 실행용 `.sql` 파일은 `api/src/main/resources/sql/verification/`에 있다(파일별 매핑은 그 폴더의 README 참고). 이 문서(설계)가 우선순위 원본이고, 내용이 갈리면 여기 기준으로 그 폴더를 고친다.

**결정론성 보장 규칙**:
- 검증 쿼리는 `NOW()`, `CURRENT_TIMESTAMP` 등 실행 시점 의존 조건을 쓰지 않는다.
- **시간에 따라 변하는 값(`users.membership_tier` 등)과 비교하지 않고, 발급 시점 스냅샷 컬럼과 비교한다.** `NOW()` 금지와 같은 원칙의 다른 표현 — 조건절에 시각이 없어도 **참조 대상이 변동값이면 결과는 실행 시점에 따라 달라진다**((e) 참고).
- **모든 검증 쿼리에 `ORDER BY`를 명시한다.** SQL은 `ORDER BY` 없이는 행 순서를 보장하지 않으므로, 같은 데이터에서도 실행 계획/버퍼 상태에 따라 순서가 뒤바뀌어 **결과 해시가 달라질 수 있다.** 스크립트에서 정렬하더라도 SQL 레벨에서 고정해 두는 편이 안전하다.
- **탐지 누락(false negative)을 만드는 `INNER JOIN`을 쓰지 않는다.** 위반 케이스는 대개 "있어야 할 행이 없는" 형태로 나타나는데, `INNER JOIN`은 정확히 그 행을 결과에서 제거한다((c)(f) 참고).
- 검증 스크립트는 결과셋을 정렬 후 JSON 직렬화 → SHA-256 해시하여 "이전 실행 해시와 동일한가"로 재실행 동일성을 기계적으로 확인한다.

## 2. 더미데이터 생성 계획

### 2.1 100만 User

- Java 배치 프로그램(초기 1회성 `CommandLineRunner` 또는 별도 `main`)에서 `JdbcTemplate.batchUpdate()`로 1,000~5,000건 단위 배치 INSERT.
- JPA `saveAll()`은 영속성 컨텍스트 오버헤드가 크므로 지양. `JdbcTemplate` + `rewriteBatchedStatements=true`(MySQL JDBC 드라이버 옵션) 조합 권장. 대안: CSV 사전 생성 후 `LOAD DATA INFILE`.
- PII 필드(name, phone, email)는 `net.datafaker`(Java Faker)로 랜덤 생성. 가상 데이터이므로 저장 자체는 평문 허용하되, **조회/응답/로그 경계에서만 마스킹**(3절)한다 — 이것이 이 프로젝트의 핵심 실습 포인트.
- `membership_tier`/`tier_calculated_at`은 더미데이터 생성 단계에서 직접 채우지 않는다 — 2.2절에서 `orders`를 먼저 생성한 뒤, 실제 `MembershipTierBatchJob`([04_아키텍처.md](./04_아키텍처.txt) 6.2절)을 그대로 1회 실행해 계산된 값으로 채운다(시드도 별도 랜덤 로직 없이 배치 결과 그대로 사용 — 로직 이원화 방지).

```java
List<Object[]> batchArgs = new ArrayList<>(BATCH_SIZE);
for (int i = 0; i < 1_000_000; i++) {
    batchArgs.add(new Object[]{ "user" + i, faker.name().fullName(), faker.phoneNumber(), faker.internet().emailAddress() });
    if (batchArgs.size() == BATCH_SIZE) {
        jdbcTemplate.batchUpdate(INSERT_SQL, batchArgs);
        batchArgs.clear();
    }
}
```

### 2.2 orders 더미데이터 (계급 산정용)

- 목표 계급 분포(이등병 40% / 일병 30% / 상병 20% / 병장 10%, [09_기획서.md](./09_기획서.txt) 6.2절)를 역산해 유저 그룹별로 다른 건수의 `orders`를 생성한다 — 예: 이등병 그룹은 유저당 0~2건, 일병 3~10건, 상병 11~30건, 병장 31~45건(상한은 임의) 식으로 구간 내 랜덤. 전부 `status=COMPLETED`, `paid_amount>=10000`으로 채우면 단순 계산상 유저 100만 명 기준 **약 1,000만 건 안팎**(CANCELED/REFUNDED나 10,000원 미만 건까지 섞으면 더 늘어남) — 300만 발급이력과는 별개의 물량이므로 일정에 별도 반영([일정과역할.md](./일정과역할.txt)).
- 볼륨이 크므로 2.1절과 동일하게 `JdbcTemplate.batchUpdate()` 대량 INSERT 방식을 그대로 재사용한다. "생성/적재 속도는 평가 안 함"이라 정확한 상한을 맞추기보다 구간별 목표 건수만 지키면 충분하다.
- 생성 완료 후 `MembershipTierBatchJob`을 1회 실행해 `users.membership_tier`/`tier_calculated_at`을 채우고 `membership_tier_log`에 최초 산정 이력을 남긴다.

### 2.3 300만 발급이력

- 동일한 배치 INSERT 방식. 실제 동시성 로직을 타지 않고 "이미 발급 완료된 것"으로 간주하는 이력.
- 분포 설계: 캠페인 10~20개 생성, 캠페인별 재고/발급량을 다양하게. **의도적으로 정합성이 깨진 소량 오염 데이터셋**을 별도로 삽입해(예: 특정 캠페인만 `total_stock`보다 1건 더 issued) 검증 배치가 실제로 위반을 탐지하는지 증명하는 데 사용한다.
- 대량 INSERT 시 FK/유니크 인덱스가 성능을 저해하므로, 적재 시점엔 인덱스 최소화 후 적재 완료 후 인덱스 생성(`ALTER TABLE ... ADD INDEX`) 고려 가능. 단 "생성/적재 속도는 평가 안 함"이므로 과도한 최적화는 우선순위 낮음.

## 3. PII 마스킹 구현 방안

### 3.1 로그 마스킹 — Logback `PatternLayoutEncoder` + 커스텀 `Converter`

```java
public class PiiMaskingConverter extends ClassicConverter {
    private static final Pattern PHONE = Pattern.compile("\\d{2,3}-?\\d{3,4}-?\\d{4}");
    private static final Pattern EMAIL = Pattern.compile("[\\w.-]+@[\\w.-]+");

    @Override
    public String convert(ILoggingEvent event) {
        String msg = event.getFormattedMessage();
        msg = PHONE.matcher(msg).replaceAll(m -> maskPhone(m.group()));
        msg = EMAIL.matcher(msg).replaceAll(m -> maskEmail(m.group()));
        return msg;
    }
}
```

`logback-spring.xml`에서 `%mask` 컨버전 워드로 등록. 추가로 `User`/`CouponIssue`의 `toString()`을 오버라이드하여 PII 필드가 로그에 원본으로 찍히지 않도록 한다(`name=김*수, phone=010-****-1234`).

### 3.2 응답 마스킹 — Jackson `@JsonSerialize` 커스텀 시리얼라이저

```java
public class PhoneMaskingSerializer extends JsonSerializer<String> {
    @Override
    public void serialize(String value, JsonGenerator gen, SerializerProvider sp) throws IOException {
        gen.writeString(value.replaceAll("(\\d{3})-?\\d{3,4}-?(\\d{4})", "$1-****-$2"));
    }
}

public class UserResponse {
    private String loginId;
    @JsonSerialize(using = PhoneMaskingSerializer.class)
    private String phone;
    @JsonSerialize(using = EmailMaskingSerializer.class)
    private String email;
    @JsonSerialize(using = NameMaskingSerializer.class)
    private String name;
}
```

DTO 계층에서 마스킹 시리얼라이저를 강제하여, 엔티티가 실수로 그대로 응답에 노출되는 경로를 컨트롤러 반환 타입 레벨에서 차단한다(엔티티를 직접 `@RestController`에서 반환하지 않는 코드 컨벤션 명문화).

## 5. 부하테스트 계획

### 5.1 시나리오 정의

> **[멘토 확정 / 2026-08-12] "20,000명이 동시에 요청"의 공식 측정 조건 — 전 팀 공통, 임의 변경 불가**
> - 테스트 유저: **20,000명 (중복 유저 없음)**
> - 부하 프로파일: **ramp-up 60초** (즉시 스파이크가 아니라 0 → 20,000명까지 60초에 걸쳐 점증)
> - 근거: `백엔드_종합프로젝트 주제 질문_멘토답변.pdf` 3-3) 답변. 상세 원문·다른 항목은 [12_멘토답변_확정사항.md](./12_멘토답변_확정사항.txt) 참고.
> - 기존 계획(shared-iterations, maxDuration 30s, ramp 없음)은 이 조건과 달라 5.2를 아래와 같이 수정했다.

| 항목 | 값 |
|---|---|
| 대상 캠페인 재고 | 10,000 |
| 동시 요청 유저 수 | 20,000명, **중복 없음**, **ramp-up 60초** (멘토 확정 공식 조건) — 재고초과와 1인1매를 분리 검증하기 위해 우선 유저 중복 없는 시나리오로 설계 |
| 추가 시나리오 | 동일 유저가 짧은 시간 내 N회 중복 요청(예: 5,000명이 각 4회씩 재요청) → 1인 1매 검증. 이건 멘토 확정 조건의 "본 시나리오"가 아니라 부가 검증용이므로 결과표에서 구분 표기 |
| 목표 | 성공 응답 수 == 10,000, 재고 초과 없음, DB row 수 == 10,000, 실패 응답(품절)은 명확한 4xx/도메인 에러코드로 구분 |
| 심사 대응 | 심사위원이 이 부하테스트를 직접 실행해볼 수 있다고 확정 안내받음(멘토답변 4-1) — 초기화 스크립트 원커맨드화(03_버전사다리 6절)와 README 실행 가이드를 항상 최신 상태로 유지할 것 |

### 5.2 k6 스크립트 개요

> 아래는 멘토 확정 조건(테스트 유저 20,000명 중복없음 / ramp-up 60초)을 반영한 버전이다.
> `ramping-vus`로 0→20,000 VU를 60초에 걸쳐 점증시키고, VU 번호를 유저 인덱스에 1:1로 매핑해
> 유저 중복 없이 "각 VU가 정확히 1회만 요청"하도록 만든다(요청 후 `sleep`으로 재반복 방지).

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';
import { SharedArray } from 'k6/data';

const users = new SharedArray('users', function () {
  return JSON.parse(open('./users_20000.json')); // 사전 생성된 20,000명의 user_id + idempotency_key (전원 서로 다른 유저)
});

export const options = {
  scenarios: {
    coupon_race: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '60s', target: 20000 }, // 멘토 확정: ramp-up 60초, 테스트 유저 20,000명(중복 없음)
      ],
      gracefulRampDown: '10s',
    },
  },
};

export default function () {
  const u = users[__VU - 1]; // VU 번호(1~20000) = 유저 인덱스 → 유저 중복 없이 1:1 매핑
  const res = http.post(`${__ENV.BASE_URL}/api/campaigns/1/coupons`, JSON.stringify({}), {
    headers: {
      'Content-Type': 'application/json',
      'X-User-Id': u.userId,
      'Idempotency-Key': u.idempotencyKey,
    },
  });
  check(res, {
    'status is 200 or 409': (r) => r.status === 200 || r.status === 409, // 409 = 품절/이미발급
  });
  sleep(120); // 이 VU는 1회만 요청 — 60초 ramp 구간이 끝나기 전에 같은 VU가 재요청하지 않도록 충분히 대기
}
```

### 5.3 성공 판정 지표 (테스트 종료 후 DB로 검증 — k6 자체 지표는 참고용)

```sql
SELECT COUNT(*) FROM coupon_issue WHERE campaign_id = 1;  -- 기대값: 10000
SELECT user_id, COUNT(*) FROM coupon_issue WHERE campaign_id = 1 GROUP BY user_id HAVING COUNT(*) > 1; -- 0 rows
```
Redis 전략 사용 시 `GET stock:1:remaining` → 기대값 0.

- k6의 `http_req_duration` 등 성능 지표는 참고치로만 리포트에 포함하고, "평가 대상은 정확성"임을 명시.
