# 실행계획 — 2주 / 6인 / 멘토링 2회

> 이 문서를 처음 읽는 사람(또는 AI)을 위한 배경
>
> - 프로젝트: 대규모 트래픽 선착순 쿠폰 발급 시스템 (팀명 태진아 / 프로젝트명 밀리버릿)
> - 소재: 배달앱 오전 11시 오픈 선착순 할인 쿠폰
> - 조건: 팀원 6명, 개발 기간 2주, LG 부트캠프 멘토링 2회 방문, 발표 및 시상 있음
> - 같은 주제로 4팀 경쟁
> - 관련 문서: 일정과역할(기존 Phase 로드맵) / 03_버전사다리 / 발표전략 / 01_설계보완검토안

이 문서는 일정과역할의 Phase 로드맵을 "6인 / 2주"라는 실제 조건에 맞춰 재구성한 것이다.
Phase 개념은 유지하되, 일정 관리 단위를 통합 게이트로 바꾼다.

주: 아래 D1~D14는 상대 일자 표기다. 실제 캘린더 날짜는 팀에서 매핑할 것.


================================================================
1. 전제 인식 — 6명은 여유가 아니라 조율 비용이다
================================================================

이 프로젝트의 핵심 산출물인 CouponIssueService의 동시성 로직은 200~300줄 규모다.
여기에 사람을 더 붙일 수 없다. 6명을 균등 배분하려 하면 두 가지 실패 모드가 온다.

  (1) 4명이 코어 담당 2명을 기다리며 논다
  (2) 6명이 각자 다른 것을 만들고, 마지막에 합쳤더니 붙지 않는다

따라서 2주 프로젝트에서 6명의 실제 제약은 총 공수가 아니라 통합 시점이다.
이 계획의 뼈대는 역할 분담이 아니라 통합 게이트 2개다.


================================================================
2. 게이트 원칙 (팀 전원이 사전 합의할 것)
================================================================

게이트를 통과하지 못하면 일정을 미루는 것이 아니라 범위를 잘라낸다.

  게이트 1 (D5) — 소규모 E2E 동작
      재고 50 / 요청 100 수준으로 발급 API가 끝에서 끝까지 동작해야 한다.
      동시성 전략은 V1 또는 V2 수준이어도 된다. 중요한 것은 "붙어서 돈다"는 사실.

  게이트 2 (D9) — 풀스케일 동작
      재고 10,000 / 요청 20,000이 실제로 돌고 초과발급 0건이 나와야 한다.
      더미데이터 적재와 검증 쿼리도 이 시점에 동작해야 한다.

게이트 미통과 시 잘라낼 우선순위 (미리 정해둘 것. 당일에 논의하면 늦는다):

  1순위로 자를 것 : 멤버십 배치 자동 산정 (01_설계보완검토안 안건 A의 A안)
  2순위          : 실시간 대시보드 (SSE/WebSocket)
  3순위          : 프론트 정적 mockup 화면 축소
  4순위          : V3의 A/B 비교를 한쪽만 구현
  절대 자르지 않을 것 : V1/V4 대조, 검증 쿼리, 장애 주입 데모, 발표 준비 시간

이 원칙을 지키지 않으면 D13에 "조금만 더 하면 되는데"로 전원이 밤을 새우고
발표 준비가 0인 상태로 무대에 서게 된다. 그것이 이 프로젝트의 가장 흔한 사망 원인이다.


================================================================
3. 개발 방식 — 걷는 해골(Walking Skeleton) 먼저
================================================================

2주 프로젝트의 가장 흔한 실패는 "각자 열심히 만들다가 마지막에 통합"이다.
반대로 간다.

D1~D2에 가짜여도 좋으니 끝에서 끝까지 뚫는다.
  POST /issue → DB INSERT → 응답
동시성 제어 없이, 하드코딩된 유저로, 검증 없이.

이 경로가 뚫리면 6명이 각자 자기 구간을 "교체"하는 방식으로 병렬 작업이 가능해진다.
뚫리지 않은 상태에서 병렬로 나가면 D9에 합쳤을 때 붙지 않는다.

5. 트랙 편성 — 3트랙 × 2인
================================================================

2인 1조로 두는 이유는 버스 팩터다.
2주짜리에서 한 명이 아프면 트랙 하나가 통째로 멈춘다.
페어 프로그래밍을 하지 않더라도 최소한 서로의 코드를 읽는 관계로 둘 것.

----------------------------------------------------------------
트랙 A — 발급 코어 (2인)
----------------------------------------------------------------
  담당: CouponIssueService, 상태전이 API, 상태 머신, 멱등성 처리,
        StockReservationStrategy 구현체 5종, Redis 게이트, DB 백스톱, 워밍업
  D9 이후: 장애 주입 시나리오 작성 및 리허설
  참고 문서: 04_아키텍처, 03_버전사다리

  주의: 이 트랙이 전체 병목이다.
        따라서 D5까지는 "느리지만 정확한" 상태(V2 수준)를 먼저 완성하고,
        최적화(V3, V4)는 그 다음에 한다. 처음부터 V4를 만들려 하면 D5 게이트를 놓친다.

----------------------------------------------------------------
트랙 B — 검증 / 데이터 (2인)
----------------------------------------------------------------
  담당: 더미데이터 생성기(유저 100만 / 발급이력 300만 / orders),
        정합성 검증 쿼리 6종, 오염 데이터 생성, 결정론성 해시 비교 스크립트,
        PII 마스킹, (스코프 유지 시) MembershipTierBatchJob
  D9 이후: 검증 리포트 정리, V1 산출 오염 데이터 탐지 시연 준비
  참고 문서: 05_시스템설계, 01_설계보완검토안

  주의: 검증 쿼리는 01_설계보완검토안 0절에서 수정된 버전을 사용할 것.
        기존 버전에는 INNER JOIN으로 인한 탐지 누락 등 결함이 있었다.

----------------------------------------------------------------
트랙 C — 인프라 / 부하테스트 / 프론트 (2인)
----------------------------------------------------------------
  담당: docker-compose(MySQL, Redis), k6 스크립트, 초기화 스크립트,
        실시간 재고 대시보드, 이벤트 페이지 / 결제 페이지
  D9 이후: 데모 환경 구성, 데모 녹화본 제작
  참고 문서: 05_시스템설계 5절, 09_기획서 5절

  주: 프론트는 Claude Design으로 제작하는 방침. 백엔드 부트캠프이므로 배점 10%.
      가게/메뉴 데이터는 mocking. 실제 동작이 필요한 화면은 이벤트 페이지와 결제 페이지뿐.

----------------------------------------------------------------
트랙 간 의존 해소
----------------------------------------------------------------
  트랙 B와 C는 트랙 A의 완성을 기다리지 않는다.
  D1에 확정된 API 계약에 맞춘 mock 응답으로 작업을 진행하고,
  D5 게이트에서 실제 구현으로 교체한다.

================================================================
7. 멘토링 2회 활용 전략
================================================================

대부분의 팀은 멘토링을 진척 보고로 쓴다. 이것은 낭비다.
멘토는 우리 진도를 알 필요가 없고, 우리는 외부 검증 기회가 두 번뿐이다.

----------------------------------------------------------------
1회차 (D5 전후) — 설계 판단을 검증받는 자리
----------------------------------------------------------------
준비물은 진행률이 아니라 결정 목록과 그 근거다.

가져갈 질문 예시:
  - "Redis 이중 카운터를 채택했는데 countReq 조기소진 이슈를 발견했습니다.
     감수하기로 했는데, 현업에서는 이런 걸 어떻게 처리하시나요?"
  - "Redis가 상태를 잃으면 총량 방어선이 사라진다고 판단해 DB 조건부 UPDATE를
     백스톱으로 넣었는데, 실무에서 이 구조를 쓰시나요?"
  - "취소 시 재고 복구를 지원하지 않기로 했습니다. 실제 서비스에서는 어떻게 하시나요?"

이 질문들이 강한 이유:
  (1) 팀이 스스로 문제를 발견했다는 것을 보여준다
  (2) 멘토가 실제로 겪은 장애 사례를 끌어낼 수 있다

LG 현업 멘토가 "우리는 이런 걸로 사고 났었다"고 말해주면,
그것은 다른 팀이 절대 가질 수 없는 발표 재료가 된다.

----------------------------------------------------------------
2회차 (D13 전후) — 발표 리허설을 시키는 자리
----------------------------------------------------------------
진행 상황을 설명하지 말고 실제 발표를 그대로 한다. 데모 포함.

멘토는 심사위원과 가장 비슷한 외부인이고,
우리가 놓친 "이 부분이 이해가 안 된다"를 짚어줄 수 있는 유일한 사람이다.

그리고 1회차에서 받은 지적을 어떻게 반영했는지 명시적으로 보고한다.
멘토가 심사에 관여하지 않더라도,
발표에서 "멘토링에서 지적받은 X를 반영했습니다"는 강력한 한 줄이 된다.
