# PRD — 대규모 트래픽 선착순 쿠폰 발급 시스템

- **프로젝트명**: 밀리버릿 (MealiVit — Meal + Delivery + it)
- **팀명**: 태진아

## 1. Overview

본 프로젝트는 한정 수량 쿠폰에 대한 대량 동시 요청 상황에서 **초과 발급 0건, 1인 1매**를 보장하는 선착순 쿠폰 발급 시스템을 Java/Spring Boot 기반으로 구축한다. 핵심은 동시성 제어의 정확성과, 발급/사용/취소/만료 전 이력에 대해 언제든 재고-이력 정합성을 스스로 검증할 수 있는 결정론적 배치/쿼리를 갖추는 것이다. 인프라는 로컬 Docker Compose(MySQL, Redis, 선택적 Kafka) 기준으로 설계하며, 100만 유저·300만 발급이력 더미데이터로 실증한다.

**도메인 시나리오**: 배민(배달의민족)류 배달앱. 매일 점심시간(11:30) 정각 배달비 무료/할인쿠폰을 선착순 발급하는 반복 이벤트. [02_아키텍처.md](./02_아키텍처.md)의 캠페인당 재고 카운터 모델을 그대로 사용.

핵심 평가 포인트: **동시성 제어 정확성(초과발급 0건)**, **정합성 설계와 자기검증 능력**. 처리 속도·도구 선택은 평가 대상이 아니다.

## 2. 전제 조건 (팀 확정 사항)

- 기술 스택: **Java + Spring Boot** (Maven/mvnw.cmd)
- DB: MySQL (확정)
- 인프라: 앱은 로컬 Docker Compose(MySQL, Redis, 선택적 Kafka), DB는 Tailscale로 연결되는 원격 호스트(`100.125.247.64:3306`) 사용 (확정)
- 동시성 제어 전략: MVP=(a) 비관적 락 → 하드닝=(f) Redis 이중 카운터(V2.1, 최종 채택) (확정) → [02_아키텍처.md](./02_아키텍처.md) 4절 참고
- 회원가입/로그인 미구현, 가상 회원 데이터로 대체
- 도메인 시나리오: **배민 스타일 배달앱** — 매일 점심시간 정각 오픈런 배달비 무료/할인쿠폰 (확정)
- 쿠폰 캠페인 (확정): 런치 오픈런 쿠폰(`FIXED`, 15,000원, 최소주문금액 조건부, 재고 10,000장, 선착순) / 상시 10% 할인 쿠폰(`RATE`, 재고 사실상 무제한)
- 할인 방식 (확정): (1) 최소 주문 금액 조건부 정액 할인(예: N만원 이상 구매 시 M원 할인), (2) 비율 할인(예: 20%). 배송비 무료/할인 쿠폰은 복잡도 검토 후 Phase 4에서 추가 여부 결정([06_일정과역할.md](./06_일정과역할.md) Phase 4)
- 쿠폰 사용 정책 (확정): 한 주문에 쿠폰 1개만 사용 가능, 조합/스태킹 미지원
- 멤버십 전용 쿠폰 (확정): 캠페인/쿠폰에 `최소 요구 등급`을 선택적으로 설정 가능 — 회원만 받을 수 있는 쿠폰 시나리오 지원 (6절 참고)

## 3. 기능 요구사항 (Functional Requirements)

| ID | 요구사항 | 검증 방법 |
|---|---|---|
| FR-01 | 캠페인은 오픈 시각과 재고 수량(예: 10,000장)을 가진다 | 캠페인 조회 API |
| FR-02 | 사용자는 캠페인당 최대 1장의 쿠폰을 발급받을 수 있다 | DB unique constraint + 검증 쿼리 |
| FR-03 | 재고 초과 발급은 어떤 동시 요청 상황에서도 발생하지 않는다 | 부하테스트 + 검증 쿼리 |
| FR-04 | 쿠폰은 ISSUED → USED / CANCELED / EXPIRED 상태를 가지며 역행 불가 상태전이는 거부된다 | 상태전이 단위테스트 + 검증 배치 |
| FR-05 | 동일한 발급/사용/취소/만료 요청이 중복·동시에 들어와도 결과는 1회만 반영된다 (idempotency) | 동시 중복요청 통합테스트 |
| FR-06 | 회원 개인정보(이름, 전화번호, 이메일 등)는 로그 및 API 응답에서 마스킹되어야 한다 | 로그/응답 스냅샷 테스트 |
| FR-07 | 알림 발송은 외부 연동 없이 Mock으로 대체된다 | Mock 호출 로그 확인 |
| FR-08 | 300만 건 발급이력 전체에 대해 재실행 시 동일 결과를 내는 정합성 검증 쿼리/배치를 제공한다 | 동일 데이터로 2회 실행 후 diff |
| FR-09 | 회원은 4단계 멤버십 등급(이등병/일병/상병/병장)을 가지며, 등급별로 발급받을 수 있는 전용 쿠폰이 있다 | 등급 미달 유저의 발급 요청이 거부되는지 통합테스트 |
| FR-10 | 캠페인/쿠폰에 최소 요구 등급(`min_membership_tier`, nullable)을 설정할 수 있고, 미설정 시 전 회원 대상이다 | 캠페인 생성 API + 발급 API eligibility 체크 |
| FR-11 | 이벤트 페이지(쿠폰 수령)와 결제 페이지(쿠폰 적용)는 실제 동작하며, 음식점 선택/음식 선택/장바구니/마이페이지는 흐름 시연용 정적 화면으로 제공한다 | 5절 화면 구성 참고 |

## 4. 비기능 요구사항 (Non-Functional Requirements)

| ID | 요구사항 |
|---|---|
| NFR-01 | 재고 10,000 vs 동시요청 20,000 상황에서 초과발급 0건 (핵심 평가지표) |
| NFR-02 | 처리량/응답속도 자체는 평가대상 아님 — 정확성 우선 설계 |
| NFR-03 | 더미데이터 생성/적재 속도는 평가대상 아니나 개발 흐름을 막지 않을 정도로는 효율화 |
| NFR-04 | 검증 배치의 실행시간은 평가대상 아니나 결과는 결정론적이어야 함 |

## 5. 화면 구성 (프론트, 배점 10점)

프론트는 배점 10점, 핵심 평가축(기술성+수행능력 60%)이 아니므로 **쿠폰 발급 플로우를 시연하는 데 필요한 화면만 실제로 동작**시키고 나머지는 정적 mockup으로 시간 배분한다.

| 화면 | 구현 범위 (확정) | 핵심 기능 |
|---|---|---|
| 이벤트 페이지 | **기능 동작** | 선착순 쿠폰 수령 — 이 프로젝트의 핵심 데모 |
| 결제 페이지 | **기능 동작** | 쿠폰 적용(할인 계산) 및 최종 결제 진행 — 정합성 검증과 연결되는 화면 |
| 음식점 선택 페이지 | 정적 mockup + 카테고리 필터 | 가게 목록/상세 UI, 카테고리 클릭 시 해당 카테고리 가게만 표시 (더미 JSON을 클라이언트에서 필터링, 백엔드/DB 연동 없음) |
| 음식 선택 페이지 | 정적 mockup | 메뉴 상세 UI만 |
| 장바구니 | 정적 mockup | 단일 가게 제한 UI는 표시하되, 실제 검증 로직은 선택 |
| 마이페이지 | 정적 mockup | 회원 정보/주문 내역 UI만 |

카테고리 필터는 프론트 더미데이터(`{name, category, ...}[]`)에 `category` 필드를 두고 클라이언트 사이드 `filter()`로 처리 — 백엔드 API·DB 스키마 변경 불필요.

시간이 남으면(Phase 4) 장바구니 단일 가게 제한, 음식점/메뉴 데이터 연동 순으로 기능 확장 우선순위를 둔다.

## 6. 멤버십 서비스

경쟁 서비스(배민클럽, 요기패스X, 쿠팡이츠 와우) 벤치마킹한 구독형 멤버십. 회원가입/로그인이 없는 프로젝트 전제이므로, 등급은 가입 절차가 아니라 **더미데이터 생성 시 유저별로 미리 부여**한다.

### 6.1 등급 체계 (확정)

군대 계급을 활용한 4단계: **이등병 → 일병 → 상병 → 병장**

### 6.2 등급 산정 기준 (가정 — 팀 회의에서 확정 필요)

⚠️ 이 프로젝트 도메인 모델에는 "주문(Order)" 테이블이 없다(음식 주문/장바구니/결제는 정적 mockup, [5절](#5-화면-구성-프론트-배점-10점) 참고). 따라서 등급을 "누적 주문 건수"로 산정하는 것은 실제로 구현할 수 없다 — 실제 구독 결제 플로우도 없으므로(회원가입 없음), **더미데이터 생성 시 유저별로 등급을 가중 랜덤 분포로 직접 부여**한다:

| 등급 | 비중(가정) |
|---|---|
| 이등병 | 40% (기본값) |
| 일병 | 30% |
| 상병 | 20% |
| 병장 | 10% |

### 6.3 회원 전용 쿠폰과의 연결

- `campaign`(또는 `coupon`)에 `min_membership_tier` 컬럼(nullable) 추가 — 설정 시 해당 등급 이상만 발급 가능
- 발급 로직(`CouponIssueService.issue`)에 **eligibility 체크를 재고 확보 이전 단계로 추가** — 동시성 전략 자체는 변경 없음, 검증 단계 하나만 추가되는 구조 ([02_아키텍처.md](./02_아키텍처.md) 6절 참고)
- 정합성 검증 쿼리에도 "등급 미달 유저에게 발급된 케이스가 없는가" 항목 추가 가능(선택)

## 7. 선택 확장 (Optional / Stretch)

| 확장 | 설명 |
|---|---|
| 오픈 시각 예약 | `campaign.open_at` 이전 요청 거부, 오픈 순간 Redis 재고 캐시 워밍업 |
| 발급 현황 실시간 조회 | Redis 캐시 조회 API + WebSocket/SSE 대시보드 |
| 검증 결과 리포트 자동화 | Spring Batch Job 결과를 Markdown/HTML 리포트로 자동 생성 |

모두 "선택"이며, MVP~하드닝 단계 완료 후 시간 여유에 따라 팀이 우선순위를 정한다. 상세는 [06_일정과역할.md](./06_일정과역할.md) Phase 4 참고.

## 8. 성공 기준 체크리스트 (평가 기준 직결)

- [ ] 재고 10,000 / 동시요청 20,000 상황에서 `coupon_issue` 테이블의 캠페인별 row 수가 정확히 10,000건 (초과발급 0건)
- [ ] 동일 캠페인에서 `(campaign_id, user_id)` 조합 중복이 0건 (1인 1매)
- [ ] 위 두 조건이 반복 실행(최소 5회) 시 매번 재현됨
- [ ] 발급/사용/취소/만료 각각에 대해 동일 요청을 동시에 N회 보내도 상태 변경이 정확히 1회만 반영됨 (idempotency 통합테스트 통과)
- [ ] 허용되지 않은 상태전이(예: CANCELED → USED)가 어떤 경로로도 발생하지 않음
- [ ] 검증 쿼리/배치가 300만 건 전체에 대해 위반 0건을 리포트
- [ ] 동일 데이터 기준 검증을 2회 이상 재실행해도 결과(위반 건수, 결과 해시)가 동일함 (결정론성)
- [ ] 오염 데이터(의도적 위반 샘플)를 삽입하면 검증 배치가 정확히 해당 건을 탐지함 (검증 로직 자체의 신뢰성 증명)
- [ ] 로그 및 API 응답 어디에도 마스킹되지 않은 이름/전화번호/이메일이 노출되지 않음
- [ ] 알림 발송이 외부 연동 없이 Mock으로 정상 동작하고 발급 트랜잭션과 분리되어 있음
- [ ] 등급 미달 유저의 회원 전용 쿠폰 발급 요청이 항상 거부됨 (동시요청 상황에서도)
