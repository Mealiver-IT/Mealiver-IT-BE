> - 프로젝트: 대규모 트래픽 선착순 쿠폰 발급 시스템 (팀명 태진아 / 프로젝트명 밀리버릿)

이 문서는 "동시성 제어 전략을 4단계로 구현하고 같은 조건에서 비교한다"는 실험의 설계서다.
구현 담당자는 이 문서만 읽어도 각 버전이 무엇을 쓰고 무엇을 증명해야 하는지 알 수 있어야 한다.


================================================================
1. 왜 버전을 나누는가
================================================================

기존 문서(04_아키텍처 4절, 리서치요약)는 전략 선택 근거를 외부 사례의 수치에 의존하고 있다.
예: "올리브영 실측 Lua 21% 저하 vs 이중카운터 8% 저하"

이 방식의 약점은 두 가지다.

(1) 인용된 수치는 그 회사의 워크로드에서 나온 값이라, 우리 조건에서 재현된다는 보장이 없다.
(2) 발표에서 "저희는 X를 골랐습니다. 왜냐하면 A사가 그랬기 때문입니다"는 방어력이 약하다.

버전을 전부 구현해서 동일 조건으로 측정하면, 근거가 남의 숫자에서 우리 숫자로 바뀐다.
"V2는 느립니다"라고 말하는 것과, 무대에서 V2를 돌려 타임아웃이 찍히는 걸 보여주는 것은 다르다.

추가 효과: 4팀이 모두 완성품만 보여줄 때, 고장난 버전에서 출발하는 팀은 우리뿐이다.

[2026-08-20 추가] V3a(Lua)/V3b(이중카운터)를 접은 이유도 같은 원칙의 연장이다 — 남의 사례
수치(올리브영)에 기대 미리 설계했던 "Redis가 발급을 직접 결정하는 게이트"는, 실제로 우리
워크로드에서 검증하기도 전에 다른 문제(DB 커넥션 풀 고갈)가 8/19 실측에서 먼저 터졌다.
없는 문제를 막으려고 검증 안 된 구조를 새로 얹는 대신, 실제로 관측된 문제(품절 이후 낭비
트래픽이 DB를 두드리는 것)를 정확히 겨냥한 최소 구조(캐시)로 바꿨다.


================================================================
2. 설계 원칙 — 각 버전은 서로 다른 축에서 실패(또는 극복)한다
================================================================

버전 사다리가 "느림 → 빠름 → 더 빠름"이면 얕다. 처리량은 평가 대상이 아니기 때문이다.
각 단계가 다른 종류의 문제를 드러내거나 해결하도록 설계하면, 사다리 자체가 논증이 된다.

  V1  정확성이 없다        → 초과발급 발생
  V2  정확하지만 병목이다   → 락 대기 타임아웃, 커넥션 풀 고갈 (8/19 실측으로 재현됨)
  V3  정확성은 그대로, 병목만 완화한다 → Redis가 죽어도 초과발급은 여전히 0건
                             (Redis는 발급을 결정하지 않는 캐시일 뿐이므로)
  V4  V3로도 안 풀리는 처리량 한계를 구조적으로 없앤다 → 재고를 여러 row(샤드)로 쪼개
                             InnoDB가 서로 다른 샤드를 동시에 잠그게 함(8/20 저녁 실측 근거)

[2026-08-20 오전 갱신] 원래 설계(V1~V4, 폐기된 옛 버전)는 V3에서 "빠르지만 취약함"이라는
새로운 실패 축을 일부러 만들고, V4에서 그걸 봉합하는 4단 구조였다. 새 V3는 그 실패 축이
없다 — "Redis에 정합성 판단 권한을 아예 주지 않았기 때문에, Redis가 죽어도 잃을 게
지연시간뿐이다"는 것을 별도 백스톱 없이 V3 자체로 증명한다.

[2026-08-20 오후 갱신] 다만 V3의 디메리트로 이미 적어뒀던 "사전필터는 품절 이후 트래픽만
줄일 뿐, 재고가 남아있는 동안의 순수 경합 자체는 그대로"라는 한계가 실측(coupon_mixed_5k_x4.js
목표 달성률 80%대 정체)으로 확인됐다. 이건 V3가 실패하는 게 아니라(정확성은 여전히 0건),
V2/V3 공통의 처리량 상한이 그대로 남아있다는 뜻이었다 — 그래서 새 V4(재고 샤딩)가
필요해졌다. V4도 V3와 마찬가지로 실패 축이 없다: 정확성은 V2/V3와 동일하게 DB(샤드별
원자 UPDATE)가 보장하고, Redis 사전필터도 그대로 상속받는다 — V4가 다루는 축은 순수하게
처리량(hot row 경합 분산)이다.


================================================================
3. API 버전이 아니라 전략 버전이다 (중요)
================================================================

REST 관례상 /v1, /v2 같은 URL 버전은 "요청/응답 계약이 바뀔 때" 올린다.
우리가 바꾸는 것은 내부 재고 확보 전략이고 응답 스펙은 동일하다.
따라서 URL에 v1~v4를 그대로 노출하면 "응답이 같은데 왜 API 버전이 다르냐"는 지적을 받는다.

[확정 구조]

  POST /api/v1/campaigns/{campaignId}/coupons
      → 실제 서비스 API. 전략은 설정값으로 주입. 계약은 프로젝트 내내 불변.
      (실제 구현 경로는 현재 /api/campaigns/... — 버전 프리픽스 미적용 상태.
       08_개발표준 문서-코드 불일치 항목 참고, 남은 기간엔 우선순위 낮음)

  POST /bench/{strategy}/campaigns/{campaignId}/coupons
      → 벤치마크 전용 경로. {strategy} = v1 | v2 | v3 | v4
      → k6 부하테스트는 이 경로를 호출한다.
      → bench 프로파일에서만 활성화. 운영 프로파일에서는 빈 등록 자체를 하지 않는다.

발표 슬라이드에서는 V1~V4라는 라벨을 그대로 써도 된다. 문제는 URL 구조이지 네이밍이 아니다.

[내부 구조 — 2026-08-20 갱신]

  interface StockReservationStrategy {
      boolean reserve(Long campaignId);   // 재고 확보 시도. 실패 시 false
      void rollback(Long campaignId);     // 확보 후 후속 단계 실패 시 원복
  }

V3는 별도의 StockReservationStrategy 구현체가 아니다 — 재고 확보 자체는 그 시점의
"활성 전략"(당시 V2 = PessimisticLockStockReservationStrategy)을 그대로 쓰고, 그
앞단(CouponIssuanceService)에 Redis 사전필터 체크 한 겹만 추가한 것이 V3다. 실제 구현:

  - CampaignStockCache (api/campaign/cache) — Redis 재고 스냅샷 read/write, 장애 시
    예외를 삼키고 null 반환(DB로 폴백)
  - CampaignStockSnapshotListener — 발급 성공 후 AFTER_COMMIT 시점에 스냅샷 갱신
  - CampaignStockSnapshotReconciliationJob — 15초 주기로 DB 기준 재동기화(자가치유),
    Redis 스냅샷 TTL(60초)은 이 잡이 멈췄을 때만 발동하는 최후 안전장치
  - CouponIssuanceService — reserve() 호출 전 campaignStockCache.getSnapshot() 조회,
    "확실히 품절"일 때만 DB 진입 전 즉시 거절. 캐시 미스/Redis 장애 시에는 무조건 DB로 통과
    (스냅샷 부재를 품절로 오판하지 않는다)

이 프리필터 계층은 어느 StockReservationStrategy가 활성인지와 무관하게 동작한다 —
그래서 [2026-08-20 저녁] V4(샤딩)가 활성 전략으로 교체된 뒤에도 코드 변경 없이 그대로
V4 위에 얹혔다(다만 스냅샷이 이제 campaign.remaining_stock이 아니라 여러 샤드의 합계를
읽는다 — 4절 V4 참고). 즉 "V3"는 특정 버전이 아니라 **어떤 reserve() 구현체 위에도 씌울
수 있는 사전필터 계층**이고, "V4"는 그 밑단의 reserve() 구현체가 한 번 더 바뀐 것이다.

[2026-08-20 기준 구현체 현황]
  - V1(NoControlStockReservationStrategy) — 미구현
  - V2(PessimisticLockStockReservationStrategy) — 구현됨, 현재 @Component 제거로 비활성
    (재활성화하려면 ShardedStockReservationStrategy의 @Component를 내리고 이쪽에 다시 붙이면 됨)
  - V4(ShardedStockReservationStrategy) — 구현됨, 현재 활성(@Component)

bench 라우팅에서 v3 스트래티지를 별도로 만들 필요는 없고, 그 시점 활성 전략에 사전필터
on/off 플래그를 주는 방식으로 A/B(필터 있음/없음)를 재현하면 된다.


================================================================
4. 각 버전 상세
================================================================

----------------------------------------------------------------
V1 — 제어 없음 (문제 실증용, 의도적으로 고장난 버전)
----------------------------------------------------------------

[사용 기술] 없음. 단순 조회 후 분기.

[구현 개요]
  재고를 조회하고, 0보다 크면 차감하고 INSERT 한다.
  조회와 차감 사이에 아무런 원자성 보장이 없다.

[의도된 결과]
  초과발급이 발생해야 한다. 20,000 요청에 10,000장 재고 기준으로 수천 장 초과가 목표.
  초과가 안 나오면 부하가 부족한 것이므로 VU 수를 올려 재현시킨다.

[이 버전이 증명하는 것]
  (1) 문제가 실재한다. 슬라이드가 아니라 데이터로 보여준다.
  (2) DB 유니크 제약 uk_campaign_user(campaign_id, user_id)가 있어도 총량 초과는 그대로 발생한다.
      유니크 제약은 "1인 1매"만 막고 "총량"은 막지 못한다는 사실을 실물로 증명한다.
      → 04_아키텍처 2절이 문장으로만 주장하던 내용의 실증

[주의]
  이 코드는 절대 /api/v1 경로에 노출하지 않는다. /bench/v1 전용.
  "일부러 고장난 코드가 실제 API에 열려 있다"는 것 자체가 지적 대상이 된다.

[2026-08-20 기준 상태] 미구현. 사다리 3단 중 유일하게 남은 신규 구현 항목. 비용이 가장
낮으므로(약 20줄) 가장 먼저 처리한다.

----------------------------------------------------------------
V2 — DB 비관적 락 (정확하지만 병목)
----------------------------------------------------------------

[사용 기술]
  MySQL row lock (SELECT ... FOR UPDATE)
  Spring Data JPA @Lock(LockModeType.PESSIMISTIC_WRITE)

[구현 개요]
  campaign 로우를 비관적 락으로 잠그고 재고를 확인/차감한 뒤 커밋한다.
  트랜잭션이 직렬화되므로 초과발급이 원천 차단된다.

[의도된 결과]
  초과발급 0건 (정확성 확보)
  동시에 hot row 경합 발생 — 다수 트랜잭션이 캠페인 로우 하나에 줄을 선다.
  락 대기 타임아웃(innodb_lock_wait_timeout), 커넥션 풀 고갈, 응답 지연이 관측되어야 한다.

[2026-08-20 오전 — 실측 확인됨]
  8/19 coupon_mixed_5k_x4.js(캠페인 300개, 20,000건 순간 동시요청)에서 정확히 이 실패
  양상이 재현됐다: DB 커넥션 풀 고갈 + hot row 경합으로 목표 5,000건 중 2,652건만 발급.
  이 실측이 V3 설계(사전 필터)를 채택한 직접적 근거가 됐다.

[2026-08-20 오후 — V2 자체도 한 번 더 개선됨]
  원래 V2는 campaign row를 `SELECT ... FOR UPDATE`로 잠근 뒤 애플리케이션 로직이 끝날
  때까지(트랜잭션 커밋 시점까지) 락을 들고 있었다 — 정확성은 보장되지만 hot row 경합 시
  그 시간만큼씩 요청이 순서대로 쌓여 20,000건 순간 폭주에서 응답시간 최대 175초까지
  관측됐다. "조건 확인 + 차감"을 단일 원자 UPDATE(`CampaignRepository.decreaseStockIfAvailable`,
  `UPDATE campaign SET remaining_stock = remaining_stock - 1 WHERE id=? AND remaining_stock>0`)
  로 묶어서, InnoDB의 암묵적 행 잠금이 이 UPDATE 문 실행 구간으로만 좁혀지도록 바꿨다.
  여전히 DB 비관적 락(row lock) 기반이라는 성격 자체는 그대로이므로 버전 번호는 그대로
  V2다 — "메이저(전략이 바뀜) vs 마이너(구현만 바뀜)" 구분에서 마이너 개선에 해당한다.

[측정 시 주의]
  타임아웃으로 실패한 요청이 5xx로 대량 찍히면 데모 인상이 나쁘다.
  실패는 "품절/재시도 안내" 도메인 에러코드로 매끄럽게 매핑해두되,
  리포트에는 타임아웃 발생 건수를 별도 지표로 기록한다.

[이 버전이 증명하는 것]
  정확성은 DB만으로도 확보된다. 문제는 품절 이후에도 요청이 계속 DB(hot row)까지
  도달해 자원을 갉아먹는다는 것. 따라서 "이미 끝난 게 뻔한 요청"만이라도 DB 앞에서
  걸러내야 한다는 결론이 도출된다 — 이게 V3의 동기다.

----------------------------------------------------------------
V3 — DB 선반영 + Redis 스냅샷 사전필터 (정확성 불변, 병목만 완화)
----------------------------------------------------------------

[2026-08-20 확정] 기존 V3a(Lua)/V3b(이중카운터)를 대체하는 새 설계. 핵심 차이는
"Redis가 발급을 결정하는가"이다 — 이 버전에서 Redis는 절대 발급 여부를 직접 결정하지
않는다. 최종 판단은 항상 V2와 동일하게 DB(비관적 락 + remaining_stock)가 한다.
Redis는 그 결과를 사후에 복사해두는 캐시이자, DB 진입 전 "확실히 끝난 요청"만 걸러내는
사전필터다.

[데이터 흐름]
  기존 계획(Redis 게이트):  요청 → Redis 체크(결정) → 통과 시 DB 기록
  새 설계(DB 선반영):       요청 → [Redis 스냅샷 있고 0 이하면 즉시 거절]
                                  → (그 외 전부) DB 기록(V2와 동일, 최종 결정)
                                  → 성공 시 AFTER_COMMIT으로 Redis 스냅샷 갱신

[사용 기술]
  StringRedisTemplate (spring-boot-starter-data-redis)
  Spring 트랜잭션 이벤트(@TransactionalEventListener(AFTER_COMMIT))
  Spring @Scheduled + ShedLock (재동기화 잡의 다중 인스턴스 중복 실행 방지)

[구현 개요 — 이미 구현·병합 완료(dev, 2026-08-19)]
  1) CouponIssuanceService가 reserve() 호출 전 campaignStockCache.getSnapshot(campaignId) 조회
  2) 스냅샷이 존재하고 0 이하 → DB 진입 없이 즉시 품절 응답
     스냅샷이 없거나(캐시 미스) Redis 장애로 조회 실패 → 무조건 DB로 통과(V2와 동일 경로)
  3) DB reserve()(V2, 비관적 락)가 최종 판단. 성공 시 coupon_issue INSERT
  4) 커밋 후(AFTER_COMMIT) CampaignStockSnapshotListener가 최신 remainingStock을
     Redis에 SET (TTL 60초)
  5) CampaignStockSnapshotReconciliationJob이 15초 주기로 DB 기준 값을 다시 써서
     스냅샷 드리프트를 자가치유 (예: 관리자 재고보정처럼 발급 흐름을 거치지 않는 경로로
     DB만 바뀌는 경우, 2026-08-19 실측으로 이 드리프트가 실제로 발견됨)

[의도된 결과]
  정상 상황: 초과발급 0건(V2와 동일, DB가 여전히 최종 판단), 품절 이후 요청은 DB에
             도달하지 않아 hot row 경합·커넥션 풀 고갈이 완화된다.
  Redis 강제 종료 시: 초과발급 0건 유지 (Redis가 애초에 결정 권한이 없으므로 붕괴할 게
             없다). 다만 사전필터 효과가 사라져 지연시간이 V2 수준으로 되돌아간다.
             Redis 복구 후에는 재동기화 잡이 스냅샷을 다시 채운다.

[이 버전이 증명하는 것]
  "Redis에 정합성 판단 권한을 주지 않는" 설계를 택하면, Redis 장애가 정확성 리스크가
  아니라 성능 리스크로 격하된다는 것. 4팀이 대개 Redis를 게이트로 쓸 것이라는 전제 하에,
  우리는 그 리스크 자체를 구조적으로 제거했다는 게 차별점(발표전략 참고).

[디메리트 — 발표에서 정직하게 인정할 부분]
  - 스냅샷은 100% 실시간이 아니라 DB 커밋 이후 비동기로 반영되므로, 아주 짧은 시차 동안
    "재고 있는데 없다고 나옴"(오탐) 창이 존재한다 — 재동기화 주기(15초)로 최소화하되
    완전히 없애지는 못한다.
  - 사전필터는 "이미 끝난 게 뻔한" 요청만 걸러줄 뿐, 재고가 실제로 남아있는 동안의
    순수 경쟁 트래픽은 여전히 V2(비관적 락)로 처리된다. 즉 hot row 경합 자체를 없애는
    게 아니라 "품절 이후의 낭비 트래픽"만 줄여준다 — 8/19 실패의 원인 중 일부만 해소한다.
    (남은 절반은 커넥션 풀 크기 조정/락 대기시간 조정 등 별도 후속 과제)

----------------------------------------------------------------
V4 — 재고 샤딩 (병목 원인 자체를 분산, 2026-08-20 저녁 신설)
----------------------------------------------------------------

> 참고: 오전에는 "Redis 게이트 + DB 백스톱"이라는 옛 계획의 V4를 폐기한다고 이 자리에
> 적었었다. 그 백스톱은 새 V3(Redis가 발급을 결정하지 않는 설계)에서 애초에 필요 없어졌기
> 때문에 여전히 유효한 결정이다. 지금의 V4는 그것과 무관한 완전히 새로운 단계다 —
> "V4"라는 번호를 폐기됐다가 재사용한 셈이라 헷갈릴 수 있어 명시해둔다.

[사용 기술]
  기존 V2/V3와 동일한 MySQL row lock 원리, 다만 잠그는 대상이 campaign 1개 row가 아니라
  campaign_stock_shard의 N개(기본 10개) row로 나뉜다.

[구현 개요 — 이미 구현·병합 완료(dev, 2026-08-20, PR #100)]
  V3까지 적용해도 coupon_mixed_5k_x4.js 실측에서 목표 달성률이 80%대에 머물렀다 —
  20,000건이 결국 campaign row 하나로 몰리는 처리량 자체의 한계였다(Prometheus로 HikariCP
  active=110/pending=100+ 확인). 캠페인 재고를 `campaign_stock_shard` 테이블의 N개 독립된
  row로 쪼개서, InnoDB가 서로 다른 샤드는 동시에 잠글 수 있게 한다.

  1) 요청마다 랜덤 시작 샤드 + 순차 폴백으로 배정 — 하필 빈 샤드부터 시도해도 재고가
     남은 다른 샤드를 자동으로 찾아가므로, 재고가 하나라도 남아있으면 정상 재고인데
     품절 처리되는 일은 없다
  2) 샤드는 캠페인 생성 시점이 아니라 이 전략이 그 캠페인을 처음 다룰 때 지연 생성된다
     (`campaign.remaining_stock` 기준으로 분배) — 기존 캠페인(부분 발급분 포함)도 별도
     백필 마이그레이션 없이 자동으로 정확한 값이 채워짐
  3) 개별 샤드 시도는 `REQUIRES_NEW`로 완전히 독립된 트랜잭션 — 한 트랜잭션이 여러 샤드를
     순회하며 락을 쌓아두면 서로 다른 순서로 방문하는 트랜잭션끼리 데드락이 남(100 동시요청
     테스트로 실측)
  4) `campaign.remaining_stock`/Redis 스냅샷은 더 이상 원본이 아니라 샤드 합계를 사후
     복사하는 표시값(V3의 스냅샷 리스너/재동기화 잡을 그대로 재사용, 소스만 교체) —
     그래서 V3의 사전필터 계층이 코드 변경 없이 V4 위에도 그대로 얹힌다(3절 참고)
  5) `rollback()`은 원래 감소시켰던 그 샤드로 정확히 복원하지 않고, capacity 여유가 있는
     아무 샤드에나 복원한다 — 각 샤드의 capacity가 생성 시점 값으로 고정되므로
     `sum(capacity) = total_stock`이 항상 성립해 정확성에 문제없다(직접 검산 완료)

[의도된 결과]
  초과발급 0건은 V2/V3와 동일(여전히 DB 원자 UPDATE가 각 샤드 단위로 최종 판단).
  처리량은 이론상 최대 N배(샤드 10개) 분산 — 재고가 넉넉한 구간은 대부분 1번 시도로
  끝나 경합이 N분의 1이 되고, 재고 소진 직전에만 여러 샤드를 순회하는 비용이 붙는다.

[이 버전이 증명하는 것]
  V3까지의 "Redis 사전필터"는 품절 이후의 낭비 트래픽만 줄일 뿐, 재고가 남아있는 동안의
  순수 경쟁 트래픽 자체는 줄이지 못한다는 한계를 V3 디메리트에서 이미 인정했었다(위 참고).
  V4는 바로 그 남은 절반 — hot row 경합 자체 — 을 없앤다. "재고 판정 권한을 DB 밖으로
  내보내지 않으면서(Redis 게이트 아님) 처리량 한계를 푼다"는 게 V4의 핵심 메시지다.

[디메리트]
  - 샤드 개수(10개)는 상수로 고정 — 캠페인별 가변 설정은 스코프 밖(필요 시
    application.properties 값으로 확장 가능)
  - rollback이 원래 샤드가 아닌 다른 샤드로 복원될 수 있어, "샤드별 remaining_stock"은
    더 이상 의미 있는 단위가 아니고 합계만 신뢰 가능한 값이다(검증쿼리 (b)도 이미 합계
    기준으로 수정됨)

5. 공정 비교 조건 (통제 변인) — 반드시 지킬 것
================================================================

버전 간 차이가 reserve() 및 사전필터 외의 요인에서 오면 비교가 무효가 된다.
멘토와 심사위원이 가장 먼저 물어볼 지점이므로 사전에 통제한다.

전 버전에서 동일하게 유지할 것:

  [ ] 멱등성 처리 (Idempotency-Key 조회 및 저장)
  [ ] 멤버십 eligibility 체크 위치와 로직
  [ ] 요청/응답 DTO 및 직렬화
  [ ] coupon_issue INSERT 로직과 컬럼
  [ ] 트랜잭션 경계
  [ ] 로깅 수준 (V1만 로그가 적으면 유리해진다)
  [ ] PII 마스킹 처리
  [ ] Mock 알림 발송 호출
  [ ] DB 인덱스 구성
  [ ] 커넥션 풀 설정

구현 방법: 공유 뼈대를 추상 클래스 또는 템플릿 메서드로 한 곳에 두고,
reserve()/rollback()만 구현체가 다르게 갖는다(V3/V4 위에도 사전필터는 동일하게 얹힘, 3절 참고).
버전별로 컨트롤러/서비스를 통째로 복사하면 위 항목이 반드시 어긋난다.

6. 실험 절차
================================================================

[반복 횟수]
  각 버전 5회 실행. 1회성 우연을 배제한다.
  일정과역할 성공기준의 "반복 실행(최소 5회) 시 매번 재현" 항목과 동일 기준.

[매 실행 전 초기화 — 스크립트로 원커맨드화 필수]
  1) coupon_issue, coupon_state_log TRUNCATE
  2) campaign.remaining_stock = total_stock 으로 리셋
  3) (V4만) campaign_stock_shard TRUNCATE — 지연 생성이라 다음 reserve() 호출 시
     campaign.remaining_stock 기준으로 자동 재생성됨
  4) Redis 스냅샷 키 삭제 (stock:*) — TTL 60초라 자연 만료도 되지만 데모 중엔 즉시 삭제 권장
  5) (V3/V4만) 재동기화 잡이 다음 15초 주기 내에 DB 기준으로 재반영되는지 확인,
     또는 수동으로 초기 스냅샷을 한 번 SET
  6) k6 유저 목록(users_20000.json) 재사용 — 매번 같은 유저 집합을 쓴다

  데모 중에 이 과정을 손으로 하면 반드시 사고가 난다. 스크립트로 만들어 둘 것.

[부하 시나리오]
  기본: 재고 10,000 / 서로 다른 유저 20,000명 동시 요청
        ※ [멘토 확정, 2026-08-12] 공식 조건 = 테스트 유저 20,000명(중복 없음) / ramp-up 60초.
          전 팀 공통 기준이며 임의 변경 불가. k6 스크립트는 05_시스템설계 5.2절 참고.
  서브: 동일 유저 중복 요청 (5,000명이 각 4회) — 1인 1매 검증용
        2026-08-19 coupon_mixed_5k_x4.js가 이 서브 시나리오의 실제 실행 사례
        (V2 기준 2,652/5,000 발급, DB 커넥션 풀 고갈 재현) — 저장소에 아직 미커밋,
        커밋 후 V3 재실행 결과와 Before/After로 비교할 것

[측정 지표]
  - 최종 발급 건수 (DB COUNT 기준. k6 응답 카운트가 아니라 DB가 진실)
  - 초과발급 건수 = 발급 건수 - total_stock (음수면 0으로 표기)
  - 1인 1매 위반 건수
  - 전체 처리 완료 시간
  - p95 응답 시간 (참고용. 평가 대상 아님을 리포트에 명시)
  - 타임아웃/에러 응답 건수 (커넥션 풀 고갈 건수 별도 집계 — 8/19 실패의 핵심 지표)
  - Redis 강제 종료 조건에서의 초과발급 건수 및 지연시간 변화 (V3/V4)

7. 결과표 템플릿 (발표용 머니 슬라이드)
================================================================

이 표 하나로 전체 서사가 전달되어야 한다. 숫자는 실측으로 채운다.

  +---------------------------+----------+-----------+------------------------+---------+
  |                           | 초과발급 | 처리시간  | Redis 장애 시          | 1인1매  |
  +---------------------------+----------+-----------+------------------------+---------+
  | V1  제어 없음             |  ____건  |  빠름     |          —             |  0건    |
  | V2  DB 비관적 락          |   0건    |  느림(실패 다수) |    —            |  0건    |
  | V3  DB + Redis 스냅샷     |   0건    |  V2보다 개선 |  0건 유지(지연만 V2로) |  0건    |
  | V4  + 재고 샤딩(N=10)     |   0건    |  V3보다 더 개선 |  0건 유지(지연만 V3로) |  0건    |
  +---------------------------+----------+-----------+------------------------+---------+

읽는 법: 왼쪽 두 열은 4팀이 모두 보여주는 영역, 오른쪽 두 열이 우리가 더 한 영역.
"Redis 장애 시" 열이 기존 계획(V3 붕괴 → V4 복구)과 가장 크게 달라진 지점이다 —
지금은 V3/V4 둘 다 장애 시에도 무너지지 않는다는 것을 보여주는 열이다.
V3→V4의 "처리시간" 개선폭은 아직 실측 전(coupon_mixed_5k_x4.js 재측정 필요, 이호성).

8. 정합성 검증과의 연결 (놓치면 아까운 지점)
================================================================

V1이 만들어내는 초과발급은 인위적으로 심은 데이터가 아니라
실제 경쟁 상태로 발생한 진짜 위반 데이터다.

기존 계획(05_시스템설계 2.3절)은 검증 배치 시연용으로 오염 데이터를 수동 삽입하는 것인데,
V1을 한 번 돌리고 그 결과를 그대로 검증 배치(ConsistencyVerificationJob, dev에 구현 완료)에
먹이면 서술이 훨씬 강해진다.

  "이건 저희가 심은 데이터가 아닙니다.
   V1을 실제로 돌려서 나온 실제 위반이고, 검증 배치가 정확히 N건을 탐지했습니다."

효과: 지금은 따로 노는 두 개의 자랑거리(버전 비교 / 정합성 검증)가 하나의 서사로 이어진다.

[실행 순서]
  1) V1 실행 → 초과발급 데이터 생성
  2) 생성된 위반 건수를 SQL로 직접 세어 기록 (기대값)
  3) 검증 배치 실행 → 탐지 건수가 기대값과 일치하는지 확인
  4) 같은 데이터로 재실행 → 결과 해시 동일 확인 (결정론성)

수동 오염 데이터 삽입도 병행한다. V1이 만들지 못하는 유형
(상태 역행, idempotency 충돌, 등급 위반)은 여전히 수동 삽입이 필요하다.
