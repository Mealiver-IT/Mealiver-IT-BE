이 문서는 "동시성 제어 전략을 3단계로 구현하고 같은 조건에서 비교한다"는 실험의 설계서다.
구현 담당자는 이 문서만 읽어도 각 버전이 무엇을 쓰고 무엇을 증명해야 하는지 알 수 있어야 한다.


================================================================
1. 왜 버전을 나누는가
================================================================

기존 문서(04_아키텍처 4절, 리서치요약)는 전략 선택 근거를 외부 사례의 수치에 의존하고 있다.
예: "올리브영 실측 Lua 21% 저하 vs 이중카운터 8% 저하"

이 방식의 약점은 두 가지다.

(1) 인용된 수치는 그 회사의 워크로드에서 나온 값이라, 우리 조건에서 재현된다는 보장이 없다.
(2) 발표에서 "저희는 X를 골랐습니다. 왜냐하면 A사가 그랬기 때문입니다"는 방어력이 약하다.

버전을 전부 구현해서 동일 조건으로 측정하면, 근거가 남의 숫자에서 우리 숫자로 바뀐다.
"V2는 느립니다"라고 말하는 것과, 무대에서 V2를 돌려 타임아웃이 찍히는 걸 보여주는 것은 다르다.

추가 효과: 4팀이 모두 완성품만 보여줄 때, 고장난 버전에서 출발하는 팀은 우리뿐이다.

[2026-08-20 추가] V3a(Lua)/V3b(이중카운터)를 접은 이유도 같은 원칙의 연장이다 — 남의 사례
수치(올리브영)에 기대 미리 설계했던 "Redis가 발급을 직접 결정하는 게이트"는, 실제로 우리
워크로드에서 검증하기도 전에 다른 문제(DB 커넥션 풀 고갈)가 8/19 실측에서 먼저 터졌다.
없는 문제를 막으려고 검증 안 된 구조를 새로 얹는 대신, 실제로 관측된 문제(품절 이후 낭비
트래픽이 DB를 두드리는 것)를 정확히 겨냥한 최소 구조(캐시)로 바꿨다.


================================================================
2. 설계 원칙 — 각 버전은 서로 다른 축에서 실패(또는 극복)한다
================================================================

버전 사다리가 "느림 → 빠름 → 더 빠름"이면 얕다. 처리량은 평가 대상이 아니기 때문이다.
각 단계가 다른 종류의 문제를 드러내거나 해결하도록 설계하면, 사다리 자체가 논증이 된다.

  V1  정확성이 없다        → 초과발급 발생
  V2  정확하지만 병목이다   → 락 대기 타임아웃, 커넥션 풀 고갈 (8/19 실측으로 재현됨)
  V3  정확성은 그대로, 병목만 완화한다 → Redis가 죽어도 초과발급은 여전히 0건
                             (Redis는 발급을 결정하지 않는 캐시일 뿐이므로)

[2026-08-20 갱신] 원래 설계(V1~V4)는 V3에서 "빠르지만 취약함"이라는 새로운 실패 축을
일부러 만들고, V4에서 그걸 봉합하는 4단 구조였다. 지금 사다리는 3단이고 V3에 실패 축이
없다 — 이게 오히려 서사의 핵심이다. "Redis에 정합성 판단 권한을 아예 주지 않았기 때문에,
Redis가 죽어도 잃을 게 지연시간뿐이다"는 것을 V4 없이 V3 자체로 증명한다. 즉 V4가 사라진
게 아니라, V4가 하려던 일(Redis 상태 유실에도 초과발급 방지)을 V3의 설계 자체가 처음부터
구조적으로 만족시키므로 별도 단계가 필요 없어진 것이다.


================================================================
3. API 버전이 아니라 전략 버전이다 (중요)
================================================================

REST 관례상 /v1, /v2 같은 URL 버전은 "요청/응답 계약이 바뀔 때" 올린다.
우리가 바꾸는 것은 내부 재고 확보 전략이고 응답 스펙은 동일하다.
따라서 URL에 v1~v3를 그대로 노출하면 "응답이 같은데 왜 API 버전이 다르냐"는 지적을 받는다.

[확정 구조]

  POST /api/v1/campaigns/{campaignId}/coupons
      → 실제 서비스 API. 전략은 설정값으로 주입. 계약은 프로젝트 내내 불변.
      (실제 구현 경로는 현재 /api/campaigns/... — 버전 프리픽스 미적용 상태.
       08_개발표준 문서-코드 불일치 항목 참고, 남은 기간엔 우선순위 낮음)

  POST /bench/{strategy}/campaigns/{campaignId}/coupons
      → 벤치마크 전용 경로. {strategy} = v1 | v2 | v3
      → k6 부하테스트는 이 경로를 호출한다.
      → bench 프로파일에서만 활성화. 운영 프로파일에서는 빈 등록 자체를 하지 않는다.

발표 슬라이드에서는 V1~V3라는 라벨을 그대로 써도 된다. 문제는 URL 구조이지 네이밍이 아니다.

[내부 구조 — 2026-08-20 갱신]

  interface StockReservationStrategy {
      boolean reserve(Long campaignId);   // 재고 확보 시도. 실패 시 false
      void rollback(Long campaignId);     // 확보 후 후속 단계 실패 시 원복
  }

V3는 별도의 StockReservationStrategy 구현체가 아니다 — reserve()/rollback()은 V2
(PessimisticLockStockReservationStrategy)를 그대로 쓰고, 그 앞단(CouponIssuanceService)에
Redis 사전필터 체크 한 겹만 추가한 것이 V3다. 실제 구현:

  - CampaignStockCache (api/campaign/cache) — Redis 재고 스냅샷 read/write, 장애 시
    예외를 삼키고 null 반환(DB로 폴백)
  - CampaignStockSnapshotListener — 발급 성공 후 AFTER_COMMIT 시점에 스냅샷 갱신
  - CampaignStockSnapshotReconciliationJob — 15초 주기로 DB 기준 재동기화(자가치유),
    Redis 스냅샷 TTL(60초)은 이 잡이 멈췄을 때만 발동하는 최후 안전장치
  - CouponIssuanceService — reserve() 호출 전 campaignStockCache.getSnapshot() 조회,
    "확실히 품절"일 때만 DB 진입 전 즉시 거절. 캐시 미스/Redis 장애 시에는 무조건 DB로 통과
    (스냅샷 부재를 품절로 오판하지 않는다)

따라서 구현체는 V1/V2 두 개뿐이고, V3는 "V2 + 사전필터"라는 조합이다. bench 라우팅에서
v3 스트래티지를 별도로 만들 필요는 없고, v2 스트래티지에 사전필터 on/off 플래그를 주는
방식으로 A/B(필터 있음/없음)를 재현하면 된다.


================================================================
4. 각 버전 상세
================================================================

----------------------------------------------------------------
V1 — 제어 없음 (문제 실증용, 의도적으로 고장난 버전)
----------------------------------------------------------------

[사용 기술] 없음. 단순 조회 후 분기.

[구현 개요]
  재고를 조회하고, 0보다 크면 차감하고 INSERT 한다.
  조회와 차감 사이에 아무런 원자성 보장이 없다.

[의도된 결과]
  초과발급이 발생해야 한다. 20,000 요청에 10,000장 재고 기준으로 수천 장 초과가 목표.
  초과가 안 나오면 부하가 부족한 것이므로 VU 수를 올려 재현시킨다.

[이 버전이 증명하는 것]
  (1) 문제가 실재한다. 슬라이드가 아니라 데이터로 보여준다.
  (2) DB 유니크 제약 uk_campaign_user(campaign_id, user_id)가 있어도 총량 초과는 그대로 발생한다.
      유니크 제약은 "1인 1매"만 막고 "총량"은 막지 못한다는 사실을 실물로 증명한다.
      → 04_아키텍처 2절이 문장으로만 주장하던 내용의 실증

[주의]
  이 코드는 절대 /api/v1 경로에 노출하지 않는다. /bench/v1 전용.
  "일부러 고장난 코드가 실제 API에 열려 있다"는 것 자체가 지적 대상이 된다.

[2026-08-20 기준 상태] 미구현. 사다리 3단 중 유일하게 남은 신규 구현 항목. 비용이 가장
낮으므로(약 20줄) 가장 먼저 처리한다.

----------------------------------------------------------------
V2 — DB 비관적 락 (정확하지만 병목)
----------------------------------------------------------------

[사용 기술]
  MySQL row lock (SELECT ... FOR UPDATE)
  Spring Data JPA @Lock(LockModeType.PESSIMISTIC_WRITE)

[구현 개요]
  campaign 로우를 비관적 락으로 잠그고 재고를 확인/차감한 뒤 커밋한다.
  트랜잭션이 직렬화되므로 초과발급이 원천 차단된다.

[의도된 결과]
  초과발급 0건 (정확성 확보)
  동시에 hot row 경합 발생 — 다수 트랜잭션이 캠페인 로우 하나에 줄을 선다.
  락 대기 타임아웃(innodb_lock_wait_timeout), 커넥션 풀 고갈, 응답 지연이 관측되어야 한다.

[2026-08-20 추가 — 실측 확인됨]
  8/19 coupon_mixed_5k_x4.js(캠페인 300개, 20,000건 순간 동시요청)에서 정확히 이 실패
  양상이 재현됐다: DB 커넥션 풀 고갈 + hot row 경합으로 목표 5,000건 중 2,652건만 발급.
  이 실측이 V3 설계(사전 필터)를 채택한 직접적 근거가 됐다.

[측정 시 주의]
  타임아웃으로 실패한 요청이 5xx로 대량 찍히면 데모 인상이 나쁘다.
  실패는 "품절/재시도 안내" 도메인 에러코드로 매끄럽게 매핑해두되,
  리포트에는 타임아웃 발생 건수를 별도 지표로 기록한다.

[이 버전이 증명하는 것]
  정확성은 DB만으로도 확보된다. 문제는 품절 이후에도 요청이 계속 DB(hot row)까지
  도달해 자원을 갉아먹는다는 것. 따라서 "이미 끝난 게 뻔한 요청"만이라도 DB 앞에서
  걸러내야 한다는 결론이 도출된다 — 이게 V3의 동기다.

----------------------------------------------------------------
V3 — DB 선반영 + Redis 스냅샷 사전필터 (정확성 불변, 병목만 완화)
----------------------------------------------------------------

[2026-08-20 확정] 기존 V3a(Lua)/V3b(이중카운터)를 대체하는 새 설계. 핵심 차이는
"Redis가 발급을 결정하는가"이다 — 이 버전에서 Redis는 절대 발급 여부를 직접 결정하지
않는다. 최종 판단은 항상 V2와 동일하게 DB(비관적 락 + remaining_stock)가 한다.
Redis는 그 결과를 사후에 복사해두는 캐시이자, DB 진입 전 "확실히 끝난 요청"만 걸러내는
사전필터다.

[데이터 흐름]
  기존 계획(Redis 게이트):  요청 → Redis 체크(결정) → 통과 시 DB 기록
  새 설계(DB 선반영):       요청 → [Redis 스냅샷 있고 0 이하면 즉시 거절]
                                  → (그 외 전부) DB 기록(V2와 동일, 최종 결정)
                                  → 성공 시 AFTER_COMMIT으로 Redis 스냅샷 갱신

[사용 기술]
  StringRedisTemplate (spring-boot-starter-data-redis)
  Spring 트랜잭션 이벤트(@TransactionalEventListener(AFTER_COMMIT))
  Spring @Scheduled + ShedLock (재동기화 잡의 다중 인스턴스 중복 실행 방지)

[구현 개요 — 이미 구현·병합 완료(dev, 2026-08-19)]
  1) CouponIssuanceService가 reserve() 호출 전 campaignStockCache.getSnapshot(campaignId) 조회
  2) 스냅샷이 존재하고 0 이하 → DB 진입 없이 즉시 품절 응답
     스냅샷이 없거나(캐시 미스) Redis 장애로 조회 실패 → 무조건 DB로 통과(V2와 동일 경로)
  3) DB reserve()(V2, 비관적 락)가 최종 판단. 성공 시 coupon_issue INSERT
  4) 커밋 후(AFTER_COMMIT) CampaignStockSnapshotListener가 최신 remainingStock을
     Redis에 SET (TTL 60초)
  5) CampaignStockSnapshotReconciliationJob이 15초 주기로 DB 기준 값을 다시 써서
     스냅샷 드리프트를 자가치유 (예: 관리자 재고보정처럼 발급 흐름을 거치지 않는 경로로
     DB만 바뀌는 경우, 2026-08-19 실측으로 이 드리프트가 실제로 발견됨)

[의도된 결과]
  정상 상황: 초과발급 0건(V2와 동일, DB가 여전히 최종 판단), 품절 이후 요청은 DB에
             도달하지 않아 hot row 경합·커넥션 풀 고갈이 완화된다.
  Redis 강제 종료 시: 초과발급 0건 유지 (Redis가 애초에 결정 권한이 없으므로 붕괴할 게
             없다). 다만 사전필터 효과가 사라져 지연시간이 V2 수준으로 되돌아간다.
             Redis 복구 후에는 재동기화 잡이 스냅샷을 다시 채운다.

[이 버전이 증명하는 것]
  "Redis에 정합성 판단 권한을 주지 않는" 설계를 택하면, Redis 장애가 정확성 리스크가
  아니라 성능 리스크로 격하된다는 것. 4팀이 대개 Redis를 게이트로 쓸 것이라는 전제 하에,
  우리는 그 리스크 자체를 구조적으로 제거했다는 게 차별점(발표전략 참고).

[디메리트 — 발표에서 정직하게 인정할 부분]
  - 스냅샷은 100% 실시간이 아니라 DB 커밋 이후 비동기로 반영되므로, 아주 짧은 시차 동안
    "재고 있는데 없다고 나옴"(오탐) 창이 존재한다 — 재동기화 주기(15초)로 최소화하되
    완전히 없애지는 못한다.
  - 사전필터는 "이미 끝난 게 뻔한" 요청만 걸러줄 뿐, 재고가 실제로 남아있는 동안의
    순수 경쟁 트래픽은 여전히 V2(비관적 락)로 처리된다. 즉 hot row 경합 자체를 없애는
    게 아니라 "품절 이후의 낭비 트래픽"만 줄여준다 — 8/19 실패의 원인 중 일부만 해소한다.
    (남은 절반은 커넥션 풀 크기 조정/락 대기시간 조정 등 별도 후속 과제)

----------------------------------------------------------------
V4 — 폐기 (2026-08-20)
----------------------------------------------------------------

기존 계획의 "Redis 게이트 + DB 백스톱"은 Redis가 발급을 직접 결정하는 구조였기 때문에
DB 백스톱(조건부 UPDATE로 Redis 상태 유실을 뒤에서 방어)이 반드시 필요했다.
새 V3는 애초에 Redis가 발급을 결정하지 않으므로, V4가 하려던 일을 V3 자체가 처음부터
만족한다. 별도 단계로 구현할 이유가 없어 사다리에서 제외한다.

5. 공정 비교 조건 (통제 변인) — 반드시 지킬 것
================================================================

버전 간 차이가 reserve() 및 사전필터 외의 요인에서 오면 비교가 무효가 된다.
멘토와 심사위원이 가장 먼저 물어볼 지점이므로 사전에 통제한다.

전 버전에서 동일하게 유지할 것:

  [ ] 멱등성 처리 (Idempotency-Key 조회 및 저장)
  [ ] 멤버십 eligibility 체크 위치와 로직
  [ ] 요청/응답 DTO 및 직렬화
  [ ] coupon_issue INSERT 로직과 컬럼
  [ ] 트랜잭션 경계
  [ ] 로깅 수준 (V1만 로그가 적으면 유리해진다)
  [ ] PII 마스킹 처리
  [ ] Mock 알림 발송 호출
  [ ] DB 인덱스 구성
  [ ] 커넥션 풀 설정

구현 방법: 공유 뼈대를 추상 클래스 또는 템플릿 메서드로 한 곳에 두고,
reserve()/rollback()만 구현체가 다르게 갖는다(V3는 V2 구현체 재사용 + 사전필터 플래그).
버전별로 컨트롤러/서비스를 통째로 복사하면 위 항목이 반드시 어긋난다.

8. 정합성 검증과의 연결 (놓치면 아까운 지점)
================================================================

V1이 만들어내는 초과발급은 인위적으로 심은 데이터가 아니라
실제 경쟁 상태로 발생한 진짜 위반 데이터다.

기존 계획(05_시스템설계 2.3절)은 검증 배치 시연용으로 오염 데이터를 수동 삽입하는 것인데,
V1을 한 번 돌리고 그 결과를 그대로 검증 배치(ConsistencyVerificationJob, dev에 구현 완료)에
먹이면 서술이 훨씬 강해진다.

  "이건 저희가 심은 데이터가 아닙니다.
   V1을 실제로 돌려서 나온 실제 위반이고, 검증 배치가 정확히 N건을 탐지했습니다."

효과: 지금은 따로 노는 두 개의 자랑거리(버전 비교 / 정합성 검증)가 하나의 서사로 이어진다.

[실행 순서]
  1) V1 실행 → 초과발급 데이터 생성
  2) 생성된 위반 건수를 SQL로 직접 세어 기록 (기대값)
  3) 검증 배치 실행 → 탐지 건수가 기대값과 일치하는지 확인
  4) 같은 데이터로 재실행 → 결과 해시 동일 확인 (결정론성)

수동 오염 데이터 삽입도 병행한다. V1이 만들지 못하는 유형
(상태 역행, idempotency 충돌, 등급 위반)은 여전히 수동 삽입이 필요하다.
