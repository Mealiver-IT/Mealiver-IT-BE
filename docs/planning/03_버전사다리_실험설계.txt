# 버전 사다리 실험 설계 — V1~V4 동시성 전략 비교

> 이 문서를 처음 읽는 사람(또는 AI)을 위한 배경
>
> - 프로젝트: 대규모 트래픽 선착순 쿠폰 발급 시스템 (팀명 태진아 / 프로젝트명 밀리버릿)
> - 소재: 배달앱에서 매일 오전 11시 오픈하는 선착순 할인 쿠폰 (배민 bhc 치킨 오픈런 스타일)
> - 핵심 요구사항: 재고 10,000장에 20,000명이 동시 요청해도 초과발급 0건, 1인 최대 1매
> - 같은 주제로 4팀이 경쟁하며 시상이 있음. 처리량/응답속도는 평가 대상이 아니고, 평가축은 동시성 정확성과 정합성 자기검증
> - 관련 문서: 09_기획서 / 04_아키텍처 / 05_시스템설계 / 일정과역할 / 01_설계보완검토안 / 07_실행계획 / 발표전략

이 문서는 "동시성 제어 전략을 4단계로 구현하고 같은 조건에서 비교한다"는 실험의 설계서다.
구현 담당자는 이 문서만 읽어도 각 버전이 무엇을 쓰고 무엇을 증명해야 하는지 알 수 있어야 한다.


================================================================
1. 왜 버전을 나누는가
================================================================

기존 문서(04_아키텍처 4절, 리서치요약)는 전략 선택 근거를 외부 사례의 수치에 의존하고 있다.
예: "올리브영 실측 Lua 21% 저하 vs 이중카운터 8% 저하"

이 방식의 약점은 두 가지다.

(1) 인용된 수치는 그 회사의 워크로드에서 나온 값이라, 우리 조건에서 재현된다는 보장이 없다.
(2) 발표에서 "저희는 X를 골랐습니다. 왜냐하면 A사가 그랬기 때문입니다"는 방어력이 약하다.

버전을 전부 구현해서 동일 조건으로 측정하면, 근거가 남의 숫자에서 우리 숫자로 바뀐다.
"V2는 느립니다"라고 말하는 것과, 무대에서 V2를 돌려 타임아웃이 찍히는 걸 보여주는 것은 다르다.

추가 효과: 4팀이 모두 완성품만 보여줄 때, 고장난 버전에서 출발하는 팀은 우리뿐이다.


================================================================
2. 설계 원칙 — 각 버전은 서로 다른 축에서 실패한다
================================================================

버전 사다리가 "느림 → 빠름 → 더 빠름"이면 얕다. 처리량은 평가 대상이 아니기 때문이다.
각 단계가 다른 종류의 문제로 무너지도록 설계하면, 사다리 자체가 논증이 된다.

  V1  정확성이 없다        → 초과발급 발생
  V2  정확하지만 병목이다   → 락 대기 타임아웃, 커넥션 풀 고갈
  V3  빠르고 정확하지만 취약하다 → Redis 장애 시 총량 방어선 소실
  V4  견딘다              → 장애 주입에도 초과발급 0건

즉 이 사다리는 성능 개선의 역사가 아니라 "동시성 문제에는 정확성/확장성/내결함성이라는
서로 다른 실패 축이 있다"는 것을 보여주는 교재다.


================================================================
3. API 버전이 아니라 전략 버전이다 (중요)
================================================================

REST 관례상 /v1, /v2 같은 URL 버전은 "요청/응답 계약이 바뀔 때" 올린다.
우리가 바꾸는 것은 내부 재고 확보 전략이고 응답 스펙은 동일하다.
따라서 URL에 v1~v4를 그대로 노출하면 "응답이 같은데 왜 API 버전이 다르냐"는 지적을 받는다.

[확정 구조]

  POST /api/v1/campaigns/{campaignId}/coupons
      → 실제 서비스 API. 전략은 설정값으로 주입. 계약은 프로젝트 내내 불변.

  POST /bench/{strategy}/campaigns/{campaignId}/coupons
      → 벤치마크 전용 경로. {strategy} = v1 | v2 | v3a | v3b | v4
      → k6 부하테스트는 이 경로를 호출한다.
      → bench 프로파일에서만 활성화. 운영 프로파일에서는 빈 등록 자체를 하지 않는다.

발표 슬라이드에서는 V1~V4라는 라벨을 그대로 써도 된다. 문제는 URL 구조이지 네이밍이 아니다.

[내부 구조]

  interface StockReservationStrategy {
      boolean reserve(Long campaignId);   // 재고 확보 시도. 실패 시 false
      void rollback(Long campaignId);     // 확보 후 후속 단계 실패 시 원복
  }

구현체 5개(V1, V2, V3a, V3b, V4)가 이 인터페이스만 다르게 구현한다.


================================================================
4. 각 버전 상세
================================================================

----------------------------------------------------------------
V1 — 제어 없음 (문제 실증용, 의도적으로 고장난 버전)
----------------------------------------------------------------

[사용 기술] 없음. 단순 조회 후 분기.

[구현 개요]
  재고를 조회하고, 0보다 크면 차감하고 INSERT 한다.
  조회와 차감 사이에 아무런 원자성 보장이 없다.

[의도된 결과]
  초과발급이 발생해야 한다. 20,000 요청에 10,000장 재고 기준으로 수천 장 초과가 목표.
  초과가 안 나오면 부하가 부족한 것이므로 VU 수를 올려 재현시킨다.

[이 버전이 증명하는 것]
  (1) 문제가 실재한다. 슬라이드가 아니라 데이터로 보여준다.
  (2) DB 유니크 제약 uk_campaign_user(campaign_id, user_id)가 있어도 총량 초과는 그대로 발생한다.
      유니크 제약은 "1인 1매"만 막고 "총량"은 막지 못한다는 사실을 실물로 증명한다.
      → 04_아키텍처 2절이 문장으로만 주장하던 내용의 실증

[주의]
  이 코드는 절대 /api/v1 경로에 노출하지 않는다. /bench/v1 전용.
  "일부러 고장난 코드가 실제 API에 열려 있다"는 것 자체가 지적 대상이 된다.

----------------------------------------------------------------
V2 — DB 비관적 락 (정확하지만 병목)
----------------------------------------------------------------

[사용 기술]
  MySQL row lock (SELECT ... FOR UPDATE)
  Spring Data JPA @Lock(LockModeType.PESSIMISTIC_WRITE)

[구현 개요]
  campaign 로우를 비관적 락으로 잠그고 재고를 확인/차감한 뒤 커밋한다.
  트랜잭션이 직렬화되므로 초과발급이 원천 차단된다.

[의도된 결과]
  초과발급 0건 (정확성 확보)
  동시에 hot row 경합 발생 — 20,000 트랜잭션이 캠페인 로우 하나에 줄을 선다.
  락 대기 타임아웃(innodb_lock_wait_timeout), 커넥션 풀 고갈, 응답 지연이 관측되어야 한다.

[측정 시 주의]
  타임아웃으로 실패한 요청이 5xx로 대량 찍히면 데모 인상이 나쁘다.
  실패는 "품절/재시도 안내" 도메인 에러코드로 매끄럽게 매핑해두되,
  리포트에는 타임아웃 발생 건수를 별도 지표로 기록한다.

[이 버전이 증명하는 것]
  정확성은 DB만으로도 확보된다. 문제는 재고 판정을 DB 안에서 하는 한 DB가 병목이라는 것.
  따라서 게이트를 DB 앞으로 빼야 한다는 결론이 자연스럽게 도출된다.

----------------------------------------------------------------
V3 — Redis 원자 게이트 (빠르고 정확하지만 취약)
----------------------------------------------------------------

Redis가 1차 관문 역할을 한다. 품절 이후의 요청은 DB에 도달조차 하지 않는다.
이 버전은 내부적으로 두 가지 구현을 A/B 비교한다.

  V3-a : Lua script
         재고 확인과 차감을 하나의 Lua 스크립트로 원자 실행. Redis 왕복 1회.
         Redis는 싱글 스레드이므로 스크립트 전체가 원자적으로 실행된다.

  V3-b : 이중 카운터 (DualCounter)
         countReq(1차 저비용 필터) INCR → count(2차 확정) INCR. Redis 왕복 2회.
         2차 실패 시 count만 자체 롤백. 리서치요약 3절 참고.

[A/B 비교의 목적]
  04_아키텍처 4.1절은 올리브영 실측(Lua -21% vs 이중카운터 -8%)을 근거로 V3-b를 채택했다.
  그러나 왕복 2회가 왕복 1회보다 싸다는 것은 직관에 반하므로,
  인용된 수치가 우리 워크로드에서 재현되는지 직접 측정한다.

  가설: 올리브영의 -21%는 Lua 자체 비용이 아니라 해당 스크립트의 작업량
        (SISMEMBER + GET + DECR + SADD 등)에서 나온 값일 수 있다.
        우리 Lua가 "재고 확인 + 차감" 수준이면 그 수치는 우리 조건에 적용되지 않는다.

[결과에 따른 판단 — 미리 합의해 둘 것]
  차이가 5% 이내로 미미  → V3-a(Lua) 채택. countReq 조기소진 결함이 없는 쪽을 택한다.
  이중카운터가 유의미하게 우세 → V3-b 유지. 결함은 감수하되 대가를 실측으로 제시한다.

  어느 쪽이든 countReq 조기소진 발견(리서치요약 3절)은 발표 자산으로 그대로 남는다.
  "이 결함을 발견했고, 재측정 결과 감수할 이유가 있었다/없었다"로 서술이 이어진다.

[의도된 결과]
  정상 상황: 초과발급 0건, V2 대비 뚜렷하게 빠름
  Redis 강제 종료 시: 카운터가 리셋되어 총량 초과발급 발생 (= V3의 실패 축)

[이 버전이 증명하는 것]
  속도 문제는 해결되지만, 총량 판정 권한이 Redis에만 있으면 Redis 상태 유실이
  그대로 초과발급으로 이어진다. 방어선이 한 겹뿐이라는 것.

----------------------------------------------------------------
V4 — Redis 게이트 + DB 백스톱 + 워밍업 (최종 채택)
----------------------------------------------------------------

[사용 기술]
  V3에서 선택된 Redis 게이트 (Lua 또는 이중카운터)
  + MySQL 조건부 UPDATE (총량 최종 방어선)
  + 기동/복구 시 DB 기준 멱등 워밍업

  상세 설계는 04_아키텍처 4.2절 참고.

[구현 개요]
  1) Redis 게이트 통과
  2) 같은 트랜잭션 안에서 조건부 UPDATE 실행
         UPDATE campaign SET remaining_stock = remaining_stock - 1
          WHERE id = :campaignId AND remaining_stock > 0
     affected rows = 0 이면 품절 처리하고 Redis 재고를 원복한다.
  3) coupon_issue INSERT
  4) 앱 기동 시 및 Redis 연결 복구 감지 시 워밍업 실행
         count = total_stock - (SELECT COUNT(*) FROM coupon_issue WHERE campaign_id = ?)

[핵심 포인트 — 발표에서 반드시 짚을 것]
  조건부 UPDATE에 도달하는 요청은 이미 Redis 게이트를 통과한 요청뿐이다.
  즉 20,000건이 아니라 최대 재고 수량만큼만 도달하므로,
  V2에서 문제였던 hot row 경합이 여기서는 발생하지 않는다.
  Redis가 정상일 때는 사실상 no-op에 가깝고, Redis가 상태를 잃었을 때만 작동하는 안전망이다.

[부수 효과]
  campaign.remaining_stock 컬럼의 용도가 확정된다.
  이 컬럼을 아무도 갱신하지 않으면 정합성 검증 쿼리 (c)(이력 vs 카운터 대사)가 공허해지는데,
  백스톱이 갱신 주체가 되면서 (c)가 실질적인 검증이 된다.
  → 일정과역할 4절의 미결항목 "remaining_stock 실사용 여부" 해소

[의도된 결과]
  V3와 완전히 동일한 부하 테스트 + Redis 강제 종료 조건에서
  V3는 초과발급 발생, V4는 0건 유지.


================================================================
5. 공정 비교 조건 (통제 변인) — 반드시 지킬 것
================================================================

버전 간 차이가 reserve() 외의 요인에서 오면 비교가 무효가 된다.
멘토와 심사위원이 가장 먼저 물어볼 지점이므로 사전에 통제한다.

전 버전에서 동일하게 유지할 것:

  [ ] 멱등성 처리 (Idempotency-Key 조회 및 저장)
  [ ] 멤버십 eligibility 체크 위치와 로직
  [ ] 요청/응답 DTO 및 직렬화
  [ ] coupon_issue INSERT 로직과 컬럼
  [ ] 트랜잭션 경계
  [ ] 로깅 수준 (V1만 로그가 적으면 유리해진다)
  [ ] PII 마스킹 처리
  [ ] Mock 알림 발송 호출
  [ ] DB 인덱스 구성
  [ ] 커넥션 풀 설정

구현 방법: 공유 뼈대를 추상 클래스 또는 템플릿 메서드로 한 곳에 두고,
reserve()/rollback()만 구현체가 다르게 갖는다.
버전별로 컨트롤러/서비스를 통째로 복사하면 위 항목이 반드시 어긋난다.


================================================================
6. 실험 절차
================================================================

[반복 횟수]
  각 버전 5회 실행. 1회성 우연을 배제한다.
  일정과역할 성공기준의 "반복 실행(최소 5회) 시 매번 재현" 항목과 동일 기준.

[매 실행 전 초기화 — 스크립트로 원커맨드화 필수]
  1) coupon_issue, coupon_state_log TRUNCATE
  2) campaign.remaining_stock = total_stock 으로 리셋
  3) Redis 카운터 키 삭제 (stock:*, countReq:*, count:*)
  4) 워밍업 실행
  5) k6 유저 목록(users_20000.json) 재사용 — 매번 같은 유저 집합을 쓴다

  데모 중에 이 과정을 손으로 하면 반드시 사고가 난다. 스크립트로 만들어 둘 것.

[부하 시나리오]
  기본: 재고 10,000 / 서로 다른 유저 20,000명 동시 요청
  서브: 동일 유저 중복 요청 (5,000명이 각 4회) — 1인 1매 검증용
        주의: 재고를 5,000에 딱 맞추면 데모 화면에 "재고 남았는데 왜 못 받지" 현상이
              찍힐 수 있다(countReq 조기소진). 재고를 여유 있게 잡을 것.
        상세는 리서치요약 3절 참고.

[측정 지표]
  - 최종 발급 건수 (DB COUNT 기준. k6 응답 카운트가 아니라 DB가 진실)
  - 초과발급 건수 = 발급 건수 - total_stock (음수면 0으로 표기)
  - 1인 1매 위반 건수
  - 전체 처리 완료 시간
  - p95 응답 시간 (참고용. 평가 대상 아님을 리포트에 명시)
  - 타임아웃/에러 응답 건수
  - Redis 강제 종료 조건에서의 초과발급 건수 (V3, V4만)


================================================================
7. 결과표 템플릿 (발표용 머니 슬라이드)
================================================================

이 표 하나로 전체 서사가 전달되어야 한다. 숫자는 실측으로 채운다.

  +---------------------------+----------+-----------+---------------+---------+
  |                           | 초과발급 | 처리시간  | Redis 장애 시 | 1인1매  |
  +---------------------------+----------+-----------+---------------+---------+
  | V1  제어 없음             |  ____건  |  빠름     |      —        |  0건    |
  | V2  DB 비관적 락          |   0건    |  느림     |      —        |  0건    |
  | V3  Redis 게이트          |   0건    |  빠름     |   붕괴        |  0건    |
  | V4  Redis + DB 백스톱     |   0건    |  빠름     |   0건 유지    |  0건    |
  +---------------------------+----------+-----------+---------------+---------+

읽는 법: 왼쪽 두 열은 4팀이 모두 보여주는 영역, 오른쪽 두 열이 우리가 더 한 영역.


================================================================
8. 정합성 검증과의 연결 (놓치면 아까운 지점)
================================================================

V1이 만들어내는 초과발급은 인위적으로 심은 데이터가 아니라
실제 경쟁 상태로 발생한 진짜 위반 데이터다.

기존 계획(05_시스템설계 2.3절)은 검증 배치 시연용으로 오염 데이터를 수동 삽입하는 것인데,
V1을 한 번 돌리고 그 결과를 그대로 검증 배치에 먹이면 서술이 훨씬 강해진다.

  "이건 저희가 심은 데이터가 아닙니다.
   V1을 실제로 돌려서 나온 실제 위반이고, 검증 배치가 정확히 N건을 탐지했습니다."

효과: 지금은 따로 노는 두 개의 자랑거리(버전 비교 / 정합성 검증)가 하나의 서사로 이어진다.

[실행 순서]
  1) V1 실행 → 초과발급 데이터 생성
  2) 생성된 위반 건수를 SQL로 직접 세어 기록 (기대값)
  3) 검증 배치 실행 → 탐지 건수가 기대값과 일치하는지 확인
  4) 같은 데이터로 재실행 → 결과 해시 동일 확인 (결정론성)

수동 오염 데이터 삽입도 병행한다. V1이 만들지 못하는 유형
(상태 역행, idempotency 충돌, 등급 위반)은 여전히 수동 삽입이 필요하다.

9. 구현 비용 추정
================================================================

핵심은 reserve()/rollback()만 다르고 나머지는 전부 공유한다는 점이다.

  V1   약 20줄 (사실상 제어 제거)
  V2   @Lock(PESSIMISTIC_WRITE) 한 줄 + 리포지토리 메서드
  V3a  Lua 스크립트 + 로딩/실행 코드
  V3b  INCR 2개 + 롤백 분기
  V4   V3 + 조건부 UPDATE + 워밍업 (약 50줄)

4개 버전 전부 만드는 것이 1개만 만드는 것보다 대략 1.5일 정도 더 드는 수준.
07_실행계획 기준 트랙 A(2인)가 D6~D8에 소화 가능한 범위다.
