## 2. 필수 제약조건 (Defense in Depth)

어떤 동시성 전략을 앱 레벨에서 선택하든, DB 제약이 최후 방어선 역할을 한다.

```sql
-- 1인 1매 보장의 최종 방어선: 어떤 동시성 전략을 쓰든 이 제약이 없으면 초과발급 가능
ALTER TABLE coupon_issue
  ADD CONSTRAINT uk_campaign_user UNIQUE (campaign_id, user_id);

-- 발급 요청 중복(재시도, 더블클릭, 네트워크 재전송) 방지
ALTER TABLE coupon_issue
  ADD CONSTRAINT uk_idempotency_key UNIQUE (idempotency_key);

-- 쿠폰 코드 자체의 유일성
ALTER TABLE coupon_issue
  ADD CONSTRAINT uk_coupon_code UNIQUE (coupon_code);

-- 상태전이 동시 중복요청에 대한 낙관적 락
ALTER TABLE coupon_issue ADD COLUMN version BIGINT NOT NULL DEFAULT 0;

-- 상태전이 요청의 멱등성 최종 방어선 (FR-CPS-005): 동일 request_id 재시도/중복 요청이
-- 두 번째 상태전이 로그로 남는 것을 DB가 물리적으로 거부한다
ALTER TABLE coupon_state_log
  ADD CONSTRAINT uk_state_log_request UNIQUE (request_id);
```

`uk_campaign_user`가 핵심이다. 애플리케이션 레벨 동시성 제어(Redis, Lua, 분산락 등)가 버그로 뚫리더라도, 이 유니크 제약이 있으면 **DB가 물리적으로 2번째 INSERT를 거부**한다. 재고 초과(수량 초과) 자체는 이 제약만으로는 못 막으므로 아래 3절의 전략이 필요하지만, "1인 1매"는 이 제약 하나로 100% 보장된다.

## 3. 상태 머신

```java
public enum CouponStatus {
    ISSUED, USED, CANCELED, EXPIRED;

    private static final Map<CouponStatus, Set<CouponStatus>> TRANSITIONS = Map.of(
        ISSUED,   Set.of(USED, CANCELED, EXPIRED),
        // CANCELED: 관리자 강제회수 (사용 여부 무관) — 종단 상태 유지
        // ISSUED:   주문취소(환불) 시 본인 재사용 가능 상태로 복귀 (2026-08-13 팀 결정)
        USED,     Set.of(CANCELED, ISSUED),
        CANCELED, Set.of(),
        EXPIRED,  Set.of()
    );

    public boolean canTransitionTo(CouponStatus target) {
        return TRANSITIONS.getOrDefault(this, Set.of()).contains(target);
    }
}
```

**`USED → ISSUED` (2026-08-13 팀 결정, FR-CPS-002/004 반영).** 주문 취소/환불 시 사용된 쿠폰을 본인이 재사용 가능하도록 복귀시킨다. 설계상 유의점:
- 관리자 강제회수(`markCanceled`, `USED→CANCELED`)와는 **다른 호출 경로**다 — 관리자 회수는 사용 여부와 무관하게 영구 종료시키는 것이고, 이건 주문취소로 인한 것만 대상이므로 별도 메서드로 구현해야 한다(같은 `markCanceled()`를 재사용하면 두 시나리오가 구분 안 됨).
- 복귀 시점에 `valid_until` 경과 여부를 별도로 체크할 필요 없다 — `markUsed()`도 애초에 `valid_until`을 안 보고, 만료 판정은 전적으로 아래 야간 배치(`CouponExpirationBatchJob`)가 게으르게(lazy) 처리하는 구조이므로, `ISSUED`로 복귀한 뒤 이미 기간이 지났다면 다음 배치 실행 때 자연스럽게 `EXPIRED`로 처리된다. 따라서 `USED → EXPIRED` 직접 전이는 불필요.
- 새 발급이 아니라 기존 `coupon_issue` row의 `status`만 되돌리는 것이므로 `Campaign.remainingStock`/`uk_campaign_user` 등 재고·중복발급 불변식과 무관하다(`allow_reissue_on_cancel=false`는 재고 카운터 전용 원칙이며 이 결정과는 별개 축 — 01_설계보완_검토안.md 3절 추가 결정 참고).

**만료(EXPIRED) 트리거 방식 — 배치 채택(팀 결정).** `@Scheduled` 메서드 하나로 처리한다(`MembershipTierBatchJob`과 동일 패턴, 별도 배치 서버 불필요). 조회 시점에만 "만료로 간주"하는 가상판정 방식은 채택하지 않는다 — `coupon_state_log`에 실제 로그가 안 남아 FR-VRF-001 (d) 체인 연속성 검증이 성립하지 않기 때문이다(05_시스템설계.md 1.1 (d) 참고).

배치가 매 실행마다 해야 하는 일 두 가지:
1. `UPDATE coupon_issue SET status='EXPIRED', expired_at=:now WHERE status='ISSUED' AND valid_until < :now` — `idx_ci_status_valid_until` 인덱스로 스캔
2. 갱신된 각 row마다 `coupon_state_log`에 `(from_status='ISSUED', to_status='EXPIRED', request_id=<생성값>)` INSERT — **주의**: 사용자 요청이 아니라 배치가 스스로 트리거하는 전이라 클라이언트가 주는 `request_id`가 없다. `uk_state_log_request` 유니크 제약을 만족시키려면 코드가 직접 고유값(예: UUID, 또는 `"AUTO-EXPIRE-" + couponIssueId`)을 생성해 넣어야 한다. 이 INSERT를 빠뜨리면 FR-CPS-006(감사 로그) 요구가 EXPIRED 건에 대해서만 조용히 깨진다.

## 4. 동시성 제어 전략 비교 (팀 회의 안건)

재고 초과 방지(수량 제어)를 위한 후보들. "1인 1매"는 2절의 unique constraint로 전략과 무관하게 보장되므로, 아래 비교는 **"재고 카운트 차감의 원자성을 어떻게 보장할 것인가"**에 초점을 둔다.

> [2026-08-20 갱신] (c)/(d)/(e)/(f)는 검토 후 기각됐다(4.1절 참고). 대신 아래 (g)를 채택했다.
> 표는 "왜 (c)/(f) 대신 (g)를 골랐는가"의 근거로 그대로 남겨둔다.

| 전략 | 정합성 보장 | 처리량 | 구현 복잡도 | 인프라 의존성 | 실패 모드 |
|---|---|---|---|---|---|
| **(a) DB unique constraint + 비관적 락** (`SELECT ... FOR UPDATE`) | 강함. 트랜잭션 내 row lock으로 완전 직렬화 | 낮음. 락 경합 시 대기 큐 발생, 재고 row 하나에 모든 요청이 몰림(hot row) | 낮음. `@Lock(PESSIMISTIC_WRITE)` 한 줄 | MySQL만 있으면 됨 | 락 대기 타임아웃, 데드락 가능성, DB 커넥션 풀 고갈 위험(**2026-08-19 coupon_mixed_5k_x4.js 실측으로 재현**: 5,000건 중 2,652건만 발급) |
| **(b) DB unique constraint + 낙관적 락/재시도** (`@Version`) | 강함이나 재시도 로직 필수 | 중간. 경합 심하면 재시도 폭증(thundering herd)으로 오히려 저하 | 중간. `spring-retry` `@Retryable` + 백오프 필요 | MySQL만 있으면 됨 | 재시도 스톰, 재시도 한도 초과 시 사용자 응답 실패 |
| **(c) Redis 원자적 감소** (`DECR` 또는 Lua script)를 DB 쓰기 앞단 게이트키퍼로 사용 | 강함(단일 스레드 원자성). Redis-DB 간 정합성은 별도 검증 필요 | 높음. 초당 수만 건 처리 가능, DB는 통과된 요청만 받음 | 중간. Lua script + 실패시 롤백(재고 복구) 로직 필요 | Redis 필수 | Redis 장애 시 전체 발급 중단, Redis-DB 불일치(보상 트랜잭션 필요) — **[기각, 2026-08-20]** |
| **(d) Redis + 메시지 큐(Kafka)로 비동기 분리** | 강함(게이트는 c와 동일) + 처리량/내구성 향상. eventual consistency 발생 | 매우 높음. 트래픽 스파이크를 큐가 흡수 | 높음. Kafka 운영, Consumer 멱등성, 순서보장, DLQ 설계 필요 | Redis + Kafka | 컨슈머 지연/장애 시 시차 발생, 큐 적체, 메시지 유실/중복 — 선택확장으로 보류 |
| **(e) Redisson 분산락** (`RLock`) | 강함. 캠페인 단위 락으로 임계구역 직렬화 | 낮음~중간 | 중간. lease time/watchdog 튜닝, 락 해제 누락 방지 필요 | Redis 필수 | Redis 장애 시 락 획득 불가, 타임아웃 미스로 중복 통과 가능성 — 기각(Kleppmann 2016 fencing token 비판) |
| **(f) Redis 이중 카운터** (`countReq`/`count` 분리 INCR) | 강함. `count`(2차 확정 카운터)가 독립적으로 자체 롤백하여 총 발급량이 `totalStock`을 절대 못 넘음(증명됨) | 높음. Lua 대비 오버헤드 낮음(올리브영 실측: Lua -21% vs 이중카운터 -8%) | 중간. 카운터 2개 관리 + 2차 실패 시 `count`만 롤백하는 로직 | Redis 필수(마스터 단일노드) | `countReq`만 소모되고 `count`는 실패하는 케이스가 쌓이면 재고가 남았는데도 신규 유저가 조기에 "품절" 처리됨(UX/공정성 이슈) — **[기각, 2026-08-20 — 아래 (g)로 대체]** |
| **(g) DB 선반영 + Redis 스냅샷 캐시(사전필터)** — **최종 채택** | (a)와 완전히 동일(강함). Redis는 발급을 절대 결정하지 않으므로 Redis 장애가 정합성에 영향 없음 | (a) 대비 개선. 품절 이후 요청이 DB에 도달하지 않아 hot row 경합·커넥션 풀 소모가 줄어듦 | 낮음. 기존 `CouponIssuedEvent`(AFTER_COMMIT) 패턴에 리스너 하나 추가 + 조회 시 캐시 우선 확인 | Redis 있으면 가속, 없어도 (a)로 자동 폴백 | Redis 장애/지연 시 사전필터 효과만 사라짐(=성능이 (a) 수준으로 되돌아갈 뿐, 정합성 영향 없음) |

### 4.1 확정 로드맵 — V1 → V2 → V3 (2026-08-20 갱신)

> 📌 **넘버링은 [03_버전사다리_실험설계.txt](./03_버전사다리_실험설계.txt) 기준.** 8/19

> 단순화하기로 확정했다. 이 절의 옛 "V3a/V3b/V4" 서술은 아래로 대체됐다 — 왜 버렸는지는
> 03_버전사다리 1절/V3 섹션 참고.

**V2 / MVP: (a) DB unique constraint + 비관적 락 (구현 완료)**
- 별도 인프라(Redis) 없이 MySQL만으로 "초과발급 0건"을 가장 확실하게, 가장 적은 코드로 증명 가능.
- 평가 핵심이 "정확성"이지 "처리량"이 아니므로, 우선 정확성을 낮은 복잡도로 확보하고 부하테스트로 입증하는 것이 리스크가 가장 낮음.
- 2026-08-19 coupon_mixed_5k_x4.js(캠페인 300개, 20,000건 순간 동시요청)로 hot row 경합이
  실측됐다: DB 커넥션 풀 고갈로 목표 5,000건 중 2,652건만 발급. 이 실측이 V3 채택의 직접
  근거가 됐다.

**V3 / 하드닝(최종): (g) DB 선반영 + Redis 스냅샷 캐시 (구현·병합 완료, dev 2026-08-19)**
- Redis는 발급을 절대 결정하지 않는다. 최종 판단은 항상 V2(DB 비관적 락)가 하고, Redis는
  그 결과를 사후에 복사해두는 캐시이자 DB 진입 전 사전필터다.
- 실제 구현: `CampaignStockCache`(Redis read/write, 장애 시 예외를 삼키고 null 반환 →
  호출측 DB 폴백) + `CampaignStockSnapshotListener`(AFTER_COMMIT 시점에 스냅샷 갱신) +
  `CampaignStockSnapshotReconciliationJob`(15초 주기 자가치유, TTL 60초는 최후 안전장치).
- V3a(Lua)/V3b(이중카운터)를 기각한 이유: 두 방식 모두 "Redis가 발급을 직접 결정"하는
  구조라 Redis 상태 유실 시 초과발급 리스크가 생기고, 이를 막으려면 V4(DB 백스톱)가
  반드시 필요했다. (g)는 애초에 Redis에 결정 권한을 주지 않으므로 그 리스크 자체가
  구조적으로 없다 — V4 없이도 "Redis가 죽어도 초과발급 0건"이 성립한다.
- 상세 설계·코드 구조는 [03_버전사다리_실험설계.txt](./03_버전사다리_실험설계.txt) V3 섹션 참고.

**기각안: 재고+중복 통합 Lua (알리바바 패턴)**
- 장애 시 영향범위가 재고+중복 둘 다 커지고 구현 복잡도만 상승 → 실제 채택은 안 하고 "검토했으나 기각" 발표 카드로만 사용.

**(d) Kafka 비동기 분리와 (e) Redisson**은 선택 확장으로 남김/기각. (d)는 eventual consistency가 "즉시 정합성 검증" 평가 포인트와 설명 부담이 크고, (e)는 Kleppmann(2016)의 fencing token 부재 비판으로 정합성 목적에 부적합해 기각.

**확정 로드맵: V1 고장버전(실증용, 미착수) → V2=(a) 비관적 락(완료) → V3=(g) DB 선반영+Redis 스냅샷 캐시(완료).**

### 4.2 Redis 상태 유실 대비 백스톱 — 불필요(V4 폐기, 2026-08-20)

기존 계획(V3b=Redis 이중카운터)에서는 **총량 판정 권한이 전적으로 Redis 카운터에 있어서**,
Redis가 강제 종료 후 재시작하면 카운터가 0으로 초기화되고 이미 발급된 수량과 무관하게
추가 통과가 발생하는 문제가 있었다. 그래서 DB 조건부 UPDATE 백스톱(V4)이 반드시 필요했다.

새 V3(4.1절)는 재고 확보의 최종 판단을 처음부터 끝까지 V2(DB 비관적 락)가 하고, Redis는
그 결과를 사후에 베껴두는 캐시일 뿐이다. 따라서 "Redis가 상태를 잃으면 총량 방어선이
사라진다"는 전제 자체가 성립하지 않는다 — 잃을 게 있다면 사전필터 효과(지연시간 단축)뿐,
정합성은 원래부터 Redis와 무관하게 DB가 보장해왔다. 별도 백스톱 UPDATE나 기동 시
워밍업 로직을 추가로 구현할 필요가 없다.

대신 스냅샷 자체의 신선도 관리를 위해 `CampaignStockSnapshotReconciliationJob`(15초 주기
재동기화 + TTL 60초)을 뒀다 — 이건 "총량 초과를 막는" 백스톱이 아니라 "사전필터가 오래된
값으로 잘못 품절 판정하는 것을 막는" 자가치유 장치라는 점에서 목적이 다르다.

**데모 시나리오**: 부하테스트 중 Redis를 강제 종료 → 사전필터가 죽어 모든 요청이 V2(DB)로
직행 → 지연시간은 V2 수준으로 늘지만 **초과발급은 여전히 0건** → Redis 재기동 →
재동기화 잡이 다음 주기에 스냅샷을 다시 채움. "장애를 주입해도 정합성은 흔들리지 않는다"는
같은 결론을 V4 없이 보여준다.

## 5. Idempotency 설계

### 5.1 발급(Issue) — Idempotency Key 기반

클라이언트는 요청마다 `Idempotency-Key` 헤더(예: `{userId}-{campaignId}` 또는 UUID)를 전송. `coupon_issue.idempotency_key`에 UNIQUE 제약으로 동일 키 재요청 시 DB가 두 번째 INSERT를 거부.

```java
@Transactional
public IssueResult issue(Long userId, Long campaignId, String idempotencyKey) {
    // 1) 이미 처리된 요청인지 먼저 확인 (조회로 빠른 반환)
    Optional<CouponIssue> existing = couponIssueRepository.findByIdempotencyKey(idempotencyKey);
    if (existing.isPresent()) {
        return IssueResult.alreadyProcessed(existing.get()); // 재요청도 동일 응답
    }

    // 2) 캠페인 OPEN 상태 체크 (FR-FCFS-031) — "캠페인 미오픈"은 품절/등급미달과 구분되는
    //    별도 실패 사유다. READY(아직 시작 전)/CLOSED(이미 종료) 둘 다 발급 대상이 아니므로
    //    OPEN만 통과시킨다. 실구현: [2026-08-12] campaign-not-open-check PR로 반영.
    Campaign campaign = campaignRepository.findById(campaignId).orElseThrow();
    if (campaign.getStatus() != CampaignStatus.OPEN) {
        throw new CampaignNotOpenException();
    }

    // 3) 멤버십 eligibility 체크 (회원 전용 쿠폰) — 재고 확보보다 먼저, 락 경합 유발하지 않음
    if (!campaign.isEligible(userMembershipTier(userId))) {
        throw new MembershipTierNotEligibleException();
    }

    // 4) (V3만) Redis 사전필터 — 스냅샷이 있고 "확실히 품절"이면 DB 진입 없이 즉시 반환.
    //    캐시 미스/Redis 장애 시에는 null이 와서 무조건 아래 DB 단계로 통과한다.
    Integer snapshot = campaignStockCache.getSnapshot(campaignId);
    if (snapshot != null && snapshot <= 0) throw new SoldOutException();

    // 5) 재고 확보 — V2(DB 비관적 락)가 유일한 최종 판단자. 버전(V2/V3) 무관하게 항상 이 경로.
    boolean reserved = stockReservationService.reserve(campaignId);
    if (!reserved) throw new SoldOutException();

    try {
        // 6) INSERT — uk_campaign_user, uk_idempotency_key 가 1인1매/중복요청 방어선
        //    발급 시점 계급을 스냅샷으로 함께 저장(검증쿼리 (d)가 이 값을 기준으로 판정)
        CouponIssue issue = CouponIssue.issuedNow(
            userId, campaignId, idempotencyKey, userTier, TierDiscountPolicy.rateFor(userTier));
        couponIssueRepository.save(issue);
        return IssueResult.success(issue);
    } catch (DataIntegrityViolationException e) {
        // unique 제약 위반 = 동시에 같은 요청/유저가 통과됨 → 재고 원복 후 기존 레코드 반환
        stockReservationService.rollback(campaignId);
        return IssueResult.alreadyProcessed(
            couponIssueRepository.findByCampaignIdAndUserId(campaignId, userId).orElseThrow());
    }
}
```

### 5.2 상태전이(사용/취소/만료) — 상태 머신 + 낙관적 락

```java
@Transactional
public void use(Long couponIssueId, String requestId) {
    // request_id 로 CouponStateLog 조회 → 이미 처리된 요청이면 즉시 리턴 (idempotent)
    if (couponStateLogRepository.existsByRequestId(requestId)) return;

    CouponIssue issue = couponIssueRepository.findById(couponIssueId).orElseThrow();
    if (!issue.getStatus().canTransitionTo(CouponStatus.USED)) {
        throw new InvalidStateTransitionException(issue.getStatus(), CouponStatus.USED);
    }
    issue.markUsed(); // 내부에서 status=USED, used_at=now, version++ (JPA @Version 자동 관리)
    couponStateLogRepository.save(new CouponStateLog(issue.getId(), issue.getStatus(), USED, requestId));
    // save 시점에 낙관적 락 충돌(OptimisticLockingFailureException) 발생하면 spring-retry로 재시도
}
```

`@Version` 컬럼으로 동시 상태변경 요청 중 하나만 성공하고 나머지는 `OptimisticLockingFailureException` → `spring-retry`의 `@Retryable(retryFor = OptimisticLockingFailureException.class, maxAttempts = 3, backoff = @Backoff(delay=50, multiplier=2))`로 재시도 후 최신 상태 기준 재판정. `request_id`(=idempotency key) 유니크 제약을 `coupon_state_log`에도 걸어 상태변경 API도 발급과 동일한 멱등 패턴을 따르게 한다.

## 6. 멤버십 Eligibility (회원 전용 쿠폰)

`MembershipTier` enum은 `PRIVATE < PFC < CORPORAL < SERGEANT` 순서를 가지며(이등병/일병/상병/병장, [09_기획서.md](./09_기획서.txt) 6절), `Campaign.isEligible(tier)`는 `min_membership_tier`가 NULL이면 항상 true, 아니면 `tier.ordinal() >= minMembershipTier.ordinal()`로 판정하는 순수 함수다.

**동시성 전략과의 관계**: eligibility 체크는 5.1절 `issue()`의 3단계(OPEN 상태 체크 다음)로, Redis 사전필터·재고 확보(락 획득) *이전에* 수행한다. 따라서 등급 미달 요청은 락 경합은 물론 Redis 조회에도 진입하지 않고 즉시 거부되어, V2/V3 어느 버전을 쓰든 동시성 설계에 영향을 주지 않는다. `campaign.min_membership_tier`는 캠페인 생성 시 고정되는 값이라 `campaign` row 자체에 캐시해도 된다.

### 6.1 TierDiscountPolicy — 계급별 차등 할인율 (확정)

RATE 타입 쿠폰은 발급 시점 유저 계급에 따라 할인율이 달라진다([09_기획서.md](./09_기획서.txt) 2절):

| 계급 | 할인율 |
|---|---|
| 이등병 / 일병 | 10% |
| 상병 | 30% |
| 병장 | 50% |

이 매핑은 캠페인마다 달라지는 값이 아니라 프로젝트 전역의 고정 정책이므로, 별도 테이블 없이 애플리케이션 레벨 상수(`TierDiscountPolicy.rateFor(MembershipTier)`)로 구현한다.

```java
public class TierDiscountPolicy {
    public static BigDecimal rateFor(MembershipTier tier) {
        return switch (tier) {
            case PRIVATE, PFC -> new BigDecimal("0.10");
            case CORPORAL -> new BigDecimal("0.30");
            case SERGEANT -> new BigDecimal("0.50");
        };
    }
}
```

**eligibility 체크(6절 본문) 다음, 재고 확보 이전 단계**에서 `TierDiscountPolicy.rateFor(userTier)`로 실제 적용 할인율을 확정하고, `CouponIssue.discount_value`에 스냅샷으로 저장한다(1절 CouponIssue 모델 참고). 이후 유저 계급이 바뀌어도 이미 발급된 쿠폰의 `discount_value`는 갱신하지 않는다 — 발급 로직이 매번 `Campaign`/`User`를 다시 조회하는 게 아니라 발급 시점에 값을 못 박아 저장하기 때문에 별도 처리 없이 자연히 불변이 보장된다.

### 6.2 계급 산정 배치 — `MembershipTierBatchJob`

`users.membership_tier`는 더 이상 고정값이 아니라 `orders`(1절 도메인 모델) 집계로 매월 1일 재산정되는 파생값이다. 산정 규칙(완료 주문 건수 구간, 결제금액 10,000원 기준, 캘린더 월 윈도우)은 [09_기획서.md](./09_기획서.txt) 6.2절 참고. 배치는 `MembershipTierLog`에 `from_tier`/`to_tier`/`order_count`를 남겨 재실행 시 동일 결과가 나오는지 감사할 수 있게 한다(재산정 SQL/배치 구조 상세는 [05_시스템설계.md](./05_시스템설계.txt) 참고). 이 배치는 발급 동시성 전략(4절)과 독립적으로 동작하며, 계급 값 자체는 5.1절에서 조회 시점 스냅샷으로만 사용되므로 배치 타이밍이 발급 트랜잭션에 락 경합을 유발하지 않는다.
