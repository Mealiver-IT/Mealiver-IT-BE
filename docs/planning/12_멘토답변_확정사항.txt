> 출처: `백엔드_종합프로젝트 주제 질문_멘토답변.pdf` (유레카 백엔드 4기 종합프로젝트 질문 LIST, 유플러스 멘토 답변)
> 이 문서는 심사위원 측이 직접 확정한 답변이므로 다른 모든 planning 문서보다 우선한다.
> 다른 문서와 이 문서가 충돌하면 이 문서가 맞다 — 발견 즉시 해당 문서를 수정할 것.

1. 원문 Q&A 전문 (요약 아님, 답변 그대로)
================================================================

## 1. 프로젝트 범위

1-1) 커머스 서비스 전체(주문/배송 등)를 만들어야 하는지, 선착순 쿠폰 발급/검증만 하면 되는지
  → 선착순 쿠폰 관련 기능만 진행

1-2) 로그인/알림 등 세부 과업에 나온 기능만 완성해도 되는지, 완전한 서비스 형태가 필요한지
  → 로그인은 구현하지 않되, 가상 회원 ID 또는 마스킹 가능한 식별값을 사용해 발급 주체를 식별한다

1-3) 기능 구현에 집중해야 할지, 서비스 구현에도 초점을 맞춰야 할지
  → 세부과업의 필수사항(선택사항 제외)은 모두 지켜야 하며, 주제를 벗어나지 않는 선에서 추가 기능/서비스 구현에
    성공하면 강점이 될 수 있다

## 2. 전체 전제 조건

2-1) 알림 발송 등 외부 연동 Mocking — 단순 로그 출력인지, Mock 서버 구축인지
  → 알림 발송처럼 외부 연동이 필요한 기능은 실제로 구현하지 말고, API가 있다는 가정 하에 Mocking 처리.
    예: 쿠폰 발급 시 알림 발송은 실제 구현이 아니라 발송 완료 여부 등만 체크하는 Mocking으로 처리

2-2) 정상 조건 초과발급 0건이면 충분한지, 예외 상황(상태 전이, Redis/서버 장애 중 요청 등)까지 커버해야 하는지
  → 다양한 예외 케이스 고려 및 방어로직 구현 시 강점이 될 수 있다

2-3) 더미데이터 300만 건과 검증 대상 300만 건이 같은 데이터인지
  → 동일한 데이터를 의미한다

## 3. 쿠폰 발급 시스템

3-1) [쿠폰 발급 시스템] 시작 가이드 제공의 의미
  → 기능에 대한 가이드 제공은 가능하나, 평가 대상이 아니다

3-2) [쿠폰 발급 시스템]/[쿠폰 정합성 검증]의 선택사항 진행 시 가산점이 있는지
  → 말 그대로 선택사항. 잘 구현해냈는지 여부에 따라 가산점/감점이 될 수 있다

3-3) "20,000명이 동시에 요청"의 측정 기준 — 세션 유지 vs 짧은 구간 도달 vs ramp-up 허용 여부
  → **20,000명이 동시에 요청은 모든 조가 동일한 조건으로 설정 후 측정해야 하며, 조건은 다음과 같다:**
    **테스트 유저: 20,000명 (중복 유저 없음) / ramp-up: 60초**

## 4. 서비스 실행/평가

4-1) 부하 테스트 실행 주체 — 팀이 실행한 결과를 제출하는 것인지, 심사 과정에서 직접 실행할 가능성이 있는지
  → 직접 실행해볼 수 있다

4-2) 동시성 제어의 정확성 확인 방식 — 시연/직접 실행/코드 리뷰 중 무엇인지
  → 평가 기준을 정확히 안내하기는 어렵다. 세부과업 수행여부와 전체적인 밸런스, 완성도를 평가한다.
    심사위원에게 구글드라이브(깃허브, 소스코드, 시연영상 등)를 사전에 공유하는 점 참고

## 5. 평가 기준(가산점 등)

5-1) 차별화 요소가 있다면 어떤 부분인지
  → 평가 기준을 정확히 안내하기는 어렵다. 세부과업 수행여부와 전체적인 밸런스, 완성도를 평가한다.

5-2) 명세의 최소 조건 외에 더 어려운 조건에서 검증하면 긍정적으로 반영되는지
  → 필수 세부과업은 반드시 지키고, 주제를 벗어나지 않는 선에서 검증에 성공하면 강점이 될 수 있다
