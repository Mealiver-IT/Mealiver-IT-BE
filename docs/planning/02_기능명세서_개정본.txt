개정 요약 — v1에서 무엇이 바뀌었나
================================================================

[A] 신규 추가 17건 — 과제 요구사항 중 v1에 없던 영역

  v1은 배달앱 서비스 기능은 잘 정리했으나, 과제의 두 축 중
  [쿠폰 정합성 검증] 축이 통째로 빠져 있었다. 구체적으로 누락됐던 것:

    - 쿠폰 사용/취소/만료 상태 관리 및 상태 전이 멱등성
    - 300만 건 대상 정합성 자기검증 수단
    - 재실행 시 동일 결과(결정론성)
    - 유저 100만 / 이력 300만 더미데이터
    - PII 마스킹
    - 알림 발송 Mocking
    - 캠페인 오픈 시각(11시) 제어

  → FR-CPS(6건) / FR-VRF(4건) / FR-DAT(3건) / FR-SEC(2건) / FR-NOT(1건) / FR-FCFS-005 추가

[B] 모순 해소 3건

  1. 할인율 이중 정의
     FR-MBR-004(상병 10%/병장 20%)와 FR-FCFS-002(상병 30%/병장 50%)가 충돌했다.
     → 서로 다른 쿠폰 정책임을 명시. MBR-004는 "월간 계급 혜택 쿠폰",
       FCFS-002는 "선착순 캠페인 전용 정책"으로 분리 명명.
       TierDiscountPolicy 상수로 구현하는 것은 FCFS-002 쪽이다.

  2. FR-FCFS-011의 "중 택1"
     Redis 원자연산 / 분산락 / DB 조건부 UPDATE 중 택1로 되어 있었다.
     → 우리 최종 설계(V4)는 택1이 아니라 Redis 게이트 + DB 조건부 UPDATE 병용이다.
       택1로 구현하면 Redis 장애 시 총량 방어선이 사라지고,
       발표의 핵심 데모(장애 주입 후에도 0건)가 성립하지 않는다.
       분산락은 04_아키텍처 4.1절에서 이미 기각(Kleppmann 근거)했으므로 선택지에서 제외.

  3. 계급 명칭 불일치
     "이병"(MBR-001) / "이등병"(FCFS-002) 혼용 → ENUM PRIVATE 기준으로 "이등병" 통일

[C] 이미 확정된 사항 반영 2건

  - FR-MBR-001 산정 윈도우: "확정 필요" → 캘린더 월 확정 (09_기획서 6.2)
  - FR-MBR-003 금액 기준: "확정 필요" → paid_amount(결제=할인 후) 확정 (09_기획서 6.2)

[D] 스키마 보완 요청 2건 (06_ERD 반영 필요)

  - coupon / coupon_issue 에 max_discount_amount 컬럼 추가
    정률 50% 쿠폰에 한도가 없으면 10만원 주문에 5만원이 할인된다.
    discount_value와 동일하게 coupon_issue에도 발급 시점 스냅샷으로 저장한다.
  - coupon_issue.issued_membership_tier 컬럼 (01_설계보완검토안 0절 #3에서 이미 반영됨)

[E] 컬럼 추가 — "단계"

  5인 2주 조건에서 무엇을 언제까지 만들어야 하는지 명시하기 위해
  게이트 기준(07_실행계획 2절)을 컬럼으로 추가했다.
    G1 = D5 소규모 E2E 게이트까지 / G2 = D9 풀스케일 게이트까지
    G3 = D14 발표까지 / 선택 = 시간 여유 시

6. 동시성·재고 (FCFS-01x) — 프로젝트 핵심
================================================================

| 기능 ID | 기능명 | 우선순위 | 단계 | 상세 기능 | 설명 |
|---|---|---|---|---|---|
| FR-FCFS-010 | 원자적 재고 차감 | 상 | G2 | 한정 수량(10,000장)을 원자 연산으로 1건씩 차감하며 잔여가 0 이하가 되는 차감은 거부 | 20,000명 동시 요청에도 정확히 10,000건만 성공시키는 핵심. read-then-write 방식 금지, 단일 원자 연산으로 처리 |
| FR-FCFS-011 | 동시성 제어 — 다층 방어 | 상 | G2 | 다중 서버·인스턴스 환경에서 재고 차감을 경쟁 조건 없이 처리한다. **1차 게이트 = Redis 원자 연산(Lua 또는 이중 카운터), 2차 방어선 = DB 조건부 UPDATE(`UPDATE campaign SET remaining_stock = remaining_stock - 1 WHERE id = ? AND remaining_stock > 0`)를 병용한다.** | **v1의 "중 택1"에서 변경.** 택1로 구현하면 Redis 상태 유실 시 총량 방어선이 사라져 초과발급이 발생한다(uk_campaign_user는 1인 1매만 막고 총량은 못 막음). | FR-FCFS-012 | 재고 소진 감지·조기 마감 | 상 | G2 | 잔여 수량 0 도달 시 이벤트 상태를 '조기 마감/수령 완료'로 자동 전환하고 이후 요청은 즉시 마감 응답 | 마감 상태는 원자적 재고 값과 정합성 유지. 마감 후에는 DB 접근 없이 Redis 단계에서 즉시 거부 |

| FR-CPS-002 | 쿠폰 취소 처리 | 상 | G1 | 주문 취소/환불 시 쿠폰을 취소 처리한다. ISSUED → CANCELED, USED → CANCELED 전이, canceled_at 기록 | **취소해도 재고는 복구하지 않는다**(allow_reissue_on_cancel = false). 재고는 발급 이벤트 기준 단조감소. 01_설계보완검토안 3절 |
| FR-CPS-003 | 쿠폰 만료 처리 | 상 | G2 | coupon_issue.valid_until(발급 시점 스냅샷 = issued_at + coupon.valid_days) 경과 쿠폰을 만료 처리한다. ISSUED → EXPIRED, expired_at 기록 | 배치 또는 조회 시점 판정 방식 중 택1. 어느 쪽이든 검증 쿼리가 NOW()에 의존하지 않도록 expired_at을 실제 컬럼으로 기록할 것(FR-VRF-002의 결정론성 요구). valid_until을 스냅샷 컬럼으로 둔 이유는 discount_value 등과 동일 — coupon.valid_days가 나중에 바뀌어도 이미 발급된 건의 마감일은 불변이어야 하기 때문(06_ERD 반영됨) |
| FR-CPS-004 | 상태 전이 규칙 강제 | 상 | G1 | 허용 전이만 수행하고 그 외는 거부한다. 허용: ISSUED→USED, ISSUED→CANCELED, ISSUED→EXPIRED, USED→CANCELED. CANCELED와 EXPIRED는 종단 상태 | CouponStatus enum의 canTransitionTo()로 구현. 04_아키텍처 3절 |
| FR-CPS-005 | 상태 전이 멱등성 | 상 | G2 | 동일 request_id의 상태 변경 요청이 반복·동시에 들어와도 정확히 1회만 반영하고 동일 결과를 반환한다 | coupon_state_log.request_id 유니크 제약 + coupon_issue.version(@Version) 낙관적 락. 충돌 시 spring-retry로 재시도 후 최신 상태 기준 재판정. 04_아키텍처 5.2절 |

9. 정합성 검증 (VRF) — 신규
================================================================

과제 원문 "어떤 상황에서도 이력과 재고가 어긋나지 않아야 하며, 이를 스스로 검증할 수 있는
수단(검증 쿼리, 검증 배치 등)을 함께 구현한다. 검증은 300만 건 전체를 대상으로 하며,
같은 데이터 기준으로 재실행하면 같은 결과가 나와야 한다"에 대응한다.

| 기능 ID | 기능명 | 우선순위 | 단계 | 상세 기능 | 설명 |
|---|---|---|---|---|---|
| FR-VRF-001 | 정합성 검증 쿼리 6종 | 상 | G2 | 300만 건 전체 대상으로 다음을 검증한다. (a) 캠페인별 발급 수량이 재고 초과 여부 (b) 유저당 캠페인별 중복 발급 (c) 이력과 캠페인 카운터 대사 (d) 상태 전이 유효성 및 로그 체인 연속성 (e) 등급 미달 유저 발급 (f) 계급과 orders 집계 일치 | **01_설계보완검토안 0절에서 수정된 버전을 사용할 것.** 원본에는 INNER JOIN으로 인한 탐지 누락(c·f), 변동값 비교로 인한 false positive(e), ORDER BY 부재 등 결함이 있었다. 05_시스템설계 1.1절 |
| FR-VRF-002 | 결정론성 보장 | 상 | G2 | 동일 데이터 기준으로 재실행하면 항상 동일한 결과가 나온다. 결과셋을 정렬 후 JSON 직렬화하고 SHA-256 해시로 재실행 동일성을 기계적으로 확인한다 | 규칙: NOW()/CURRENT_TIMESTAMP 등 실행 시점 의존 조건 금지 / 시간에 따라 변하는 값 대신 발급 시점 스냅샷과 비교 / 모든 쿼리에 ORDER BY 명시 / 탐지 누락을 만드는 INNER JOIN 금지 |
| FR-VRF-003 | 오염 데이터 탐지 검증 | 상 | G3 | 의도적 위반 데이터를 삽입한 뒤 검증 로직이 유형별로 정확히 탐지하는지 확인한다. 유형: 초과발급 / 중복발급 / 상태 역행 / idempotency 충돌 / 등급 위반 | **"위반 0건"만 보여주는 것은 아무것도 증명하지 못한다** — 검증 로직이 비어 있어도 같은 결과가 나오기 때문. 양방향(정상 데이터 0건 + 오염 데이터 정확히 N건) 테스트가 필수. 추가로 V1 전략(03_버전사다리 4절)을 실제 실행해 발생한 진짜 초과발급 데이터를 탐지 대상으로 사용하면 시연 설득력이 크게 올라간다 |
| FR-VRF-004 | 검증 결과 리포트 | 중 | 선택 | 검증 결과를 위반 유형별 건수·샘플·원인 추정과 함께 리포트로 출력한다(Markdown 또는 HTML) | Spring Batch ConsistencyVerificationJob 결과를 verification_result 테이블에 적재 후 리포트 생성. MVP는 SQL 수동 실행으로 충족 가능하므로 선택 |
