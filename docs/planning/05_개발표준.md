## 1. Java 코딩 표준

- 클래스/레코드: PascalCase (`CouponIssue`, `CampaignService`), 메서드/필드: camelCase, 상수: UPPER_SNAKE_CASE
- 컨트롤러는 `*Controller`, 불변 데이터는 `record`(DTO), 엔티티는 `final` 필드 + getter만
- **생성자 주입만 사용, `@Autowired` 필드 주입 금지**
- `Optional`은 `find*` 메서드 반환에만, `get()` 대신 `map/orElseThrow`
- 도메인 예외는 언체크로 분리 정의 (`SoldOutException`, `InvalidStateTransitionException` — [02_아키텍처.md](./02_아키텍처.md) 5절과 일치)
- 패키지 구조 ([04_기술문서.md](./04_기술문서.md) 2절 경로와 일치):

```
com.mealiverit.coupon/
  config/       # @EnableCaching, @EnableAsync, JpaConfig 등
  controller/
  service/
  repository/
  domain/       # CouponIssue, Campaign, CouponStateLog
  dto/
  batch/        # ConsistencyVerificationJob
```

## 2. Spring Boot API 패턴

- 계층: Controller(얇게) → Service(`@Transactional`) → Repository. 컨트롤러에서 엔티티 직접 반환 금지, 항상 DTO 경유([03_시스템설계.md](./03_시스템설계.md) 3.2절 PII 마스킹과 동일한 이유)
- 요청 DTO는 Bean Validation(`@Valid`, `@NotBlank`, `@NotNull`) 필수
- 전역 예외 처리는 `@RestControllerAdvice` 하나로 통일 (`SoldOutException`→409, `InvalidStateTransitionException`→409, validation→400)
- 읽기 전용 쿼리는 `@Transactional(readOnly = true)`
- **Rate limiting 사용 시 주의**: `X-Forwarded-For`는 신뢰할 수 없는 헤더. 로컬 Docker Compose 환경(프록시 없음)에서는 `request.getRemoteAddr()`를 그대로 사용

## 3. 보안 체크리스트 (기능 완성 후 PR 전 확인)

이 프로젝트에서 실제로 의미 있는 항목만 채택:

- [ ] **DB 자격증명**: `100.125.247.64:3306` 접속 정보는 `application.properties`에 하드코딩 금지 → 환경변수(`DB_URL`, `DB_USER`, `DB_PASSWORD`)로 주입
- [ ] **SQL Injection**: [03_시스템설계.md](./03_시스템설계.md) 1절 검증 쿼리·Spring Batch native query는 반드시 파라미터 바인딩(`:param`), 문자열 연결 금지
- [ ] **PII 마스킹**: 로그/응답 경로 모두 마스킹 컨버터·시리얼라이저 경유 확인 (FR-06, [03_시스템설계.md](./03_시스템설계.md) 3절)
- [ ] **에러 응답**: `e.getMessage()`나 스택트레이스를 API 응답에 그대로 노출하지 않음 — 도메인 에러코드로 매핑
- [ ] **로그**: `System.out.println` 대신 SLF4J, 발급/상태전이 로그에 원본 PII 없는지 확인
- [ ] **Idempotency key 노출**: 발급 요청 실패 응답에도 idempotency key 재사용 가능하도록 일관된 응답 반환(재시도 유도)

의도적으로 제외: 인증/인가(JWT, `@PreAuthorize`), CSRF, CORS, 파일업로드, 블록체인 — 이 과제 범위(회원가입/로그인 미구현, 가상 회원)에 해당 없음.

// 전략 (a) 비관적 락 — MVP 재고 차감
public interface CampaignRepository extends JpaRepository<CampaignEntity, Long> {

- HikariCP: DB가 Tailscale 경유 원격(로컬 대비 네트워크 지연 있음) → `connection-timeout`, `validation-timeout`을 로컬 기준보다 여유 있게 설정하고, 부하테스트 전 실측으로 조정
- N+1 방지: 발급 이력 조회 시 `JOIN FETCH` 또는 DTO 프로젝션, `EAGER` 금지

## 5. TDD 워크플로우 (JUnit5 + Mockito + MockMvc + Testcontainers)

순서: 실패하는 테스트 작성 → 최소 구현 → 리팩터링 → 커버리지 확인(JaCoCo 80%+, [04_기술문서.md](./04_기술문서.md) 3절과 동일 기준이나 이 프로젝트는 **동시성 시나리오 재현성이 커버리지 수치보다 우선**).

@ExtendWith(MockitoExtension.class)

### 5.1 회원 전용 쿠폰 테스트 (예: 병장 전용 캠페인)

3단계로 나눠서 검증한다 — 단일 요청 거부(단위) → 동시 요청 거부(통합) → 사후 검증(SQL/배치).

```java
// 1) 단위: 등급 미달 단건 요청은 즉시 거부
@Test
void 이등병_병장전용쿠폰_요청시_거부() {
  when(campaignRepository.findById(sergeantOnlyCampaignId))
      .thenReturn(Optional.of(campaignWithMinTier(SERGEANT)));
  when(userRepository.findMembershipTier(privateUserId)).thenReturn(PRIVATE);

  assertThatThrownBy(() -> service.issue(privateUserId, sergeantOnlyCampaignId, "key-1"))
      .isInstanceOf(MembershipTierNotEligibleException.class);
}
```

```java
// 2) 통합: 등급 미달 유저 다수가 동시에 눌러도 0건 발급 (더미데이터의 이등병/일병/상병 유저 섞어서)
@Test
void 등급미달_동시요청_전부거부() throws InterruptedException {
  int threads = 100;
  ExecutorService pool = Executors.newFixedThreadPool(threads);
  CountDownLatch latch = new CountDownLatch(threads);

  for (Long userId : ineligibleTierUserIds(100)) { // SERGEANT 미만 유저 100명
    pool.submit(() -> {
      try {
        service.issue(userId, sergeantOnlyCampaignId, UUID.randomUUID().toString());
      } catch (MembershipTierNotEligibleException ignored) {
      } finally {
        latch.countDown();
      }
    });
  }
  latch.await();

  assertThat(couponIssueRepository.countByCampaignId(sergeantOnlyCampaignId)).isZero();
}
```

3) 사후 검증(실제 더미데이터 300만 건 기준): [03_시스템설계.md](./03_시스템설계.md) 1.1절 (e) 쿼리 실행 — 등급 미달 유저에게 발급된 row가 0건인지 확인. 병장 전용 캠페인은 재고를 병장 티어 더미 유저 수(약 10만 명, [01_기획서.md](./01_기획서.md) 6.2절 비중 기준)보다 작게 잡아야(예: 500장) 선착순 초과발급 여부도 같은 캠페인에서 함께 시연 가능.
