# retry_mix 시나리오 — 동일 유저 5,000명 × 4회 재요청

체크리스트: **"동일 유저 5,000명×4회 재요청" 혼합 시나리오 추가**

## 뭘 테스트하나

같은 유저 N명이 각자 **같은 Idempotency-Key로 4번씩** 재요청을 보냅니다. 네트워크
타임아웃/중복클릭 때문에 클라이언트가 같은 요청을 재전송하는 상황을 흉내낸 것으로,
핵심 확인 포인트는 두 가지입니다.

1. **1인 1매**: 같은 유저가 4번 요청해도 실제로 발급되는 쿠폰은 1개뿐이어야 함
2. **멱등성**: 재시도로 받은 응답(2~4번째)이 최초 발급분과 **같은 쿠폰**을 가리켜야 함
   (실제 API 기준 최초 성공만 `201`, 이후 재시도는 `200`으로 같은 쿠폰을 재응답해야 정상)

- 스크립트: [`retry_mix.js`](retry_mix.js) (독립 실행형, `retryScenario` 기본 export)
- VU 수: `RETRY_USERS` (원래 요청사항은 5,000명)
- 유저당 요청 수: `RETRY_ATTEMPTS` (기본 4회)
- Idempotency-Key: **같은 유저는 4회 모두 동일한 키** (진짜 재시도 흉내)
- 재시도 사이 대기: `RETRY_BACKOFF` (기본 1초)
- ramp-up: 15초 (`RAMP_UP`)
- 커스텀 메트릭 `retry_duplicate_issue_rate`: 같은 유저의 재시도 응답들이 서로 다른
  쿠폰을 가리키거나 두 번째 이후에도 `201`이 또 나오면 "진짜 멱등성 버그"로 집계 (임계값 1%)

## 실행 방법

`race.js`와는 별개 파일이라 같이 실행할 일 자체가 없습니다 (원하면 다른 터미널에서
동시에 돌릴 순 있지만, 원인 분리를 위해 항상 하나씩만 돌리는 걸 권장합니다).

```bash
# 로컬 스텁 서버
k6 run -e RETRY_USERS=5000 retry_mix.js

# 실제 API (사전에 테스트 전용 캠페인 만들고 OPEN 상태로, 재고는 5,000 이상 권장)
k6 run -e API_MODE=real -e CAMPAIGN_ID=<campaignId> -e USER_ID_BASE=<안 쓴 범위> \
  -e RETRY_USERS=5000 -e BASE_URL=http://<서버>:8080 retry_mix.js
```

결과(로그/summary/대시보드 html)는 저장소에 커밋하지 않았습니다 (실행할 때마다 새로
생기는 산출물이라 — 아래 결과는 실제로 실행해서 나온 수치를 요약해둔 것입니다).

## 지금까지 결과 (재고 5,000 vs 5,000명 × 4회, 실제 API)

**원칙**: k6 자체 집계(client 쪽 요약)만으로 끝내지 않고, 각 회차마다 **서버 쪽 실제 값
(재고 API `remainingStock`/`issuedCount`, 그리고 개별 유저의 `GET /api/members/me/coupons`)
으로 재검증**했습니다. k6가 응답을 받았다고 "성공"으로 집계해도 실제 DB에 반영 안 됐을
수 있다는 걸 run4에서 직접 겪었기 때문입니다 (아래 run4 항목 참고).

| 회차 | 캠페인 | k6 발급 성공 | k6 409 | `retry_duplicate_issue_rate` | p95 | **서버 재검증 (issuedCount / remainingStock)** |
|---|---|---|---|---|---|---|
| `my-run1` | 332 | 20,000/20,000 | 0 | 0.00% | — | 검증 안 함 (당시엔 이 원칙이 없었음) |
| `retry-5kx4-run1` | 329 | 20,000/20,000 | 0 | **0.00%** | 1.74s | **5,000 / 0** — `totalStock`과 정확히 일치, 유저 3명 샘플링 전부 1개 |
| `retry-5kx4-run2` | 330 | 20,000/20,000 | 0 | **0.00%** | 1.76s | **5,000 / 0** — 일치, 유저 3명 샘플링 전부 1개 |
| `retry-5kx4-run3` | 331 | 20,000/20,000 | 0 | **0.00%** | 1.72s | **5,000 / 0** — 일치, 유저 3명 샘플링 전부 1개 |
| `retry-5kx4-run4` | 466 | (k6 summary 없음, 아래 참고) | | | | **5,000 / 0** — 일치, 유저 8명 샘플링 전부 1개 |

run1~3의 서버 재검증은 **사후에(이 피드백을 받고 나서) 다시 조회**한 것입니다 — 캠페인이
`CLOSED` 상태여도 `GET /api/campaigns/{id}/stock`, `GET /api/admin/campaigns/{id}/stats`,
`GET /api/members/me/coupons`는 과거 값을 그대로 보여주기 때문에 뒤늦게라도 검증이
가능했습니다. 세 회차 다 **k6가 보고한 수치와 서버 실측치가 정확히 일치**함을 확인했습니다.

**run4는 k6 자체 요약이 없습니다.** 첫 시도(campaign 465) 때 k6는 20,000/20,000 성공을
보고했는데 실제로는 유저 계정에 쿠폰이 하나도 생성되지 않은 이상 현상이 있었습니다
(원인 불명 — 비슷한 시점에 대상 서버가 한동안 응답 없음/빈 응답 상태였던 것과 관련
있을 가능성). 그 결과는 폐기하고, **새 캠페인(466)으로 재실행하면서 이번엔 k6 프로세스
자체가 도구 타임아웃으로 중간에 종료**됐지만(그래서 client 쪽 summary.json이 없음),
종료 시점에 이미 서버 쪽 재고가 다 소진돼 있어서 **서버 통계로 직접 검증**했습니다:

- `issuedCount: 5000`, `remainingStock: 0` (`totalStock: 5000`과 정확히 일치)
- 유저 8명 무작위 샘플링(`GET /api/members/me/coupons`) — **전부 이 캠페인 쿠폰 정확히 1개**

즉 client 쪽 요약 파일은 없지만, 서버 쪽 실제 데이터로 **1인 1매 + 초과발급 0건**을
run1~3과 동일하게 재확인했습니다.

정리하면 **4번 모두 재고 5,000개 = 발급 5,000개(1인 1매), 진짜 멱등성 버그 0건**으로
재현됐습니다. retry_mix 시나리오는 단독으로 완벽하게 동작합니다. 자세한 경위는
[`../RESULTS.md`](../RESULTS.md) 참고.
